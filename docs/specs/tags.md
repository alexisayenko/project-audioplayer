## Semantics

- TAG-001 MUST: tags are the only grouping mechanism; there is no playlist entity and no `genre` field. A "playlist" is a tag filter. Status: implemented
- TAG-002 MUST: a tag is a plain string (`workout`) or namespaced `key:value` (`genre:synthwave`, `mood:chill`). Status: implemented
- TAG-003 MUST: the first `:` splits key and value. Status: implemented

## Normalisation (server: create, PATCH, preview, migration)

- TAG-010 MUST: whitespace is trimmed and runs of spaces collapsed. Status: implemented
- TAG-011 MUST: a valid `key:value` (both parts non-empty) is stored lowercased. Status: implemented
- TAG-012 MUST: a plain tag keeps its case. Status: implemented
- TAG-013 MUST: a tag with `:` but an empty key or value is dropped, never saved as a plain tag (`mood:` and `:x` vanish). Status: implemented
- TAG-017 MUST: the tag editor commits leftover input text on Save only if it is a complete tag (non-empty; for `key:value` both parts non-empty); an incomplete `mood:` or `:x` is ignored. Status: implemented
- TAG-014 MUST: empty tags are dropped; duplicates are removed case-insensitively, first occurrence wins, order preserved. Status: implemented
- TAG-056 MUST: `country:` and `lang:` values are canonicalised to ISO codes (`server/app/countrycodes.py`, `server/app/langcodes.py`, embedded tables, no dependency): a country given as alpha-2, alpha-3, English name or alias (`usa`, `U.S.A.`, `United States of America`, `uk`/`england` to `gb`, `russia`/`Russian Federation` to `ru`, `holland` to `nl`, `Deutschland` to `de`, `Türkiye` to `tr`) becomes `country:<alpha-2>`; compared case, accent, punctuation and a leading "the" ignored. A language name (English or native, `russian`, `Deutsch`), 639-3 code or region-tagged code becomes `lang:<639-1>`. Duplicates collapse after mapping (`country:usa` + `country:us` give one). Historical countries are a closed list of first-class values (TAG-058): `ussr`, `cccp` and `Soviet Union` map to `country:su`; other former states map to nothing. Applied in `library.clean_tag` on every write and on load (the load migration; idempotent, saved with the next write). The web client canonicalises and merges counts defensively (`mergeTagCounts`, `web/js/tagname.js`, `countries.js`). Status: implemented
- TAG-059 MUST: the web resolves every typed or suggested country through ONE function, `canonicalCountry` in `web/js/countries.js` (alias, name and code table `countries-data.js`, generated by `scripts/gen-countries.py`); `countryCode` in `metadata-apply.js`, the tag editor, the chip field and the tag display all call it, so the picker, the pills and the Add form never disagree on a code. Status: implemented
- TAG-057 MUST: `country:` accepts only known countries: creating or editing a song with an unknown `country:` value is refused (API-052); legacy unmapped values are kept untouched on load (a warning is logged) and shown in the editor as flagged chips that can be removed; suggestions from MusicBrainz and Wikidata emit only ISO codes (`XW`, `XE` and similar are dropped; MusicBrainz `SU` is kept as `country:su`). The tag editor opens a searchable country list (English names, codes and aliases) after `country:`; typing an unknown country shows "Pick a country from the list" and adds nothing. `lang:` stays free for unknown values. Status: implemented
- TAG-058 MUST: historical countries. `country:su` (display name "Soviet Union", ISO 3166-3 former code, alpha-3 `SUN`) is a predefined value: accepted on write, never flagged as unknown, offered by the country picker (search `soviet`, `ussr`) and suggested from MusicBrainz or Wikidata code `SU`. Aliases `ussr`, `u.s.s.r.`, `soviet union`, `the soviet union`, `cccp`, `sssr` map to `su`. The table marks such codes `historical` (`countrycodes.is_historical`, `isHistoricalCountry` in `web/js/countries.js`); names come from the table, not `Intl.DisplayNames`, which does not know them. Reason: flags will be shown later, and no emoji flag exists for a former state, so flag assets for historical codes must be images. Candidates, add on request: `yu` Yugoslavia, `cs` Czechoslovakia, `dd` East Germany. `web/js/countries-data.js` is generated from the table: run `python3 scripts/gen-countries.py` after editing `countrycodes.py`. Status: implemented
- TAG-016 MUST: namespaces `country:` (ISO 3166-1 alpha-2, e.g. `country:lt`) and `lang:` (ISO 639-1, e.g. `lang:ru`) are ordinary tags with normalised values: lowercase; `lang:` is no longer suggested (languages dropped, ADR-0012 note) but existing `lang:` tags keep this normalisation: a 3-letter code with a 2-letter equivalent is mapped (`rus` to `ru`) and a region suffix is dropped (`ru-RU` to `ru`); unknown `lang:` shapes are kept as plain lowercase tags, never rejected (`country:` is stricter, TAG-057). Status: implemented
- TAG-050 MUST: decade tags: the server derives `decade:<NN>s` from `year` for every year from 1950 up to `max_year()` (the current UTC year + 1; `decade:50s` ... `90s`, `00s`, `10s`, `20s`, then `30s` once the clock reaches 2029 with no code change; rule: floor(year/10)*10 mod 100 as two digits + `s`; 1994 gives `decade:90s`, 2007 `decade:00s`, 2013 `decade:10s`); a year below 1950, above `max_year()` or missing derives nothing. Groups sort chronologically, future decades last. Status: implemented
- TAG-051 MUST: on every create, PATCH and load, when `year` is in range the song's `decade:*` tags are replaced by exactly the derived one (a manually typed or stale decade tag is overwritten, so changing the year updates it); when the year is missing or out of range existing `decade:` tags are left untouched. Existing songs with a year are migrated on load and saved on the next write. Status: implemented
- TAG-052 MUST: the `decade:` value is lowercased like any `key:value`; a value not matching `^\d{2}s$` is kept as a plain-normalised tag, never rejected. Status: implemented
- TAG-053 MUST: the Genres field suggests values from `GET /genres` (API-050) while typing: the user's own genres first, then common ones; a suggestion is added as a `genre:<value>` tag, free text stays allowed. Status: implemented (server, WEB-030, IOS-067)
- TAG-054 MUST: feat-aware artist matching: the saved artist keeps its `feat.` credit; `titles.lookup_credits` splits it into the primary artist and the featured names (split on `,`, `&`, ` and `, ` x `). The query text stays the primary artist, but among the MusicBrainz recordings credited to the primary artist the lookup prefers the first one whose credit also has every featured name (case and accent insensitive; else the first one, as without feat), and takes the primary artist's id from that credit for country, genres and the Wikipedia/Wikidata artist links, so two same-named artists are told apart ("Kato feat. Jon" gives the Danish Kato, `country:dk`). It extends the fallback chain of TAG-047: song page genres, then the artist page's infobox genres, then Wikidata; in the guessed path (`/preview`, and the guess of `POST /metadata`) a song page whose infobox `artist` does not match the primary artist is never attached (no genres, album, year or link from it); links the user gave are used as given. Status: implemented
- TAG-055 MUST: suggested `genre:` tags are filtered and canonicalised before the caps (TAG-047 order and caps unchanged, so dropped tags use no slot) in `metadata.finalize_tags` (`server/app/genre_filter.py`), the one rule shared by `POST /metadata`, `POST /preview` and `POST /lookup/wikipedia`: values that are not genres are dropped (nationalities and countries, roles such as dj/producer/band, MusicBrainz meta tags such as seen live/favorites/female vocalists, decade-like tags and plain years, language names, city names, and the words music/songs/single/remix/cover/live/official), matched lowercase, accent-folded, ignoring spaces and hyphens; a trailing " music" is stripped ("house music" gives "house") unless the built-in genre list has that exact name ("bass music"); a spelling matching a built-in genre uses the built-in spelling ("hip-hop" gives "hip hop"); duplicates then collapse, first one kept. Genres the user enters (create, PATCH) are never filtered. Status: implemented
- TAG-015 SHOULD: limit tag count and length (today none is enforced; only suggestions are capped, TAG-023; the web chip fields cap a song at 12 genres (`GENRE_CAP`, `metadata-apply.js`) and 1 country; the server enforces nothing; `api.tags` (`GET /tags`) is unused client code). Status: to-confirm

## Tag suggestions (Add preview only)

- TAG-020 MUST: suggested `genre:` tags come from exactly two sources: yt-dlp's real `genre` field and MusicBrainz. YouTube categories are never used. Status: implemented
- TAG-021 MUST: yt-dlp `genre` (string or list; strings split on `,` and `;`) becomes `genre:<value>` tags. Status: implemented
- TAG-022 MUST: the MusicBrainz lookup runs in `/preview` only, never at save. Artist and title are cleaned of noise (`Official Video`, `- Topic`, `VEVO`) and of feat/ft/featuring credits (kept in the saved values, ADD-075) and the title also of version info (`(Live from ...)`, `(Acoustic)`, see ADD-073), for the query only; a recording is accepted at score >= 90 with a loosely matching artist; genres and tags of the recording (else of the artist) are ranked by votes; top 3 are returned. Status: implemented
- TAG-023 MUST: yt-dlp and MusicBrainz tags are merged, normalised, de-duplicated and capped per namespace, with `lang:` dropped, by one rule shared by `POST /metadata` (`metadata.merge`, API-048), `POST /preview` (`preview.tags`) and `POST /lookup/wikipedia` (`metadata.finalize_tags`): genre 8 overall (TAG-055 filter first; the song's own genres, infobox and Wikidata, come first and are exempt from the cap, up to 12) and country 1. The user can edit them before saving. Status: implemented
- TAG-024 MUST: a lookup failure, timeout (5 s), no match, or `AUDIO_TAG_LOOKUP` or `AUDIO_GENRE_LOOKUP` (alias) in `0|false|no|off` yields no tags and never fails `/preview`. Status: implemented
- TAG-025 MUST: MusicBrainz calls are limited to ~1 request/s globally and cached in memory per (artist, title, featured names); concurrent lookups of one key share one fetch. One retry after 1 s on HTTP 503 (TAG-027). Status: implemented
- TAG-026 MUST: suggestions are written to a song only when the user saves the Add form. Status: implemented
- TAG-027 MUST: the same MusicBrainz lookup also suggests `country:<code>` from the matched artist's `country` (nothing when missing); no `lang:` tag is suggested from work languages or from yt-dlp's `language` field (languages dropped). The lookup also returns an `album` (used by `POST /metadata`): the release credited to the matched artist whose release group is an Album or EP (never a Single) without Compilation/Mixtape/DJ-mix/Live/Remix types, Albums first, then official releases, then the earliest date; none otherwise. One retry after 1 s on HTTP 503. A failing artist call keeps the recording's tags. Status: implemented

## Suggestions from Wikipedia and Wikidata

- TAG-040 MUST: the MusicBrainz lookup also requests `url-rels` (recording, artist; the first linked work when the recording has none) and picks the `wikipedia` relation, English preferred, else the `wikidata` one resolved to an English (else any) Wikipedia sitelink via `Special:EntityData/Q<id>.json`, else kept as the Wikidata URL. They go to `preview.wikipedia_song` / `wikipedia_artist`. Status: implemented
- TAG-041 MUST: facts come from structured Wikidata claims; article text is read only for the infobox `genre`, `album` and `released` parameters (TAG-045 to TAG-048), by a deterministic parser, never by AI: genre `P136` (English label; all of the song's own genres first, max 12, then the artist's, which fill only the remaining slots of the overall cap of 8; one batched `wbgetentities` call), country from the artist's `P495`, else `P27`, else `P740` via the place's `P17`, else the song's `P495`, mapped through `P297` to `country:xx` (the song's `P407` language is not used); year from the song's `P577` (earliest, precision year or finer), else MusicBrainz `first-release-date`; the artist's inception `P571` is never a song year. Status: implemented
- TAG-042 MUST: these merge into `preview.tags` after the MusicBrainz and yt-dlp tags (dedupe, per-namespace caps of TAG-023); `preview.suggested_year` carries the year and fills `year` only when yt-dlp gave none. Status: implemented
- TAG-043 MUST: `POST /lookup/wikipedia` derives the same tags and year from user-edited links (Wikipedia URL to Wikidata id via the `pageprops` API); the UI puts the tags in the Suggested row only. Status: implemented
- TAG-044 MUST: all Wikimedia calls use `AUDIO_MB_USER_AGENT`, a 5 s timeout and in-memory caches by Wikidata id; the `AUDIO_TAG_LOOKUP` switch disables them; any failure gives no suggestions and never breaks `/preview`. Status: implemented
- TAG-045 MUST: for the song's and the artist's `en.wikipedia.org` page (given or suggested link; a Wikidata-only or other-language link is skipped) the server fetches the lead section wikitext (`action=parse&prop=wikitext&section=0&redirects=1`, same User-Agent, 5 s timeout, cached per page) and reads the `genre` (or `genres`) parameter of the first `{{Infobox ...}}`. Any failure, a missing infobox or unbalanced braces gives no genres. Status: implemented
- TAG-046 MUST: the parser is pure and handles `{{hlist}}`, `{{flatlist}}`, `{{plainlist}}`, bulleted lines, `<br>`, comma-separated text and `[[Link|text]]` (display text; `File:` and `Category:` links dropped); it strips `<ref>`, `{{cite}}`, `{{efn}}`, `{{sfn}}`, `{{citation needed}}`, comments, `<small>` and footnote marks, lowercases, collapses spaces, de-duplicates in order and returns at most 12 (`[[Neo soul]]`, `[[R&B]]` give `neo soul`, `r&b`). Status: implemented
- TAG-047 MUST: the song page's infobox genres come first, all kept (up to 12, even beyond the overall cap of 8); the artist page's infobox is a fallback only when the song page gave none; Wikidata genres follow, de-duplicated by normalised name (`contemporary r&b` and `alternative r&b` stay distinct). They apply in `POST /metadata`, `POST /lookup/wikipedia` and `/preview` (the same 12 and 8 caps in all three, TAG-023), and count as a hit for `services.wikipedia.found`. Status: implemented
- TAG-048 MUST: the same single fetch of the song page's lead wikitext also yields the song's album and release year from its first `{{Infobox ...}}`; the artist page never provides them. Album is the `album` parameter (link display text; refs, templates, italics and quotes stripped; the first of several, e.g. `{{hlist|[[A]]|[[B]]}}`); an infobox without `album` (a standalone single) gives no album, and the song's own title is never used. Year is the first year of `released` (`{{Start date|2009|5|11}}`, `{{start date and age}}`, `{{Release date}}`, `11 May 2009`, `May 2009`, `2009`, first of several or of an `{{hlist}}`), ignored outside 1900 to next year. The pure parser returns `{genres, album, year, type, name, artist}`; `type`, `name` and `artist` (cleaned as in TAG-049) never change the app's Artist or Title by themselves. Status: implemented
- TAG-049 MUST: `POST /metadata` returns `suggest: {artist, title}` from the same song-page infobox fetch (the user-given or resolved `wiki_song` link, never the artist page): `artist` and `title` are the infobox `artist` and `name` parameters, cleaned (links to display text; refs, templates, italics and quotes stripped); several artists (`{{hlist|[[A]]|[[B]]}}`, `{{plainlist}}`, comma-separated plain text outside links) are joined with ", ", while "A and B", "A & B" and a comma inside a link (`[[Earth, Wind & Fire]]`) stay exactly as written; a leading lowercase "the " becomes "The " (`[[the Prodigy]]` gives `The Prodigy`); a missing `name` is `null` (the page title is never used). When the infobox, `name` or `artist` is missing both are `null`. It is a hint only: Artist and Title are never auto-filled. Status: implemented

## Counts and filtering

- TAG-030 MUST: `GET /tags` returns `[{tag, count}]` sorted case-insensitively; tags equal case-insensitively are one entry (first spelling shown). Status: implemented
- TAG-031 MUST: the web UI computes the same counts client-side from the loaded library (`store.tagCounts`), not from `/tags`. Status: implemented
- TAG-032 MUST: ~~the Library filter groups chips by key~~ superseded on the web by WEB-011 and LIB-030 (four category chips Tags, Genres, Years, Countries opening a multi-select sheet); the key grouping (Genre, Decade chronological, Country, other keys title-cased, plain tags in "Tags" last; a chip shows the value only plus the count) remains the model for the category split. Status: superseded (web); iOS to follow ios.md
- TAG-033 MUST: ~~filtering is single-select~~ superseded on the web by multi-select (OR within a category, AND across, WEB-011, LIB-030); the match stays exact and case-insensitive on the full tag, and a selected value whose tag no longer exists is dropped. Status: superseded (web)
- TAG-034 MUST: where tag chips are shown (Playback details, tag editor, tag picker) a `key:value` tag shows the key as a highlighted prefix; Library rows no longer show tag chips (LIB-010, LIB-015). Status: implemented
- TAG-036 MUST: `country:` values display as names via `Intl.DisplayNames`; `lang:` tags in stored data are kept untouched but hidden everywhere in the web UI (not shown, filtered, searched or offered; no Language group) (`web/js/tagname.js`; raw value as fallback, raw tag in the tooltip); search matches code and name; editing always uses the raw `key:value` tags. Status: implemented
- TAG-038 MUST: `decade:90s` displays as "the 90s" (raw tag in the tooltip, `web/js/tagname.js`); search matches "90s"; the tag editor previews the derived decade chip as soon as the Year input changes (the server is authoritative on save). Status: implemented
- TAG-037 MUST: tags are edited with the shared tag editor (LIB-055, ADD-004). Status: implemented
- TAG-070 MUST: suggestions from audio identification (API-070) and from Discogs are never applied: they fill the shared tag editor's Suggested row (genre and country chips included, though the editor hides those namespaces elsewhere) and a chip is added only when the user clicks it; picking a suggested country replaces the current one (cap 1). Discogs styles (progressive house, vocal trance) are preferred over its broad genres and over the community-voted MusicBrainz tags; `lang:` suggestions are returned by the API but the web UI keeps `lang:` hidden. Status: implemented
- TAG-035 SHOULD: multi-tag filtering (AND/OR). Status: implemented on the web (OR within a category, AND across categories; WEB-011, LIB-030, LIB-061)
