# API

Code: `server/app/main.py` (app wiring) and one router per area in `server/app/routes/` (`health`, `auth`, `me`, `legacy`, `files`, `catalog`, `genres`, `lookup`, `songs`, `analyze`, `removal`, `backfill`, `legal`; 13 routers); shared state and dependencies in `server/app/deps.py`, request bodies in `schemas.py`. Same origin as the web UI; JSON bodies; errors
are `{"detail": "<message>"}`, or `{"error": <code>, "detail": <message>, ...}` for coded refusals (API-026, API-040..046). Every data route works on the caller's own library only (ADR-0012).

## Auth

- API-001 MUST: every route except `GET /health`, the static UI and the read-only guest allow-list (API-090) requires header `X-API-Token` equal to env `AUDIO_API_TOKEN` (compared with `hmac.compare_digest`) (owner) or an OAuth ID token (API-007). Status: implemented
- API-002 MUST: `GET /files/{id}` and `GET /covers/{id}` also accept `?token=<token>` (the header wins when both are sent), because `<audio>` and `<img>` cannot send headers. Status: implemented
- API-003 MUST: wrong or missing token gives 401 `bad token`; `AUDIO_API_TOKEN` unset gives 503 `AUDIO_API_TOKEN is not set` (the API is closed, never open). Status: implemented
- API-004 MUST: static files at `/` are public, carry no data, and are served with `Cache-Control: no-cache`; API routes are registered first and are never shadowed; for the versioned asset paths `GET /_v/<version>/...` see API-051. Status: implemented
- API-005 MUST: `{id}` path params must match `^[A-Za-z0-9_-]{11}$` (YouTube), `^soundcloud-[0-9]{1,20}$` (SoundCloud) or API-034, else 422 `invalid video id` (blocks path traversal and yt-dlp option injection). Status: implemented
- API-007 MUST: `Authorization: Bearer <ID token>` from Sign in with Apple or Google is accepted on every authenticated route, including `GET /files/{id}` and `GET /covers/{id}`. The server tries Google, then Apple (it never reads unverified claims to choose), checking the RS256 signature against the provider JWKS (cached), `iss`, `aud` (`APPLE_AUDIENCE` / `GOOGLE_CLIENT_ID`, each a comma-separated list; `APPLE_WEB_CLIENT_ID` and `GOOGLE_WEB_CLIENT_ID` count too) and `exp`, and admits any verified `email` (Apple without email: the `sub`) as a user (API-040). ~~Only `ALLOWED_EMAIL` or an Apple `sub` in `ALLOWED_APPLE_SUB`; anyone else 403 `not the owner`.~~ The owner is the user whose email is `OWNER_EMAIL` (alias `ALLOWED_EMAIL`, default `alex.isayenko@gmail.com`); an Apple `sub` listed in `ALLOWED_APPLE_SUB` is mapped to that owner (Apple may hide the email), it no longer restricts who may sign in. Invalid or expired token gives 401 `bad token`; an unverified email 403 `unverified_email`; a new user while `SIGNUP_OPEN=0` 403 `signup_closed`. If `X-API-Token` is also sent it decides. Status: implemented
- API-008 MUST: a valid session cookie `__Host-session` (API-020) authenticates every route that accepts a header token, including `GET /files/{id}` and `GET /covers/{id}`, so no token is needed in a URL; the web UI uses only this cookie (WEB-005). Order: `X-API-Token`, then Bearer ID token, then cookie, then `?token=` (files and covers only). Status: implemented
- API-009 MUST: `GET`, `HEAD` and `OPTIONS` need nothing more; a cookie-authenticated `POST`, `PATCH` or `DELETE` needs header `X-Requested-With: audioplayer` and, when `Origin` is sent, an `Origin` host equal to `Host`, else 403 `missing or foreign CSRF header`. Header-authenticated requests are exempt. Status: implemented
- API-006 SHOULD: use HTTPS and keep logs private, since `?token=` appears in URLs. Status: implemented (via the live Cloudflare Tunnel at https://electrophone.cc; see [non-functional.md](non-functional.md))

## Web session

- API-020 MUST: `POST /auth/session` `{id_token}` verifies the ID token exactly as API-007, then answers 200 `{email, provider}` and sets cookie `__Host-session` (`HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=43200`), a payload `{provider, email, exp}` signed with HMAC-SHA256 (the payload also carries the server-derived `uid`). The key is env `AUDIO_SESSION_SECRET`, else derived from `AUDIO_API_TOKEN`; neither set gives 503 `AUDIO_SESSION_SECRET or AUDIO_API_TOKEN is not set`. Errors: 401 `bad token`, 403 `unverified_email`, 403 `signup_closed`, 403 `no_email` (the account has no email), 403 CSRF (API-009 applies). Status: implemented (seen live: 6 successful `POST /auth/session` in the server journal; provider not recorded)
- API-021 MUST: `POST /auth/logout` deletes the cookie and answers 204 (CSRF header required). Sessions are stateless: a stolen cookie stays valid until it expires or the secret changes. Status: implemented
- API-022 MUST: `GET /auth/config` is public and returns `{google_client_id, apple_client_id, apple_redirect}` from `GOOGLE_WEB_CLIENT_ID`, `APPLE_WEB_CLIENT_ID` and `APPLE_WEB_REDIRECT_URI`; empty string when unset. `apple_redirect` resolves in this order (`hosts.oauth_redirect`): the `OAUTH_REDIRECT_URIS` entry whose host matches the request host, else its first entry; then `APPLE_WEB_REDIRECT_URI`; else `https://<origin>/`, the origin from `PUBLIC_HOSTS` / `CANONICAL_HOST` / `X-Forwarded-Host` (trusted peers only). Client ids are not secrets. Status: implemented
- API-023 MUST: `GET /auth/me` returns `{method:"session"|"bearer"|"token", email, provider, owner}` for the current credentials, else 401. Status: implemented
- API-024 MUST: API responses carry `Cache-Control: no-store`; `/files` and `/covers` carry `private, no-cache`; static files `no-cache`. Status: implemented

- API-010 MUST: `POST /songs` returns 202 immediately (`status` `downloading`, or `queued` when the user or the server is at its download cap) and downloads in the background; the song is written to `library.json` only when the download succeeds. Status: implemented
- API-011 MUST: `POST /songs` accepts any YouTube watch, `youtu.be`, shorts, embed, live or `music.` URL, or a bare 11-char id, and a SoundCloud track link (`soundcloud.com/<artist>/<track>`, private `/s-<secret>`, `on.soundcloud.com/<code>`). Status: implemented
- API-012 MUST: `GET /songs/{id}/status` answers from the in-memory job first, else `done` if the song is in the library, else 404. Status: implemented
- API-013 MUST: job state is in memory; a server restart forgets in-flight jobs and past errors. Status: implemented
- API-014 MUST: a failed job (`status:"error"`, message with yt-dlp noise stripped, max 300 chars) can be retried with a new `POST /songs`. Status: implemented
- API-015 MUST: `PATCH` applies only the keys sent; `title`/`artist`/`album`/`remixer` are trimmed (empty becomes `null`, empty title is 422); `tags` is normalised; `tags: null` is ignored. Status: implemented
- API-016 MUST: `DELETE` removes the record, the cover and the audio file, and drops the job entry. Status: implemented
- API-017 MUST: every write endpoint (`POST /songs` job, PATCH, DELETE, bpm/detect) runs under the single-writer lock and, with the git store, commits `audioplayer: <uid8> add|edit|delete|bpm <id>` (`<uid8>` = first 8 characters of the user id). Status: implemented
- API-025 MUST: song ids are `^[A-Za-z0-9_-]{11}$` (YouTube) or `soundcloud-<numeric track id>` (SoundCloud, always longer than 11 characters, so no collision); `source_of(id)` gives `youtube`/`soundcloud`; `POST /download` stays YouTube-only. Status: implemented
- API-052 MUST: a write that carries a `country:` tag whose value is not an ISO 3166-1 alpha-2 country (after alias mapping, TAG-056) is refused with 422 `{"error":"unknown_country","detail":"Unknown country: <v>","value":"<v>"}` on `POST /songs` and `PATCH /songs/{id}` (nothing is saved); a `country:` value the song already carries (legacy) passes on PATCH. Suggestions never carry unknown countries. Status: implemented
- API-060 MUST: `POST /songs/{id}/audio` fetches audio for a song already in the user's catalog (state `none` to `server`, ADR-0010) from its first `sources` link, as a normal download job (same status endpoint, `GET /songs/{id}/status`, same queue and caps as API-045). It checks, in this order: the hourly counter (`USER_ADDS_PER_HOUR`, the SAME counter as `POST /songs`, API-041: one fetch counts as one add; the owner is exempt), the user's audio bytes (`USER_MAX_BYTES`, owner exempt), the pool (`POOL_MAX_BYTES`); it does not check the song count (the song already exists). On success it sets `file`, fills `duration`, `bpm` and `cover` only when missing and writes `updated_at`; on failure the job ends `error` and the record is untouched, so the call may be repeated. Another user's song answers 404 (API-047). Status: implemented
- API-026 MUST: refusals of `POST /preview` and `POST /songs` for links are JSON `{"error": <code>, "detail": <message>}` with codes `unsupported` (422), `preview_only` (422), `not_found` (404), `private` (403), `failed` (502); clients show `detail`. Status: implemented
- API-018 SHOULD: keep `/search` and `/download` only for the iOS secondary text search (IOS-023); the web UI does not use them. `/download` bypasses the library and tags, so the row download should be replaced by the preview flow. Status: to-confirm
- API-019 MUST: `/health` reports `sync.state` `ok` whenever no git store is configured (owner form: `unpushed` 0, `mode` `"none"`). Status: implemented
- API-030 MUST: `GET /library` and `PATCH` responses add `audio_state`, `sources` and `audio` without removing or renaming any field, so old web and iOS clients keep working. Status: implemented
- API-031 MUST: `GET /catalog` returns the same song objects (metadata only, no audio bytes) plus `revision` (content hash of the catalog, audio state included), `total` and `ids` (every id, so a client can drop deleted songs). `songs` holds all songs, or with `since` those whose `updated_at` (else `added_at`) is `>= since`; clients dedupe by id. An unchanged catalog answers 304 to a matching `If-None-Match`. Status: implemented
- API-032 MUST: `POST /songs` with `audio:false` saves a catalog entry (`file: null`, `sources` from the link, missing fields filled from the link's metadata and cover) without downloading; 409 if the id exists. Status: implemented
- API-033 MUST: `DELETE /songs/{id}/audio` removes only the file; `DELETE /songs/{id}` removes record, cover and file. Commits: `audioplayer: <uid8> delete audio <id>` and `audioplayer: <uid8> delete <id>`. Status: implemented
- API-034 MUST: song ids also accept `spotify-`, `applemusic-` and `shazam-<id>` (metadata-only sources), in every `{id}` path. Status: implemented (ids; adding from these sources is planned)

## Users, quotas and limits (ADR-0012)

- API-040 MUST: every authenticated request resolves to one user: `X-API-Token` and `?token=` are the owner; a Bearer ID token or the session cookie is the user whose `uid` the server computes from the verified identity (`sha256(lowercased email)[:16]`, Apple without email: `sha256(sub)[:16]`). A `uid` sent by the client (path, query, header, body) is never read. The first sign-in creates the profile (`SIGNUP_OPEN=1`, default); with `SIGNUP_OPEN=0` only existing users and the owner get in, others get 403 `{"error":"signup_closed"}`. Status: implemented
- API-041 MUST: before anything is downloaded `POST /songs` (and `POST /download`) checks, in this order: songs (`USER_MAX_SONGS`, queued adds included), adds in the last hour (`USER_ADDS_PER_HOUR`), the user's audio bytes (`USER_MAX_BYTES`, audio adds only), the server pool (`POOL_MAX_BYTES`, audio adds only). The owner skips the per-user checks, not the pool. Status: implemented
- API-042 MUST: 429 `{"error":"hourly_limit","detail":"...","retry_after_minutes":N}` with header `Retry-After: <seconds>`; N is the time until the oldest add of the last hour expires, at least 1. Status: implemented
- API-043 MUST: 403 `{"error":"library_full_songs"}` or `{"error":"library_full_bytes"}`; deleting a song (or only its audio, for bytes) frees the quota at once because bytes are the real file sizes. A metadata-only add (`audio:false`) is not blocked by bytes or the pool. Status: implemented
- API-044 MUST: 503 `{"error":"server_full"}` when the audio under `music_root/users` has reached `POOL_MAX_BYTES`; applies to the owner too. Status: implemented
- API-045 MUST: downloads run under `GLOBAL_MAX_CONCURRENT_DOWNLOADS` (default 2) and `USER_MAX_CONCURRENT_DOWNLOADS` (default 1, owner exempt); a job waiting for a slot has status `queued`, starts in order, and re-checks bytes and pool when it starts (a refusal ends as `status:"error"` with `code`). Status: implemented
- API-046 MUST: `GET /me/usage` counts `songs`, real `bytes`, and `adds_last_hour` (adds accepted in the last 60 min; after a restart relearned from `added_at`). Status: implemented
- API-047 MUST: `GET /files/{id}`, `GET /covers/{id}` and `GET /songs/{id}/status` of another user's id answer 404 as if the song did not exist; the file path is always `<music_root>/users/<own uid>/<name>` and is checked to stay inside it. Status: implemented
- API-114 MUST: `spotify_url` (DATA-072) is accepted by `POST /songs` (`metadata`) and `PATCH /songs/{id}` and returned on every song, in the guest view and in the catalog; `PATCH` also accepts `youtube_url` and `soundcloud_url` (DATA-073) while responses keep the `sources` / `source_url` shape. All additive: a client or record without them is unchanged. Status: implemented
- API-048 MUST: `POST /metadata` merges, concurrently under one 15 s cap, yt-dlp info of each source link (max 5; genre, album, year), the MusicBrainz match of artist+title (genres, artist country, first release year, best matching album title), the `genre` parameter of the song's (else the artist's) English Wikipedia infobox (deterministic parser, TAG-045 to TAG-047; taken first, all kept up to 12) and Wikidata (the user-given `wiki_song`/`wiki_artist` links, plus the guessed links as for `POST /lookup/wikipedia`; genre `P136`, country, year `P577`). Tags are normalised, de-duplicated and capped per namespace (genre 8, country 1; the song's own Wikidata genres come first and are all kept, up to 12, even beyond 8); no `lang:` tag is ever suggested. The song page's infobox (never the artist's) also supplies `album` and the `released` year (TAG-048; a single without an `album` parameter gives none). Precedence: album yt-dlp, the song page's infobox, then MusicBrainz; year Wikidata links, the song page's infobox, Wikidata guess, MusicBrainz, Discogs, never yt-dlp; tags the song's own Wikidata genres (links, else guess), yt-dlp, MusicBrainz, then the remaining links/guess tags (artist genres, country). A failing, unusable or late source is skipped, never an error; empty fields are `null` / `[]`. Spotify is not used. Nothing is stored. The response also returns the guessed `wikipedia_song`, `wikipedia_artist` and `wikipedia_album` page links (else the user-given ones, `null` when none), found as in TAG-040 and TAG-087; the web form puts each into an empty link field and never over a typed one (ADD-050). The response also carries `suggest: {artist:str\|null, title:str\|null}`, a hint taken from the song page's infobox `artist` and `name` (TAG-049; both `null` when either is missing); the app decides when to show it and Artist/Title are never auto-filled, and `services: {youtube, soundcloud, wikipedia, spotify, musicbrainz, discogs}`, each `{found:bool, url:str\|null}`, for the UI's per-service icons only (never merged into the song): `youtube`/`soundcloud` are found when a source link of that service returned an album, year or tags (`url` is that link); `wikipedia` is found when the Wikidata lookup (given links or guess) or the infobox produced tags, an album, a year or a page (`url`: the song's page, else the artist's, else `null`; a bare Wikidata item is `https://www.wikidata.org/wiki/<QID>`); `musicbrainz` is found when the MusicBrainz match of artist+title (a recording) exists, with `url` `https://musicbrainz.org/recording/<mbid>` taken from the match already fetched (no extra request, same cache; no confident match keeps `{found:false, url:null}`); `spotify` is always `{found:false, url:null}` (no lookup yet); `discogs` follows API-173; clients ignore unknown keys, so old builds are unaffected. The `musicbrainz` url is what the clients then save as the song's `musicbrainz_url` (DATA-009); the response itself still stores nothing. Concurrent lookups of one track share one MusicBrainz fetch. Status: implemented
- API-049 MUST: `POST /preview` returns `remixer` (`str|null`, the text of the cut remix or version bracket, ADD-070 and ADD-159) and a `title` already cut of it, and additive `version_year` (`int|null`); `POST /metadata` has no remix field. ## Drafts (ADR-0032)

- API-180 MUST: the draft routes are user routes: `Depends(deps.require_token)` (session, Bearer or owner token), so a guest or anonymous caller gets 401 and the public view (ADR-0018) never lists or reads drafts; each user has their own list (`users/<uid>/drafts.json`, DATA-180); `GET /library`, `/catalog`, `/tags` and every iOS-decoded response are unchanged. `GET /drafts` returns `{drafts: [draft], counts: {total, unfetched}, limit: 500}`, newest paste first. A draft is `{id, text, url, source, title, mainArtists, featuredArtists, withArtists, version, year, duration, thumbnail, state, inLibrary, createdAt}`: `id` `d_<12 hex>`, `text` the typed "Artist - Title" part, `url` the cleaned link or "", `source` `youtube` | `soundcloud` | `link` | null, `version` a song-style version or null, `year` the upload year (a version-year suggestion, DATA-124), `state` `new` | `fetched` | `failed`, `inLibrary` computed on every read (never stored). Status: implemented (built, not deployed)
- API-181 MUST: `POST /drafts {lines: [string]}` (at most 1000 items of at most 100000 characters, else 422) splits every item on newlines, trims, drops empty lines, takes the first 100 lines, skips lines over 300 characters, reads each line with `drafts.line_parts` (the first link anywhere in the line, cleaned with `urlclean.clean_url`; the rest is the text; "Artist - Title [link]" and "link Artist - Title" are both fine) and creates drafts up to 500 per user. The text is parsed with the add paths' helpers (`titleclean.clean`, `titles.split_title` with the leading "Artist - Title" rule and a first-dash fallback, `credit_title.parse` with the `vs` split, the version bracket as `version`); a draft without text takes the credits of its lookup; a text without artists takes the lookup's. A line whose link is already a draft, and a text-only line whose normalised text is already a draft's text, is a duplicate and is not added; a line with a known link and a text for a draft that has none gives that draft the text (`updated`). Response `200 {created: [draft], updated: [draft], counts}` with `counts: {lines, overLineCap, tooLong, duplicates, created, updated, overCap, unfetched, total, rateLimited, retryAfterMinutes, fetchErrors}`. Status: implemented (built, not deployed)
