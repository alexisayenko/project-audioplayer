# iOS app

Code: `ios/Sources/` (SwiftUI, iOS 17, iPhone only). Same API as the web UI;
screen flow matches it (ADR-0007). Status values reflect code read on
2026-10-13; "implemented" means built into the app, not yet proven on a
device unless a line says so.

## Shell and navigation

- IOS-001 MUST: the app has five destinations in a left panel (side drawer, `Drawer.swift`) in the order "Library", "Now playing", "Playlists", "Statistics", "Settings" (Library first as the landing destination; this intentionally differs from the web order) with the web labels (web `#/library`, `#/playback`, `#/playlists`, `#/stats`, `#/settings`) and SF Symbols; there is no bottom tab bar. The drawer opens from a menu (hamburger) button at the leading edge of each root screen header ("Open menu") or a swipe from the left edge on a root screen, is 75% of the screen wide (at most 320pt) over a dimming scrim, and closes by tapping the scrim, swiping left, choosing an item (selection haptic) or Escape; items and the account row activate on touch-down, not on release (VoiceOver activation still works); the active item has the select-tint capsule with select-ink icon and label; an account row at its bottom (person icon with the signed-in email, or "Sign in" when signed out) opens Settings. It is a VoiceOver modal (focus moves in, "Close menu" action, `isSelected` on the active item), items are at least 44pt, text scales to accessibility2, and with Reduce Motion it appears without sliding. Add is not a destination: a + button in the Library header opens the AddSheet (ADR-0009). The queue length is shown on Playback ("Queue (N)"). Status: implemented (verified in the simulator)
- IOS-002 MUST: the mini-player bar is the only panel at the bottom: it shows on every destination except Playback while a song is loaded, opens Playback on tap and is hidden on Playback. Status: implemented
- PLS-102 MUST: Playlists is a placeholder, as on the web: the header "Playlists" and the line "Playlists are coming soon." (`PlaylistsView.swift`). Status: implemented
- STT-100 MUST: Statistics (`StatisticsView.swift`) works on the same song list as Library (the songs in the app's library; signed out, only the songs stored on the phone) and has tabs Songs, Genres and, only when signed in, Listening. Listening reads `GET /stats/listening` (most listened and most skipped, with the listen count) and is never requested signed out; Songs and Genres show an empty state while the list is loading or has no year, BPM or genres. Status: implemented (verified in the simulator)
- IOS-003 MUST: the app runs on iPhone only, portrait only. Status: implemented

- IOS-075 MUST: the Files app shows the app's `Documents` folder (On My iPhone > Electrophone; `UIFileSharingEnabled`, `LSSupportsOpeningDocumentsInPlace`) and only the `audio` folder is visible in it: the files have readable names (IOS-075a). The library index `library.json` and the local covers live in `Application Support`, hidden and backed up; an index left in `Documents` by an older build is migrated once. Status: implemented (not verified on a device)
- IOS-075a MUST: audio files are named "Artist - Title.m4a" (`AudioFiles.swift`): the displayed artist and title, just "Title" without an artist, the title text as it is (a version or remix already in it stays). The name is cleaned: `/ : \ ? * " < > |` and control characters are removed, whitespace runs become one space, dots and spaces are trimmed at both ends, at most 120 characters before the extension; a song without a usable title keeps `<id>.m4a` until it has one. A name already taken by another song (compared ignoring case) gets " (2)", " (3)" and so on; a song keeps its name, including the number, as long as the artist and title still fit it. The id -> file name map is stored in `library.json` (`files`; a missing map means every song uses `<id>.m4a`, so old indexes and files keep working); `Track.fileURL` resolves through it, so playback, deletion, "Remove from iPhone" and the on-the-phone check all follow it, and covers stay keyed by song id. Every writer names the file this way: signed-in downloads, the anonymous add, local adds. At launch, files still named `<id>.m4a` are renamed once, off the main thread, by atomic same-folder moves: idempotent, a collision or move error skips that file, no audio is ever deleted, a song without metadata keeps its id name. Editing the artist or title (or a catalog sync that brings new ones) renames the file and updates the map in one step. A map entry whose file is missing counts as not on the phone; a file in `audio/` without a map entry counts only when it is named `<id>.m4a`. Known limitation: a file renamed by hand in the Files app is no longer found (its song shows as not on the phone and may be downloaded again); the app does not track such renames, and the stray file is left alone. Status: implemented

## Adding songs without an account

Contract: API-207..API-215 (`/anon/*`). Code: `AnonAPI.swift`, `AnonDownloader.swift`, `AnonAddSheet.swift`, `LocalCover.swift`. Status of this block: implemented, builds, not run against a server (the `/anon` routes are not deployed) and not seen on a device.

- IOS-080 MUST: while nobody is signed in the Add sheet (`AnonAddSheet`) takes a pasted YouTube or SoundCloud link or a bare video id (cleaned by `cleanPasted`, "Already in your library" as IOS-062) and a button "Add"; there is no preview form and no search: a line "Sign in to search" with a Sign in button (closes the sheet, opens Settings) stands where Search is. Signed in, the Add sheet is unchanged (IOS-020).
- IOS-081 MUST: the device gets an anonymous token with `POST /anon/session`, kept in the Keychain (`anon-session`) with its expiry and server, renewed a minute before it expires (the old token goes along, so the device id and its limits stay) and once after a 401 `bad_token`. It goes as `X-Anon-Token` and only on `/anon/` paths (`LiveAnonAPI`); `Authorization` and `X-API-Token` are never sent to them.
- IOS-082 MUST: the transfer (`AnonDownloader`): `POST /anon/downloads {url}`; poll `GET /anon/downloads/{id}` (1 s, growing to 4 s, at most 15 minutes, 8 transient failures in a row); when `ready`, `GET .../file` with `Range` from the size of the partial file (`Application Support/anon/<job>.part`, `If-Range` with the saved ETag; a 200 starts over, a 416 restarts; a 409 `not_ready` goes back to waiting) up to `size`, over the "Use mobile data" session (IOS-017); the SHA-256 of the file must equal `sha256` (one fresh re-download, then "The file arrived damaged"); the file moves to `Documents/audio/<id>.m4a`; `GET .../cover` (a 404 is fine) is stored as `Documents/covers-local/<id>.jpg` and referenced as `local-cover:<id>`; the song is added with `localOnly` true and `onServer` false; then `POST .../ack {sha256}` (the computed one; a 404 counts as done; a 422 `hash_mismatch` or `bad_hash` downloads the file once more and replaces the stored one). The progress bar is 80% server work, 20% copy. The song never starts playing by itself.
- IOS-083 MUST: the local song id is the server's `video_id` (`soundcloud-<number>` for SoundCloud, prefixed with `platform-` when it is not already), characters outside `[A-Za-z0-9._-]` replaced by `_`, at most 80, never starting with a dot, so it matches the id regex and equals the server's own id for the same song if the person signs in later.
- IOS-084 MUST: the job id and state are saved in `Application Support/anon/jobs.json`; at launch, when the app becomes active and when the Add sheet opens, jobs that are not running continue (the partial file resumes with Range) while the server's `expires_at` has not passed; an interruption (offline, 5xx, 429, 503, mobile data off) keeps job and partial file and shows a toast; a 404 for a job that is not stored yet (the server keeps jobs in memory and empties staging on restart) deletes the partial file and starts one fresh server job for the same link, once; a final failure (server `failed`, a second 404, a refused link, damaged file, no space) deletes the partial file and the job and shows the message. A stored song whose ack failed keeps only the ack to retry.
- IOS-085 MUST: server error codes read as: `limit_hour` "You have reached the hourly limit for adding songs without an account. Try again later, or sign in."; `limit_ip` "Too many songs were added from this network just now. Try again in a while, or sign in."; `too_long` "This track is too long to add without an account."; `too_big` "This track is too large to add without an account."; `unsupported_url` "Unsupported link. Electrophone takes single YouTube and SoundCloud tracks only."; `disk_low` "The server is short on space right now. Try again later."; `extractor_failed` "The server could not fetch this track. Check the link and try again."; `limit_concurrent`, `not_found`, `private`, `preview_only` and `anon_disabled` have their own lines too (`AnonError.message(forCode:)`); `busy` and `not_configured` have lines too; `Retry-After` of a 429 sets the wait in the `limit_*` and bare 429 lines and paces retries of a running job; a bare 429 "Too many requests. Try again in a minute."; a bare 503 "The server is busy. Try again in a minute.". Refusals at job creation show under the link field; later ones in the sheet and as a toast.
- IOS-086 MUST: after "Add" the sheet shows the fetched title and artist (`meta` arrives with `ready`, so while the copy runs), a progress bar and a status line, and closes by itself when the song is stored; Close leaves the transfer running as a "Downloading NN%" row in Library. Deleting such a song (or "Remove from iPhone" for a local-only one) removes its file and cover. Signing in later keeps these songs as local-only until the catalog lists the same id.

## Per-user storage (ADR-0012)

The server is open to any signed-in user and every user has their own library. Implemented in the client: Google and Apple sign-in for any verified account (IOS-012), the 403 "not allowed" texts (IOS-010, IOS-023, IOS-035). Still open in [task-0016](../tasks/task-0016.md): the `queued` job status and its "Waiting..." display, so an iOS user may still see raw error texts for refused jobs.
- IOS-071 MAY: web-added links (`spotify_url`, edited `sources[]` via `youtube_url` / `soundcloud_url`, DATA-072, DATA-073) are not decoded or edited by the app yet: `Track` ignores `spotify_url` (the Spotify icon stays inert) and the song sheet shows the YouTube and SoundCloud links from `sources[]` as before; unknown fields are ignored on decode, so nothing breaks. Status: planned

## Credits and versions (ADR-0024)

- IOS-072 MUST: the app edits the legacy keys (`title`, `artist`, `remixer`, `year`, `album`) and keeps the structured ones read-only: `ServerSong` and `Track` carry `version {type, name, artists, releaseYear, originalArtists}`, `mainArtists`, `featuredArtists`, `withArtists`, `releaseYear`, `albums`, `genres`, `remix_year`, `rawTitle`, `wikipedia_album` and `discogs_url` as optionals, pinned in `ios_contract.json`. A catalog song that fails to decode is logged (`NSLog`) and skipped, not silently dropped. Status: implemented
- IOS-073 MUST: an Edit sends only the credit keys the person changed (`artist`, `album`, `remixer`, `year`), so the structure (version, `withArtists`, `remix_year`, albums) survives a save; changing the artist text replaces `mainArtists` with its pills and clears `featuredArtists` and `withArtists`; clearing the remixer of a remix removes the version. A version whose type is not remix or other (cover, live, ...) is shown read-only and its Remix text is not sent. Status: implemented
- IOS-074 MAY: the edit form shows the version in words and the featured artists read-only; the decade tag follows the displayed year (the version's `releaseYear` when it has one, else the release year, as the server computes it). Editing featured artists, version type and `withArtists` on the phone is a later iOS task. Status: partly implemented
