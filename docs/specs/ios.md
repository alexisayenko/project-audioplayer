# iOS app

Code: `ios/Sources/` (SwiftUI, iOS 17, iPhone only). Same API as the web UI;
screen flow matches it (ADR-0007). Status values reflect code read on
2026-10-13; "implemented" means built into the app, not yet proven on a
device unless a line says so.

## Accepted playback change: implementation pending

[ADR-0043](../tech/decisions.md#adr-0043-persistent-queue-and-ephemeral-visible-song-audition)
and [PLY-190 onward](playback.md#two-independent-playback-contexts-adr-0043)
define the target: the dock belongs to the continuing queue; Library/Song
Details use a separate visible-song audition with only Play/Pause, allowed to
sound simultaneously with the queue. Audition stops on losing its owning
surface, navigation, lock, background or exit, without changing queue playback.
This is **not implemented** ([task-0085](../tasks/task-0085.md)); the current
behavior below remains the implementation record, including Library cover
Play replacing the queue (IOS-030) and Play all matched (IOS-031). Do not infer
that the existing row/details controls already implement audition. The label
in IOS-032 is now **Decade** (formerly Era); this is a UI label change, not a
different filtering model.

Status: implemented (not verified on a device)
- IOS-075a MUST: audio files are named "Artist - Title.m4a" (`AudioFiles.swift`): the displayed artist and title, just "Title" without an artist, the title text as it is (a version or remix already in it stays). The name is cleaned: `/ : \ ? * " < > |` and control characters are removed, whitespace runs become one space, dots and spaces are trimmed at both ends, at most 120 characters before the extension; a song without a usable title keeps `<id>.m4a` until it has one. A name already taken by another song (compared ignoring case) gets " (2)", " (3)" and so on; a song keeps its name, including the number, as long as the artist and title still fit it. The id -> file name map is stored in `library.json` (`files`; a missing map means every song uses `<id>.m4a`, so old indexes and files keep working); `Track.fileURL` resolves through it, so playback, deletion, "Remove from iPhone" and the on-the-phone check all follow it, and covers stay keyed by song id. Every writer names the file this way: signed-in downloads, the anonymous add, local adds. At launch, files still named `<id>.m4a` are renamed once, off the main thread, by atomic same-folder moves: idempotent, a collision or move error skips that file, no audio is ever deleted, a song without metadata keeps its id name. Editing the artist or title (or a catalog sync that brings new ones) renames the file and updates the map in one step. A map entry whose file is missing counts as not on the phone; a file in `audio/` without a map entry counts only when it is named `<id>.m4a`. Known limitation: a file renamed by hand in the Files app is no longer found (its song shows as not on the phone and may be downloaded again); the app does not track such renames, and the stray file is left alone. Status: implemented

## Playback and offline

- IOS-040 MUST: playback uses local files only, with `AVPlayer`, background audio and lock-screen controls (`MPNowPlayingInfoCenter`, `MPRemoteCommandCenter`). Status: implemented
- IOS-041 MUST: Playback leads with the cover (title and artist on it; no deck, platter, tonearm or LED), a horizontally scrollable row of read-only genre chips when the current song has genres, a seek bar, a transport tray (shuffle, previous, play/pause, next, repeat off/all/one), position and an Up next card (no volume row: the device buttons set the volume; no status line); the full queue (jump, remove, clear) and add-by-tag open from the Queue link and the ⋯ menu, which also holds Song details (opens the song sheet), Share link (SHARE-019: outbound link sheet; opening links in the app is not built), back and forward 5 seconds, and Clear queue. Status: implemented (not verified on a device)
- IOS-035 MUST: catalog sync (CAT-005, CAT-006): on launch, when the app becomes active and on pull-to-refresh the app calls `GET /catalog` with `If-None-Match` (the ETag is stored in `library.json`; 304 changes nothing) and merges it into `Application Support/library.json` (hidden from the Files app; an older `Documents/library.json` is copied there once and deleted), which holds the whole catalog plus the ETag (the old array format is still read). Phone state is never stored: a song is on the phone when `Documents/audio/<id>.m4a` exists. ## Listening history (task-0056 phase 4)

Code: `ios/Sources/PlayRecorder.swift`, `PlayQueue.swift`, hooks in `PlayerService.swift`; shared with the macOS target. Counting follows the web recorder ([PLY-170 to PLY-177](playback.md)); the server side is API-196 and API-197. Status of all four: implemented (built for iOS and macOS, not run on a device, not in a TestFlight build).

- IOS-087 MUST: `PlayRecorder` records plays for songs that exist in the server library. `listened_s` is the sum of forward position steps of at most 1.5 s between the 0.5 s position ticks of the audio that is actually playing (`isPlaying` and `AVPlayer.rate > 0`); a seek (`seek(to:)`, skip, previous) or a pause resets the reference, so seeks, paused time and buffering add nothing, and a backward seek that replays a part adds time again. A pause does not end a play: pause then resume of the same song is one play. A play ends (`ended`, song change) when a different item is attached or the player is emptied (next, previous, jump, queue removal, a new queue, a retry after a failed item), at the end of the item (the last step up to the item duration counts), and at app termination; plays under 5 s are dropped; a repeat of the same song is a separate play; autoplay counts. The play is stamped with the time it began (ISO 8601 UTC with milliseconds). Songs with `localOnly == true` (added without an account, not in the catalog) are never recorded, because the server has no such song id and would ignore the play; they are not backfilled after sign-in. The macOS target records the same way.
- IOS-088 MUST: the open play is saved to `Application Support/plays/open.json` when playback pauses or stops being heard, when the app enters the background and every 30 s of listening; after a kill the saved play (if at least 5 s) is queued at the next launch. A play cut by termination (`willTerminate`) or recovered after a kill makes the next play of the same song within 10 minutes a continuation, `cont: true` (API-196), as the web does after `pagehide`. Entering the background does not end a play (audio continues).
- IOS-089 MUST: finished plays go to `PlayQueue`, stored as JSON with atomic writes in `Application Support/plays/queue.json` (cap 1000, oldest dropped first), so they survive a kill and an offline period. A batch is at most 200 plays; its `batch_key` (UUID) is written to disk with the batch before the request, and a failed batch is sent again with the same key (API-196 appends nothing for a repeated key). Rounding: `listened_s` to 0.1 s.
- IOS-090 MUST: upload is `POST /plays` through `APIClient` (same bearer token or legacy token as every call, no new auth path) when a play is queued, on pause, when the app becomes active, when connectivity returns (`NWPathMonitor`), and on sign-in (a new session or a legacy token). Without credentials nothing is sent and the queue is kept. 2xx removes the batch; 400, 404, 409, 410, 413 and 422 drop it (as the web); a network error, 401, 403, 429 or 5xx keeps it and retries after 30 s, doubling to 15 minutes, and a regained connection or a sign-in retries at once. Failures never reach playback or show UI. After a 2xx the app posts `playsUploaded`; the Library reloads `GET /stats/listening` through `ListeningStore` (Plays numbers) and the open Statistics Listening tab reloads, with no polling. Known limit: plays queued under one account upload under whichever account is signed in when the app flushes.
