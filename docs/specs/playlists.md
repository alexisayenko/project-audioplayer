# Playlists (PLS)

A top-level "Playlists" menu item: named, ordered lists of catalog songs. Decision: ADR-0022 (accepted), amended 2026-10-24 to a flat first slice ([task-0058](../tasks/task-0058.md), phase 1 of 4). Built so far: the server side (deployed 2026-10-24), `playlists.json` with the API of API-229 to API-238 and the text export (PLS-110 to PLS-120), and the web (phase 2, deployed 2026-10-24): the Playlists list and playlist pages, the "Add to playlist..." picker and the queue rename (PLS-121 to PLS-128). Not built: "Save queue as playlist" (PLS-013, phase 3) and the apps (phase 4).

Playlists own the playlist data model. A playlist is not the play queue ([terminology](terminology.md)): a playlist is saved and named, the queue is the transient "what plays next".

Scope of this slice (owner decision, 2026-10-24): **flat only**. Folders, import (YouTube, SoundCloud, Spotify, files), export to M3U8, CSV and JSON, smart playlists, sharing and guest visibility are **deferred** to [task-0034](../tasks/task-0034.md): their rules below keep their text and carry the status "deferred", and the connectors that would create playlists through them ([Connect YouTube](youtube-connect.md) YTC, the Spotify import CAT-015) wait with them.

## Model

- A **playlist** is `{id, name, description, created, updated, songs}`. `songs` is the ordered list of song ids (the song's own library id: a YouTube id, `soundcloud-<n>`, or a `spotify-`, `applemusic-` or `shazam-` id). A playlist references songs by id and never copies a song field, so title, artist and cover edits show up in every playlist and the library quotas (NFR-050, DATA-112) are not affected.
- There is no entry object: no `entryId`, no `addedAt`. A song id appears at most once in one playlist (PLS-113); the same song may be in many playlists.
- No folders, no `parent`, no nesting. The playlists of a user form one flat list, ordered by name (PLS-116).
- The cover is derived by the client from the first song (`first_song_id`) and is never stored. Counts are derived; the total duration is derived by the client from the songs it already has.
- Deferred (task-0034): folders, `source`, smart playlists (`smart`, `rules`), a custom cover, entry objects.

## Flat model (phase 1)

- PLS-110 MUST: a playlist is `{id, name, description, created, updated, songs: [song_id, ...]}` and is stored per user in `users/<uid>/playlists.json` (DATA-199), in the git-synced store beside `library.json` and `drafts.json`, written atomically inside one transaction per change. Playlists are private to their user: owner and other users alike read and write only their own, a guest or anonymous caller gets 401, and the public read-only view (ADR-0018) never shows them. Status: implemented (deployed 2026-10-24)
- PLS-111 MUST: a name is 1 to 120 characters after trimming, without control characters, and unique per user case-insensitively (409 `playlist_name_taken`); the UI suggests "Name (2)" on a clash. A description is optional, at most 1000 characters (422 `bad_description`; a bad name is 422 `bad_name`). Status: implemented (deployed 2026-10-24)
- PLS-112 MUST: the id is server generated and opaque, `pl_` plus 8 random lower-case letters or digits, unique among the user's playlists when made; the client never picks it. Status: implemented (deployed 2026-10-24)
- PLS-113 MUST: a song id appears at most once in a playlist: a second add is ignored and reported as skipped (the web shows the toast "Already in the playlist"); ids that are not in the user's library are ignored the same way. Status: implemented (deployed 2026-10-24); toast implemented (web, deployed 2026-10-24)
- PLS-114 MUST: deleting a song from the library (`DELETE /songs/{id}`) removes its id from every playlist of that user in the same transaction; ids that are not in the library are also dropped lazily on every read (never listed, counted or exported, and not written until the next change). Status: implemented (deployed 2026-10-24)
- PLS-115 MUST: caps for non-owners (the owner is exempt as elsewhere): 200 playlists per user (422 `too_many_playlists`) and 2000 songs per playlist (422 `too_many_songs`). Playlists do not count toward the library quotas (DATA-112). Status: implemented (deployed 2026-10-24)
- PLS-116 MUST: the playlists are listed by name, A to Z, case-insensitively, with no manual order; the order of the songs inside a playlist is the user's own and is kept (no automatic sort). The cover is the first song's, derived by the client from `first_song_id`. Status: implemented (deployed 2026-10-24) for the server order; cover implemented (web, deployed 2026-10-24)
- PLS-117 MUST: reordering sends the final order once (`PUT /playlists/{id}/order`): the list must be exactly a permutation of the current songs, else 422 `bad_order`; one write for the whole new order, so a lost update is last-writer-wins and never corrupts the list. Status: implemented (deployed 2026-10-24)
- PLS-118 MUST: the text export of a playlist (`GET /playlists/{id}/export`) is one line per song in the playlist's order, `Artists - Title (Version) - m:ss`: `Artists` are the song's main artists joined with `, ` (a song without main artists falls back to the credited artist text of the library); `Title` as stored; ` (Version)` only when the song has a version, with the library's version text (`credits.version_text`: the version name as stored, e.g. `Liquid Soul rmx`, else its artists, else the capitalised type); ` - ` and the length as `m:ss`, or `h:mm:ss` from one hour (whole seconds, rounded down), and when the duration is unknown the whole ` - length` part is omitted. Whitespace inside a line collapses to single spaces. Lines end with `\n`; there is no header and no blank line other than the final newline; songs no longer in the library are skipped. An empty playlist exports an empty file. Status: implemented (deployed 2026-10-24)
- PLS-119 MUST: the export answers `text/plain; charset=utf-8` with `Content-Disposition: attachment` and `filename*=UTF-8''<name>.txt` (with an ASCII `filename=` fallback, as for audio downloads): the playlist name with path separators, control characters and `: * ? " < > |` replaced, whitespace collapsed, trimmed of spaces and dots and cut to 100 characters; an empty result is `playlist`. Status: implemented (deployed 2026-10-24)
- PLS-120 MUST: the API of the flat model is API-229 to API-238 (`GET/POST /playlists`, `GET/PATCH/DELETE /playlists/{id}`, `POST /playlists/{id}/songs`, `DELETE /playlists/{id}/songs/{song_id}`, `PUT /playlists/{id}/order`, `GET /playlists/{id}/export`). Status: implemented (deployed 2026-10-24)

## API

The API of the flat model is API-229 to API-238 in [api.md](api.md); the rules below describe the tree API of task-0034 and are kept as the deferred design.

- PLS-070 MUST: `GET /playlists` answers the whole tree `{folders, playlists}` without entries (id, name, parent_id, position, count, duration, cover, source, smart; a smart playlist's count and duration are evaluated live); `POST /playlists` creates a playlist, smart playlist or folder (`{name, parent_id, kind: playlist|folder, smart?: bool, rules?: {...}}`; `smart` requires valid `rules`, PLS-092); `GET /playlists/{id}` answers one playlist with entries; `PATCH /playlists/{id}` renames, edits description, cover, `rules` (smart only), `parent_id`, `position`; `DELETE /playlists/{id}` (a folder takes `?contents=move|delete`, default 409 `folder_not_empty`). Status: replaced by API-229 to API-238 for the flat model; folders, smart playlists, `cover`, `position` and `parent_id` deferred (task-0034)
- PLS-071 MUST: `POST /playlists/{id}/songs` `{song_ids:[...], position?}` adds, `DELETE /playlists/{id}/songs` `{entry_ids|song_ids}` removes, `PUT /playlists/{id}/songs/order` `{song_ids:[...]}` reorders (the list must be a permutation of the current entries, else 422); each answers the updated playlist header. Status: replaced by API-235 and API-236 (song ids, no entry ids; `DELETE /playlists/{id}/songs/{song_id}`, `PUT /playlists/{id}/order`)
- PLS-072 MUST: `POST /playlists/import` `{url, parent_id?, include_long?}` (202 `{job_id}`; `GET /playlists/import/{job_id}`) and `POST /playlists/import/file` (multipart) import; `POST /playlists/{id}/refresh` refreshes (PLS-040); `GET /playlists/{id}/export?format=` exports. Status: deferred (task-0034); the flat slice has only `GET /playlists/{id}/export`, a text file (API-237)
- PLS-073 MUST: every write goes to the signed-in user's own store (ADR-0012); a guest has `GET` only (a smart playlist evaluates against the owner's library); a write by a guest is 401. Writes use the existing git-synced write path (STO) and its revision conflict handling; reordering sends the full order so a lost update is last-writer-wins and never corrupts the list. Status: implemented for the flat model (deployed 2026-10-24) as PLS-110 and PLS-117, API-229; guest `GET` of the owner's playlists and smart-playlist evaluation deferred (task-0034)

## Smart playlists (deferred to task-0034, fully specified)

- PLS-091 MUST: a smart playlist is a playlist with `smart: true` and `rules` (a saved set of Library filter rules); it is created by "New smart playlist" or by "Save as smart playlist" on the Library filter bar (the current filters and sort become the rules). It lives in folders, shows in the tree with a distinct icon, and counts toward `USER_MAX_PLAYLISTS` (PLS-016). Status: deferred (task-0034)
- PLS-092 MUST: `rules` is `{match: "all"|"any", conditions: [...], sort: {by, dir}, limit?: int}`. A condition is `{field, op, value}`; fields and ops: `genre`, `tag`, `country`, `language` (`is`, `is_not`, `any_of`; `value` is a tag value or list; lower-case keys as in TAG, `lang:` included), `year` and `decade` (`is`, `between`, `before`, `after`), `bpm` (`between`, `before` meaning below, `after` meaning above; BPM range), `added` (`since` with an ISO date or a relative `{days: N}`), `has_audio` (`is` true|false: server audio present), `text` (`contains`, matches title, artist, album and tags like Library search), `not_set` (`field` one of `genre`, `year`, `country`, `language`, `bpm`: the system "not set" entries of LIB-132). Unknown fields or ops answer 422. Status: deferred (task-0034)
- PLS-093 MUST: `sort.by` is one of `title`, `artist`, `year`, `bpm`, `added`, `duration`, `random`; default `added` descending; `limit` (1 to 5000) keeps the first N after sorting (a "top 50 newest" list). Status: deferred (task-0034)
- PLS-094 MUST: a smart playlist is evaluated live on every open, play and export, against the library visible to the viewer (the owner's for guests); it needs no refresh and updates itself when songs are added, edited or removed; the header count and duration are computed from the result. Status: deferred (task-0034)
- PLS-095 MUST: a smart playlist cannot be hand-ordered and songs cannot be added to it or removed from it by hand: "Add to playlist..." pickers list only normal playlists, entry reorder and "Remove from playlist" are absent, and the API answers 409 `playlist_is_smart` for `POST/DELETE/PUT /playlists/{id}/songs`. It can be renamed, moved, deleted, its rules edited (`PATCH` with `rules`) and its cover and description set. Status: deferred (task-0034)
- PLS-096 MUST: a smart playlist can be played, shuffled, added to the queue and exported like a normal one (PLS-012); playing takes a snapshot of the result at that moment, so later library changes do not alter the running queue. Status: deferred (task-0034)
- PLS-097 MUST: export of a smart playlist evaluates the rules at that moment: M3U8 and CSV contain the resulting songs (PLS-052, PLS-053); JSON contains the resulting `entries` and also `"smart": true` and `"rules"`, and importing that JSON recreates a smart playlist with the same rules (a "Import as snapshot" choice makes a normal playlist from the entries instead). Status: deferred (task-0034)
- PLS-098 MUST: "Convert to playlist" (menu item, confirm) freezes the current result into a normal playlist in the same folder, in the current sort order; the smart playlist is kept unless the user ticks "Replace the smart playlist". `POST /playlists/{id}/convert` `{replace?: bool}` answers the new playlist. Status: deferred (task-0034)
- PLS-099 SHOULD: a rule editor shows the conditions as the Library filter chips (WEB-011) with a live preview count and the first rows; a rule that matches nothing shows "No songs match these rules". Status: deferred (task-0034)
