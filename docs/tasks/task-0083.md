# Artist and Release entities

Alex first said "Album"; C2 decided the umbrella entity is called Release (2026-10-21).

Analysis first: no code until Alex approves. Decision record: [ADR-0039](../tech/decisions.md) (proposed). Phase 5 (iOS) needs Alex's permission to edit `ios/`.

## Motivation

- "View in Library" by artist or title, by id.
- Aliases (Тимур Муцураев / Timur Mutsurayev).
- Release-level data: cover, year, type, full tracklist.
- A "complete releases" view: the release knows its total tracks and which ones you have.
- Compilations (release artist "Various Artists").
- Importing a YouTube playlist or a time-coded video ([task-0038](task-0038.md) phase 1, playlists [task-0058](task-0058.md) and [task-0059](task-0059.md)) creates or links the release and track numbers automatically, so no playlist is re-created by hand. Playlists stay a separate user-made ordered list.

## Difference from genre

Genres are a shared curated vocabulary. Artists and releases are open-ended, come from the user's imports, and identity is ambiguous (Alice DJ versus Alice Deejay; "Greatest Hits" is many albums).

## Decision (Alex, 2026-10-21): curated matching

- Matching and merging songs to entities is done by Alex: no automatic fuzzy matching, no silent merging.
- Allowed automation: create one entity per exact name after normalising case, whitespace and punctuation.
- Everything fuzzy (alias candidates, near-duplicate names, the same album title with different artists) is only suggested in a review queue or merge tool.
- A merge happens only on his explicit approval and is reversible (undo, backup). Duplicates stay separate until he merges them.

## Proposed model (to analyse)

- Artist {id, name, aliases[], country?, external ids (MusicBrainz, Discogs)}.
- Release {id, title, release_artist (artist id or the reserved "Various Artists"), year, type (album, EP, single, compilation, live, DJ mix, soundtrack; extend only with Alex's approval), cover, tracks_total, optional tracklist [{no, title}], external ids}.
- Song keeps its name text fields and gains optional ids: artist_ids with roles from the credits model ([ADR-0024](../tech/decisions.md), ADR-0025, [task-0043](task-0043.md), [task-0048](task-0048.md)), release_id, track_no. The existing `album` text field stays for compatibility; it maps to the Release title. Offline playback and the iOS app keep working unchanged (playback and offline reliability beat features).
- IDs stable. Entities live in a shared catalogue in the owner/server data area (`artists.json`, `releases.json`, git-synced, not per-user storage, not in quotas), changeable only by the owner (A decided). Umbrella entity name: Release (C2 decided).

## Migration

Idempotent and backed up like the other startup migrations (`migrate_renames`, `migrate_version_norm`): create entities by exact normalised names only; fill release_id and artist ids; never merge fuzzy matches; produce the review queue.

## UI sketch

- Library Releases view: group by release, badge "12/12" complete or "7/12", filter "Complete only", "Play release" in track order.
- The UI says "Album" for type album, "Compilation" for compilations, etc.; "Release" is the generic name. Open UI detail (not decided): title the Library view "Releases" with a type filter.
- Artist page; merge tool and review queue; "View in Library" by id.

## Open questions

A. DECIDED (Alex, 2026-10-21): one shared catalogue, only the owner can change it.
- One set of artist and release entities for everybody, like the genre vocabulary.
- Only Alex creates, edits, merges and deletes entities; the merge and curation tools are owner-only (matches curated matching above).
- The catalogue lives in the owner/server data area, synced through git; it is not per-user storage and not counted in user quotas.
- Other signed-in users get read-only use: their songs may link to catalogue entities, and they cannot edit it.
- Users' own songs keep their name text and optional ids, so offline playback is unaffected.
- Where no entity exists, a non-owner sees the text only (no link, no artist page).
- How users could suggest additions later: open, not decided.

B. DECIDED (Alex, 2026-10-21): option 1. Every credited person (main, featured, remixer, producer, composer, etc.) gets an artist entity id; the role stays on the song's credit entry (credits link artist_id + role; consistent with ADR-0024/0025 and task-0048).
Question and options as asked:
Credit roles are the part a person plays on a song: main artist, featured artist (feat.), remixer ("Netsky Remix"), producer, composer, "vs" or "with", original artist for covers (ADR-0024, ADR-0025, task-0048). Example: "Dua Lipa & Elton John - Cold Heart (PNAU Remix)" has two main artists and one remixer (PNAU).
1. Every credited person (also featured artists and remixers) becomes an artist id, the role stays on the song
2. Main artists only get ids first
3. Decide with task-0048

C. DECIDED (Alex, 2026-10-21): option 1, compilations use one reserved "Various Artists" entity as release artist.

C2. DECIDED (Alex, 2026-10-21): option 1, the umbrella entity is called Release (the common industry term, as in MusicBrainz and Discogs) with a `type`: album, EP, single, compilation, live, DJ mix, soundtrack (extend only with Alex's approval).
- The UI says "Album" for type album, "Compilation" for compilations, etc.; "Release" is the generic name. Library view title "Releases" with a type filter: open UI detail.
- The song's existing `album` text field stays for compatibility and maps to the Release title.
Findings behind the decision:
- MusicBrainz: "Release Group" (an album, EP, single or compilation as an abstract work) and "Release" (a specific edition). Primary types: Album, Single, EP, Broadcast, Other. Secondary types: Compilation, Soundtrack, Live, Remix, DJ-mix, Mixtape/Street, etc.
- Discogs: "Master release" (abstract) and "Release"; formats include Compilation.
- Spotify and Apple Music: "Album", "Single", "EP", "Compilation".
- "Various Artists" (VA) is the standard album artist for compilations; MusicBrainz has a special Various Artists entity.
1. Entity "Release" with a type (album, EP, single, compilation, live, DJ mix, soundtrack); the UI label "Album" for type album
2. Entity "Album" with a Compilation type
3. Entity "Collection"

D. DECIDED (Alex, 2026-10-21): cover fallback chain, most specific wins.
- Order, weakest to strongest: Electrophone default song cover image < artist image < album image < song image < version image.
- Every level is optional; a song shows the most specific cover that exists.
- New concepts: artist image (a picture of the artist; needs a source: upload, URL, or Wikipedia and Discogs suggestions as in the cover dialog) and version image (a version such as a remix may have its own cover).
- Relation to [task-0054](task-0054.md): the song cover and `cover_source` stay as they are (the "song image" level); the default placeholder is the bottom of the chain. Album image uses the same sources.

E. DECIDED (Alex, 2026-10-21): option 2, build the entities after task-0038 phase 1 and playlists 0058/0059.
- The migration back-fills albums and artists for songs imported before.
- Importers store album name, track numbers and tracks_total on the songs from day one, so the back-fill has the data.
