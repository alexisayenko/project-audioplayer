# Complete albums: browse and download full albums

> Alex (2026-10-25): "implement complete albums / full albums, so I can 1) easily browse full albums, 2) easily download full albums". Addendum: "create a task; this also introduces a new entity of Album".

Status 2026-10-26: in progress. All questions are answered (owner, 2026-10-26: "all recommended", see DECISIONS below). Built on the server and the web: the Library menu, the Albums list and album page, Add album (a five-step wizard since 2026-10-27, for a YouTube playlist or a time-coded video; the Discogs-address mode was removed from the web), manual link and unlink, covers, total length (see Phases for what is built and what remains); the iOS Albums view, album screen and Download album are built in source (2026-10-26, see phases 4 and 5; not run on a device); MusicBrainz, the `type` and the completeness status are not built. Decision record: [ADR-0050](../tech/decisions.md) (accepted). Prior art that this task narrows and replaces: [task-0083](task-0083.md) (superseded by this task) and ADR-0039 (narrowed). Phases that edit `ios/` need Alex's permission, as in task-0083.

## Earlier decisions (Alex, 2026-10-26)

1. Library navigation is a menu with the sub-items Songs, Albums and Drafts, modelled on the Help menu with sub-items (`web/js/nav-help.js`). Drafts leaves the in-page switch "Songs | Drafts N" and lives in this menu. Songs is the current song-oriented Library, unchanged. Artists waits (phase 7).
2. Albums are explicit objects, no longer derived from songs. The Albums view has an "Add album" button that takes a URL: a Discogs release (e.g. `https://www.discogs.com/release/545650-Derango-Tumult`), a MusicBrainz release, or a YouTube playlist.
3. Discogs and MusicBrainz: the album is created with its tracks stored as title and length only (metadata, no audio). The user then links songs from the library to the album's tracks by hand; there are no automatic matching rules; a link can be removed. Discogs needs `DISCOGS_TOKEN`; MusicBrainz is keyless.
4. YouTube playlist: a preview of the tracks comes first; after the user confirms, the album is created, each video is added as a library song and its audio is fetched, within the existing quotas (20 server fetches an hour; pause and resume on `hourly_limit`).

## Goal

1. Browse: an Albums view in the Library (a grid of covers), an album page with the track list in track order, and per album a status: complete, "partial N of M", or the list of missing tracks.
2. Download: one action that gets every track of an album onto the iPhone, with progress and quota awareness, and a way to add the tracks that are missing.

Key principle check ([CLAUDE.md](../../CLAUDE.md)): this makes downloading and keeping a whole album more dependable and changes nothing about offline playback; songs keep their own text fields and play without any album data.

## What exists today (read from `origin/main`, 2026-10-25)

- Song model: only text. `album` is a legacy derived string (the first album, [data-model.md](../specs/data-model.md) DATA-149), the stored form is `albums[]` (a list of titles, `albums[0]` is the original album, DATA-144, DATA-156, ADR-0025). There is NO track number, disc number, album artist, tracks total, album id or album cover anywhere in `server/`, `web/js/` or `ios/Sources/` (a search for `track_no`, `trackNo`, `track_number`, `tracks_total`, `album_artist`, `disc` finds nothing).
- Album text is shown in the song card (`web/js/song-card.js`, "Album"/"Albums" line, LIB-142, LIB-187), searched by the Library search (LIB-020, LIB-141; iOS `LibraryMatching.swift`), edited in the shared song form (iOS `SongFormView.swift`, `SongFormState.swift`; web `song-form.js`) and sent to the lock screen (`PlayerService.swift`, `MPMediaItemPropertyAlbumTitle`). There is no Albums view, no album grouping, no album filter facet (Library facets are Tags, Genres, Era, Countries, IOS-032), and no album entity or file.
- Statistics and the Genres map group by genre, artist and decade, never by album ([stats.md](../specs/stats.md), [genres.md](../specs/genres.md)).
- Where album text comes from today: yt-dlp (`server/app/metadata.py` `merge`: source `album`, then the Wikipedia infobox, then MusicBrainz `genre_lookup._album`); "Identify from audio" (`server/app/identify.py`) returns genres, countries, year and links, not album or track data. MusicBrainz is keyless (`server/app/genre_lookup.py`; it already reads the release-group id and its url relations but does not store or return them). Discogs needs `DISCOGS_TOKEN` (`server/app/discogs_lookup.py`; the release `tracklist` is read only to check that a title is on the release, `_has_track`, never returned). AcoustID needs `ACOUSTID_API_KEY` and `fpcalc`. The docs do not say whether the two keys are set on the live server ([deploy.md](../tech/deploy.md#identification-keys) lists them as optional); the identify availability flags (`identify.py`) and the song Edit dialog show it.
- Covers are per song (`covers/<id>.jpg`, `cover_source`, task-0054). Task-0083 decision D already puts an "album image" level into the cover fallback chain (song cover over album image over artist image over the default).
- Importing: a YouTube playlist link in the Add dialog opens an import table (ADD-150 to ADD-159) and, since task-0059, creates or extends a saved playlist that keeps `source {type: "youtube", id, url, positions}` (PLS-135, PLS-136, PLS-138). The positions are the playlist order, so an album uploaded as a playlist already carries track order. A single-song Add refuses albums, sets and playlists (ADD-061). Time-coded videos (a full album in one video) are task-0038 phase 1, not built. Drafts (ADR-0032) hold pasted "Artist - Title" lines per user, outside the quotas.
- Download: the web is catalog-only; it plays audio already on the server and, with "Auto-download songs" on, asks the server to fetch a song's audio (`POST /songs/{id}/audio`, PLY-110, ADR-0010 amendment). Only iOS copies audio to the phone: `ServerLink.getAudio` (server fetch, then copy), `ServerLink.download`, and `downloadAllMissing` ("Download all to iPhone" in Settings: `BulkDownload {total, done, failed, running, cancelled, stopReason}`, two at a time, cancel, resumable, stops on `hourly_limit`).
- Quotas (ADR-0012, owner exempt): `USER_MAX_SONGS=500`, `USER_MAX_BYTES=5GB`, `USER_ADDS_PER_HOUR=20` (one server audio fetch is one add), `USER_MAX_CONCURRENT_DOWNLOADS=1`; errors `hourly_limit` (429), `library_full_songs`, `library_full_bytes`. A metadata-only `POST /songs` does not count against the hourly adds.
- Missing-track audio has no match flow yet: Get audio with a YouTube match and confirm (CAT-021 to CAT-025) is [task-0008](task-0008.md), to do.
- Data sync: each user's `library.json`, `drafts.json`, `playlists.json`, `genre_layout.json` live under `audioplayer/users/<uid>/` in the git-synced data repo; the server is the only writer of owned paths and a hand push to those paths makes the sync report "data diverged" ([ADR-0026 to ADR-0028](../tech/decisions.md), [storage-and-sync.md](../specs/storage-and-sync.md)).
- Precedent against a second entity: ADR-0025 gave artists a table, ADR-0031 removed it again (task-0049) because every fact now sat two hops from the song, needed endpoints, sync rules and a migration that lost data; Alex: "I don't want an RDBMS with dozens of tables/entities".

## Requirements

### A. Browse

- A1. Library menu: the Library entry becomes a menu with the sub-items Songs, Albums, Drafts (with the Drafts count), built like the Help menu with sub-items, on the web and on iOS. The in-page switch "Songs | Drafts N" (LIB-159) is removed; Songs and Drafts behave as before (saved sort and filters, the Drafts count). Artists is a later item (A8, phase 7). Signed-in users and the owner; guests have no library view (ADR-0041).
- A2. Albums view: a cover grid, one card per album with the cover, title, album artist, year and the completeness badge (A5), an "Add album" button (B5) and an empty state that points to it. Release-type chips above the grid (All, Albums, EPs, Singles, Compilations, Live; others under "More" only when some exist). Sort: Title, Artist, Year, Recently added, Completeness; search over album title, album artist and track titles; filters: status (complete, partial) and "On phone" (all linked tracks downloaded). The cover is the source's cover when it gives one, else the first linked song's cover (an album image from Cover Art Archive is phase 6).
- A3. Album page (`#/library/albums/<id>` on the web; a pushed screen on iOS): back link, cover, title, album artist, year, type, "N tracks, H:MM", status, actions (Play album in track order, Add to queue, Shuffle, Download album on iOS, Delete album). The track list is in the stored order, with "Disc" headings when the source has several discs. A linked track shows as a normal Library row (play, queue, playlist, audio state) with "Unlink"; an unlinked track shows a muted row with its number, title, length and the buttons "Link song" (pick from the library, searchable) and "Find" (B5).
- A5. Status: "Complete" when every track is linked to a library song; "Partial N of M" otherwise, with the unlinked tracks listed; plus a separate line for audio, "On phone N of M" (question JA). Deleting a linked song from the library unlinks its track.
- A6. A song can be linked to tracks of several albums (a single, the album, a compilation); a track has at most one song.
- A7. Albums are server data of a signed-in user. Signed out on iOS the Albums item shows only a sign-in prompt; offline playback never depends on albums (a downloaded song plays as before).
- A8. Artists view (later, phase 7): a list of artists DERIVED from the song credits (ADR-0024: main artists, featured artists and version artists such as remixers, each with a role count), one row per artist with a count of songs and albums (albums by matching album-artist text), sorted by name or by song count, with a search box. An artist opens to a page with their songs (as Library rows) and their albums (as album cards, A2). Nothing is stored: computed from `library.json` and `albums.json` on read and cached in memory by version; there is no Artist table, no `artists.json` and no artist id beyond a derived slug of the normalised name (the table removed in data model v3, ADR-0031 and task-0049, is not reintroduced). Two spellings of one person stay two artists until the user edits the songs; "View in Library" by artist (LIB-210) keeps working as a search.

### B. Download and add

- B1. "Download album" (iOS): for every linked track in album order that is not yet on the phone: if its audio state is `none`, fetch it to the server (`getAudio`), then copy it to the phone (`download`). It reuses the bulk machinery of `downloadAllMissing` (concurrency, cancel, resume, `stopReason`) with the linked tracks as the queue; unlinked tracks are skipped and counted ("9 of 12 tracks are linked"); tracks already on the phone are skipped; it is safe to run again.
- B2. Before the first transfer the sheet shows the cost: "12 tracks, 3 on the phone, 9 to fetch, about 85 MB; 20 server fetches left this hour" (`GET /me/usage`, track durations and the average bytes per second of the user's songs). If the plan exceeds the hourly adds it runs what the quota allows, shows "Paused: hourly limit, resumes in N min" and continues on its own while the app is open or on the next tap; it never exceeds the quotas and never queues forever silently. `library_full_songs` and `library_full_bytes` are checked up front and block the action with the real reason.
- B3. Progress: "5 of 12", per-track state in the album page (waiting, fetching, downloading %, on phone, failed with a retry), a cancel button, a result line ("11 of 12 on the phone, 1 failed").
- B4. Web: "Download" to the phone does not exist. The web album page plays audio already on the server and, only when "Auto-download songs" is on (PLY-110), has "Get audio on server" for the linked tracks (the per-song `POST /songs/{id}/audio`, one add each, one at a time, paused on `hourly_limit`); otherwise it offers Open on YouTube/SoundCloud per row (question JC).
- B5. Add album (button in the Albums view, web and iOS; one URL field). Amended 2026-10-27: the web takes only a YouTube playlist or a time-coded video, through a five-step wizard (item 1 below is no longer offered on the web; see "Add album wizard"). The URL is recognised as:
  1. A Discogs release (`discogs.com/release/<id>[-slug]`; needs `DISCOGS_TOKEN`, otherwise a clear "Discogs is not configured" error) or a MusicBrainz release (`musicbrainz.org/release/<mbid>`, keyless). A preview (title, album artist, year, tracks with lengths) is shown, then Add creates the album with its tracks as title and length only. No songs are created and no audio is fetched; the user links songs by hand (A3). The same release added twice is refused ("already in your albums").
  2. A YouTube playlist. The preview lists the videos (title, length) first; after Confirm the album is created, each video is added as a library song (the existing playlist import, ADD-150 to ADD-159, creates the songs; each track is linked to its song) and the audio of each is fetched within the quotas. The client paces the fetches (the per-song `POST /songs/{id}/audio`, one at a time), pauses on `hourly_limit`, shows "Paused: hourly limit, resumes in N min", and continues on its own while the page or app is open or on "Fetch remaining audio". The 500-song and 5 GB limits are checked on the preview and block the confirm with the real reason; videos already in the library as songs are linked, not added twice.
  3. "Find" on an unlinked track (any album): a YouTube search for "album artist - title" with the track length as a hint, candidates to pick (the match flow of task-0008, CAT-021 to CAT-025); on confirm the song is added and linked. Never added silently.
- B6. Undo: Unlink on a track; Delete album removes the album and its links, never the songs.

### C. Data (summary; the full proposal is in the next section and ADR-0050)

- C1. An album is an explicit object created by Add album and stored in the user's `albums.json`; its id is random (`alb_` plus 8 hex), not derived.
- C2. The track list is read once from the source at creation (Discogs `tracklist`, MusicBrainz release recordings, or the playlist items) and stored as `tracks[{title, durationS, songId|null}]`; there is no refresh and no re-link in the first slice.
- C3. A track is linked to a song only by the user (or by the YouTube playlist import that creates both); there is no automatic matching, no title or artist rule and no version parsing.
- C4. Edge cases: compilations take the album artist text of the source ("Various Artists" as Discogs and MusicBrainz give it) and each track may carry its own artist; multi-disc releases keep the source order and an optional `disc` number per track for "Disc 2" headings; different editions (deluxe, remaster) are different albums, each added from its own URL; one album uploaded as a single long video is task-0038, not here.

## Album entity and data model

Albums are explicit objects with an id, a page, a status and a track list, stored in one light per-user file. The song stays the source of truth for every fact about a song; the album stores only its own metadata and links to songs. This is the answer to the ADR-0025 / ADR-0031 precedent: no Artist table, no album facts copied onto songs, no song field added.

### Fields

Album (the stored record in `albums.json`):

| Field | Meaning |
| --- | --- |
| `id` | `alb_` plus 8 random hex |
| `title`, `albumArtists[]` | from the source (names only; "Various Artists" for compilations) |
| `releaseYear` | from the source, optional |
| `type` | `album`, `EP`, `single`, `compilation`, `live`, `soundtrack`, `DJ mix` where the source says (Discogs format, MusicBrainz primary type), else `album` |
| `coverUrl` | the source's cover URL when given, optional (fetching it is phase 6) |
| `source` | `{type: discogs, musicbrainz or youtube; id; url}`; also the duplicate check |
| `tracks[]` | `{title, durationS, songId or null}` in album order, with optional `disc` and `artist` |
| `createdAt` | ISO time |

Derived at read time: `have`, `total`, `status` (`complete` or `partial`), `onPhoneHint`, each track's `audio_state` (from the linked song), the cover fallback. Song gains no field: no `trackNo`, `discNo`, `albumArtist` or `albumId`; the link itself touches nothing on the song, but creating or linking a song may copy the album's title, year, vocabulary genres and artist into EMPTY existing text fields of that song (2026-10-27, see "Add album review and track fields").

### Where it lives

- A sparse per-user file `users/<uid>/albums.json` beside `library.json` and `drafts.json` (git-synced like them, atomic write inside `deps.tx`, tolerant reader: a missing, unreadable or malformed file or entry reads as empty). It does not count toward the song or byte quotas (a few KB per album). It is the only copy of the albums and the links, so it is backed up like `library.json`; re-adding from the URL restores the tracks, not the links.
- Not a shared owner-curated catalogue (ADR-0039 option): open signup (ADR-0012) means every user has own songs; a shared catalogue makes the owner the editor of everyone's albums. A server-side, non-git cache of Discogs and MusicBrainz responses (memory or a cache file outside the tracked tree) keeps repeat previews cheap and polite to the services.
- A song deleted from the library sets `songId` to `null` on every track that pointed to it, in the same transaction.

### Data model version and migration

- No schema bump and no song migration: `albums.json` is a new file, absent means no albums; `credits_schema` stays 3 (ADR-0031); `ios_contract.json` changes only when the iOS phase adds the album endpoints.

### Sync and the "data diverged" pitfall

- `albums.json` is an owned path (`audioplayer/users/<uid>/`, `GIT_SYNC_OWNED_PREFIXES`, ADR-0028): only the server writes it; the sync's loader check lists it with `drafts.json` and `genre_layout.json` (valid JSON, an object with `albums`).
- Nothing in this feature may be done by pushing files into the data repo by hand: a push to `audioplayer/users/<uid>/` while the server has unpushed commits makes the sync report "data diverged" and needs a manual rebase ([ADR-0027](../tech/decisions.md), the data-repo note in the project memory). Changes go through the API only.
- Concurrency: create, link, unlink and delete run under `deps.tx` like every library write; the network fetch (Discogs, MusicBrainz, YouTube) runs outside the lock and its result is written in one short transaction.

### API (planned only, API-241 to API-247)

- `GET /albums`: `[{id, title, albumArtists, releaseYear, type, coverUrl, have, total, status, onPhoneHint}]` (computed from `albums.json` and the library in memory, no external call).
- `GET /albums/{id}`: the album with `tracks[]` in order, each with `songId` or `null` and `audio_state`.
- `POST /albums/preview` with `{url}`: recognises the source and returns `{source, title, albumArtists, releaseYear, type, tracks[{title, durationS}], alreadyAdded}` without writing; errors for an unknown URL, `discogs_not_configured` (no `DISCOGS_TOKEN`), and for YouTube the library limits (`library_full_songs`, `library_full_bytes`).
- `POST /albums` with `{url}` (Discogs or MusicBrainz: creates the album at once) or `{url, confirm: true}` (YouTube: refused without `confirm`; creates the album and the missing songs, links the tracks, returns the song ids that still need audio; a metadata-only song add does not count against the hourly adds). `DELETE /albums/{id}` removes the album only.
- `PUT /albums/{id}/tracks/{index}/song` with `{songId}` links; `DELETE /albums/{id}/tracks/{index}/song` unlinks.
- `GET /albums/{id}/download-plan`: the ordered linked song ids that need a server fetch and a phone copy, the quota check (hourly adds left, songs, bytes) and the byte estimate. The client then runs the existing per-song calls; the YouTube album's audio fetch uses the same calls. A server-side `POST /albums/{id}/download-queue` is not recommended (a queue that outlives the app breaks the client-paced, one-at-a-time and `hourly_limit` pause that ADR-0010 and ADR-0012 give clients).

## DECISIONS (owner, 2026-10-26: all recommended)

The owner took the recommended option of every question; each line is the question and the chosen option.

- JA. What does "complete" mean? Every track is linked to a library song; a separate line "On phone N of M" shows the audio.
- JB. Source of the track list? (answered earlier, decisions 2 and 3, kept) A pasted Discogs release, MusicBrainz release or YouTube playlist URL in Add album.
- JC. Download on the web? "Download" to the phone is iOS only; the web saves to the catalog and, with Auto-download on, asks the server for the audio per track.

## Add album review and track fields (2026-10-27)

Server side of "adding an album from a YouTube playlist or video fills the tracks' fields". Amendment to the data-model rule above: copying EXISTING song text fields from the album into its songs (`albums[]`, `releaseYear`, genre tags, artist) is allowed because it adds no field to the song; the album stays the only home of album-only facts (type, track order, links, cover).

- Fill on create and link: every song created by `POST /albums/youtube/commit` gets Album (`albums[]` = the album title), `releaseYear` = the album year, the album's genres that are in the closed vocabulary (TAG-079; unknown names are dropped, never a 422) and Artist = the track's own artist, else the album artist (never "Various Artists"). A track whose only artist came from the uploader channel gets the album artist. For a song already in the library, and in `PUT /albums/{id}/tracks/{no}/song` and `POST /albums` with `songIds`, only EMPTY fields are filled; non-empty values are never overwritten.
- Preview guess: `guess {artist, album, year, type}`. The title pattern "Artist - Album (year) [FULL ALBUM]" (hyphen, en or em dash; year in () or []; tags such as [FULL ALBUM], (Full Album), (Official Audio) stripped) gives artist, album and year; the channel name is the artist only when the title has no "Artist - " part. Example: "Astral Projection – For All Mankind (2025) [FULL ALBUM]" on channel "Banjankri" gives Astral Projection, For All Mankind, 2025. `type` is one of `album` (default), `EP`, `single`, `compilation`, `soundtrack`, `live`, `mix`; `mix` only when the title or description says DJ mix, DJ set, live set, mixed by (title only) or continuous mix. Commit accepts `type` (top level or in `fallback`) and stores it on the album.
- Suggested genres: the preview response carries `genres` (vocabulary names, at most 4, may be empty): the styles and genres of the matched Discogs release (best candidate), else MusicBrainz for the first track via `genre_lookup`; synonyms mapped, duplicates removed; any failure gives `[]` and never breaks the preview. Each Discogs candidate also carries `genres` (its raw styles then genres). `fallback.genres` of the commit is mapped to the vocabulary.
- Specs: LIB-256, CAT-061, API-298, API-299. Tests: `server/tests/test_albums_review.py`, `test_albums_youtube.py`, `test_albums_youtube_flow.py`.
- 2026-10-27 video flow: the single-video Add album preview now uses the playlist guess, type and genre helpers (a "FULL ALBUM" title is an Album by the guessed artist, "mix" only on explicit DJ mix signals), reads Discogs, Wikipedia and RateYourMusic links from the description and prefills from a Discogs release link; "Find on Discogs" (`POST /albums/discogs/search`) covers videos without a link (API-300, API-301, LIB-257).
- 2026-10-27 track list: the Add album video table shows each track as a read-only text label with length, edit on demand via a pencil icon (LIB-258).
