# Complete albums: browse and download full albums

> Alex (2026-10-25): "implement complete albums / full albums, so I can 1) easily browse full albums, 2) easily download full albums". Addendum: "create a task; this also introduces a new entity of Album".

Analysis and requirements only: nothing is built, no code changes until Alex answers the open questions (JA to JL). Decision record: [ADR-0050](../tech/decisions.md) (proposed). Prior art that this task narrows and partly replaces: [task-0083](task-0083.md) and ADR-0039 (Artist and Release entities, proposed 2026-10-21, never built). Phases that edit `ios/` need Alex's permission, as in task-0083.

## Goal

1. Browse: an Albums view in the Library (a grid of covers), an album page with the track list in track order, and per album a status: complete, "partial N of M", or the list of missing tracks.
2. Download: one action that gets every track of an album onto the iPhone, with progress and quota awareness, and a way to add the tracks that are missing.

Key principle check ([CLAUDE.md](../../CLAUDE.md)): this makes downloading and keeping a whole album more dependable and changes nothing about offline playback; songs keep their own text fields and play without any album data.

## What exists today (read from `origin/main`, 2026-10-25)

- Song model: only text. `album` is a legacy derived string (the first album, [data-model.md](../specs/data-model.md) DATA-149), the stored form is `albums[]` (a list of titles, `albums[0]` is the original album, DATA-144, DATA-156, ADR-0025). There is NO track number, disc number, album artist, tracks total, album id or album cover anywhere in `server/`, `web/js/` or `ios/Sources/` (a search for `track_no`, `trackNo`, `track_number`, `tracks_total`, `album_artist`, `disc` finds nothing).
- Album text is shown in the song card (`web/js/song-card.js`, "Album"/"Albums" line, LIB-142, LIB-187), searched by the Library search (LIB-020, LIB-141; iOS `LibraryMatching.swift`), edited in the shared song form (iOS `SongFormView.swift`, `SongFormState.swift`; web `song-form.js`) and sent to the lock screen (`PlayerService.swift`, `MPMediaItemPropertyAlbumTitle`). There is no Albums view, no album grouping, no album filter facet (Library facets are Tags, Genres, Era, Countries, IOS-032), and no album entity or file.
- Statistics and the Genres map group by genre, artist and decade, never by album ([stats.md](../specs/stats.md), [genres.md](../specs/genres.md)).
- Where album text comes from today: yt-dlp (`server/app/metadata.py` `merge`: source `album`, then the Wikipedia infobox, then MusicBrainz `genre_lookup._album`); "Identify from audio" (`server/app/identify.py`) returns genres, countries, year and links, not album or track data. MusicBrainz is keyless (`server/app/genre_lookup.py`; it already reads the release-group id and its url relations but does not store or return them). Discogs needs `DISCOGS_TOKEN` (`server/app/discogs_lookup.py`; the release `tracklist` is read only to check that a title is on the release, `_has_track`, never returned). AcoustID needs `ACOUSTID_API_KEY` and `fpcalc`. The docs do not say whether the two keys are set on the live server ([deploy.md](../tech/deploy.md#identification-keys) lists them as optional); the identify availability flags (`identify.py`) and the song Edit dialog show it.
- Covers are per song (`covers/<id>.jpg`, `cover_source`, task-0054). Task-0083 decision D already puts an "album image" level into the cover fallback chain (song cover over album image over artist image over the default).
- Importing: a YouTube playlist link in the Add dialog opens an import table (ADD-150 to ADD-159) and, since task-0059, creates or extends a saved playlist that keeps `source {type: "youtube", id, url, positions}` (PLS-135, PLS-136, PLS-138). The positions are the playlist order, so an album uploaded as a playlist already carries track order. A single-song Add refuses albums, sets and playlists (ADD-061). Time-coded videos (a full album in one video) are task-0038 phase 1, not built. Drafts (ADR-0032) hold pasted "Artist - Title" lines per user, outside the quotas.
- Download: the web is catalog-only; it plays audio already on the server and, with "Auto-download songs" on, asks the server to fetch a song's audio (`POST /songs/{id}/audio`, PLY-110, ADR-0010 amendment). Only iOS copies audio to the phone: `ServerLink.getAudio` (server fetch, then copy), `ServerLink.download`, and `downloadAllMissing` ("Download all to iPhone" in Settings: `BulkDownload {total, done, failed, running, cancelled, stopReason}`, two at a time, cancel, resumable, stops on `hourly_limit`).
- Quotas (ADR-0012, owner exempt): `USER_MAX_SONGS=500`, `USER_MAX_BYTES=5GB`, `USER_ADDS_PER_HOUR=20` (one server audio fetch is one add), `USER_MAX_CONCURRENT_DOWNLOADS=1`; errors `hourly_limit` (429), `library_full_songs`, `library_full_bytes`. A metadata-only `POST /songs` does not count against the hourly adds.
- Missing-track audio has no match flow yet: Get audio with a YouTube match and confirm (CAT-021 to CAT-025) is [task-0008](task-0008.md), to do.
- Data sync: each user's `library.json`, `drafts.json`, `playlists.json`, `genre_layout.json` live under `audioplayer/users/<uid>/` in the git-synced data repo; the server is the only writer of owned paths and a hand push to those paths makes the sync report "data diverged" ([ADR-0026 to ADR-0028](../tech/decisions.md), [storage-and-sync.md](../specs/storage-and-sync.md)).
- Precedent against a second entity: ADR-0025 gave artists a table, ADR-0031 removed it again (task-0049) because every fact now sat two hops from the song, needed endpoints, sync rules and a migration that lost data; Alex: "I don't want an RDBMS with dozens of tables/entities".

## Requirements

### A. Browse

- A1. Library sub-navigation (owner idea, 2026-10-25): the header switch "Songs | Drafts N" (LIB-159) becomes "Songs | Albums | Artists | Drafts N" on the web and on iOS. Songs and Drafts stay exactly as they are. Albums ships first; Artists is a later, separate phase that does not block albums (A8); until then the switch shows Songs | Albums | Drafts N. Signed-in users and the owner; guests have no library view (ADR-0041).
- A2. Albums view: a cover grid grouped by album, one card per album with the cover, title, album artist, year, and the completeness badge (A5). Release-type chips above the grid: All, Albums, EPs, Singles, Compilations, Live (soundtrack and DJ mix albums show under All and, as `type` values, in a "More" chip only when some exist). Sort: Title, Artist, Year, Recently added, Completeness; search over album title, album artist and track titles; further filters: status (complete, partial, no track list) and "On phone" (all tracks downloaded). The cover is the first track's cover (derived, nothing stored) until an album cover exists (phase 6).
- A3. Album page (`#/library/albums/<id>` on the web; a pushed screen on iOS): back link, cover, title, album artist, year, type, "N tracks, H:MM", status, actions (Play album in track order, Add to queue, Shuffle, Download album on iOS, Add missing tracks, Link release). The track list is in disc and track order; a track you have shows as a normal Library row (play, queue, playlist, audio state); a missing track shows a muted row with its number, title, length and a "Find" button.
- A4. Songs of an album that have no track number sort after the numbered ones, by title, and show a "No track number" hint; the user can set the number in the song form (Track no.).
- A5. Status of an album: "Complete" when every track of the release (the expected track list, bonus tracks excluded) is in the library; "Partial N of M" when some are missing, with the "Missing tracks" list (title, number, length); "N songs" with no status when no expected list is known; plus a second, separate line for audio: "On phone N of M".
- A6. A song with several albums (a single, then the album, then a compilation): it appears on each album it belongs to (question JJ); its primary album decides its track number.
- A7. Signed out on iOS: albums are derived from the phone-only songs (local library), with no status beyond "N songs" (the expected lists are server data). No sign-in is needed to play.
- A8. Artists view (later phase 7, question JL): a list of artists DERIVED from the song credits (ADR-0024: main artists, featured artists and version artists such as remixers, each with a role count), one row per artist with a count of songs and albums, sorted by name or by song count, with a search box. An artist opens to a page with their songs (as Library rows) and their albums (as album cards, A2). Nothing is stored: the list is computed from `library.json` on read and cached in memory by library version; there is no Artist table, no `artists.json` and no artist id beyond a derived slug of the normalised name (the table removed in data model v3, ADR-0031 and task-0049, is not reintroduced). Two spellings of one person stay two artists until the user edits the songs (no automatic merging; aliases are not part of this task); "View in Library" by artist (LIB-210) keeps working as a search.

### B. Download

- B1. "Download album" (iOS): for every track of the album in track order, in the library, not yet on the phone: if its audio state is `none`, fetch it to the server (`getAudio`), then copy it to the phone (`download`). It reuses the bulk machinery of `downloadAllMissing` (concurrency, cancel, resume, `stopReason`) with the track list as the queue; tracks already on the phone are skipped; it is safe to run again.
- B2. Before the first transfer the sheet shows the cost: "12 tracks, 3 on the phone, 9 to fetch, about 85 MB; 20 server fetches left this hour" (`GET /me/usage`, track durations and the average bytes per second of the user's songs). If the plan exceeds the hourly adds the download is split: it runs what the quota allows, shows "Paused: hourly limit, resumes in N min" and continues on its own while the app is open or on the next tap; the app never exceeds the quotas and never queues forever silently. Library or byte limits (`library_full_songs`, `library_full_bytes`) are checked up front and block the download with the real reason.
- B3. Progress: "5 of 12", per-track state in the album page (waiting, fetching, downloading %, on phone, failed with a retry), a cancel button, a result line ("11 of 12 on the phone, 1 failed").
- B4. Web: "Download" to the phone does not exist. The web album page saves to the catalog and, only when "Auto-download songs" is on (PLY-110), has "Get audio on server" for the whole album (the same per-song `POST /songs/{id}/audio`, one add each, one at a time, paused on `hourly_limit`). Otherwise the web album page offers Open on YouTube/SoundCloud per row, as the Library does (question JC).
- B5. Add missing tracks (the tracks of the release that are not in the library), from three sources, always shown to the user for confirmation, never added silently:
  1. The user's own links: a pasted YouTube playlist (a YouTube Music album page is a playlist whose id starts with `OLAK5uy_`; unverified here) or a SoundCloud set. The existing import table (ADD-150 to ADD-159) is reused; "This is an album" marks the rows as one album with the playlist positions as track numbers.
  2. The MusicBrainz or Discogs track list of the linked release: the missing rows are created as catalog entries without a source link (metadata only, `audio: false`, album id and track number set), or as Drafts (question JK).
  3. A source for each missing track: "Find" runs a YouTube search for "album artist - title" with the track length as a hint and shows candidates to pick (this is the match flow of task-0008, CAT-021 to CAT-025). "Find all" returns one candidate list per missing track as a review list, never an automatic add.
- B6. An added track keeps the album link, so the album turns "Complete" when the last missing track is added; undo is the normal Delete from library.

### C. Data (summary; the full proposal is in the next section and ADR-0050)

- C1. Albums are derived from songs, not typed in: a song belongs to an album by its `albums[0]` title plus its album artist, normalised (case, whitespace, punctuation, diacritics as in the Library search; exact match only, per the curated-matching rule of ADR-0039: nothing fuzzy is merged automatically).
- C2. The expected track list (the release) comes from MusicBrainz or Discogs, or from a pasted playlist, is confirmed by the user once (Link release), and is stored with the album.
- C3. Matching a track of the release to a song: same normalised base title and same main artists (the album artist for a compilation); a bracket version in the release title is parsed with the existing title parser (ADD-159, `credit_title.parse`) so "Title (2011 Remaster)" matches a song titled "Title" with the version `remaster` (DATA-191); a different version (remix, live) is a different track; a manual link or unlink always wins. The match reuses the Library's folding (`web/js/search-text.js`, iOS `LibraryMatching.folded`) and is computed, not stored.
- C4. Edge cases: compilations and "Various Artists" (album artist is the reserved text "Various Artists", each track keeps its own artist); multi-disc (disc number then track number, "Disc 2" headings, "tracks total" counts all discs); bonus and hidden tracks (flagged `bonus`, listed, not counted for "Complete"); singles and EPs are albums of type single and EP with the same rules; one album uploaded as a single long video (task-0038: the split songs carry `source.start`, so they become tracks in time order); different editions (deluxe, remaster) are different expected lists, the user links the edition they own; a song whose album text differs by spelling ("Greatest Hits" by two artists is two albums because the artist is part of the key); live albums with the same title as a studio one are told apart by the album artist and the user's link.

## Album entity and data model

Albums are a first-class concept in the API and the UI (an id, a page, a status, a track list) but stored lightly: the song stays the source of truth for every fact the user sees on a song, and the album is derived and rebuildable. This is the answer to the ADR-0025 / ADR-0031 precedent: keep Album light, derived and rebuildable from songs plus external ids, with no manual maintenance and no data that lives only in the album.

### Fields

Album (an API object; the stored part is the sparse record below):

| Field | Meaning | Derived or stored |
| --- | --- | --- |
| `id` | `alb_` plus the first 8 hex of the sha1 of the normalised title, `\|`, the normalised album artist key | derived, stable across rebuilds |
| `title` | the album title as written on the first song (most common spelling) | derived; stored only as an override |
| `albumArtists[]` | credits as in ADR-0024 (names, roles main; "Various Artists" for compilations) | derived from `albumArtist` text on the songs, else the shared main artists; stored only as an override |
| `releaseDate` / `releaseYear` | from the release when linked, else the earliest song year | stored when linked |
| `type` | `album`, `EP`, `single`, `compilation`, `live`, `soundtrack`, `DJ mix` (the list of task-0083, extend only with Alex's approval) | stored when linked, else guessed (`single` for one track) |
| `cover` | the first track's cover (phase 1), later an album image (phase 6, Cover Art Archive for linked MusicBrainz releases, unverified) | derived |
| `label` | optional | stored when linked |
| `ext` | `{musicbrainz_release_group, musicbrainz_release, discogs_master, discogs_release, youtube_playlist}` | stored (the link the user confirmed) |
| `tracks[]` | the expected list: `{disc, no, title, artists?, durationS?, bonus?}` | stored (a cache of the external list; refetchable from `ext`) |
| per track `songId` | the library song for that track, or `null` = missing | derived at read time from the match rules (C3); not stored; the song's own `albumId` + `trackNo` is the stored link |
| `have`, `total`, `status` | counts and `complete` / `partial` / `unknown` | derived |

Song gains optional fields (all additive, absent means unknown):

- `trackNo` (integer 1 to 999) and `discNo` (integer 1 to 99, absent means one disc).
- `albumArtist` (text, trimmed; set when it differs from the main artists, notably "Various Artists").
- `albumId` is not stored in the first slice: the id is derived from `albums[0]` + `albumArtist`/main artists on read. It is stored only after a manual link or merge (then it is the override that wins).
- A song on several albums (question JJ, recommended): the primary album is `albums[0]` with its `trackNo` / `discNo`; the other titles in `albums[1:]` are listed on those albums without track numbers unless the user links them. No many-to-many appearance table.

### Where it lives

- Recommended: a sparse per-user file `users/<uid>/albums.json` beside `library.json` and `drafts.json` (git-synced like them, atomic write inside `deps.tx`, tolerant reader: a missing, unreadable or malformed file or entry reads as empty), holding only what cannot be derived: external ids, the confirmed expected track list, overrides (title, album artists, type), manual track links and merges. Delete the file and every album still appears (derived from songs); only the link to a release and its cached list are lost and refetchable. It does not count toward the song or byte quotas (it is a few KB per linked album).
- Not a shared owner-curated catalogue (ADR-0039 option): open signup (ADR-0012) means every user has own songs and own spellings; a shared catalogue makes the owner the editor of everyone's albums, and was the part of the earlier model that grew into dozens of tables. A server-side, non-git cache of MusicBrainz and Discogs responses (memory or a cache file outside the tracked tree, like `backups-*`) keeps repeat lookups cheap and polite to the services.
- The ids in `albums.json` are the album ids above, so a rebuild finds the same album; a renamed album keeps its stored record through a `key` alias.

### Data model version and migration

- Recommended: no schema bump. Adding optional song keys is additive (iOS ignores unknown keys, `ios_contract.json` pins the keys the app reads, IOS-072). `credits_schema` stays 3 (ADR-0031). If a model bump is wanted anyway it would be named v4, with the same migration pattern as `migrate_model2` / `migrate_model3` (backup, marker, dry run, one commit per user).
- Backfill, an idempotent startup migration `app.migrate_albums` (same pattern as `migrate_version_norm`: backup in `backups-albums/<uid>/`, marker, `AUDIO_ALBUMS=0` disables, dry run by default on the command line, one commit per user, `updated_at` untouched): it writes nothing but `trackNo` where a source gives one (a YouTube playlist position kept in a playlist `source.positions` is a candidate; yt-dlp `track_number` is not kept by `extractor.py` today and needs a check). The `albums[]` titles are already there, so grouping needs no migration. A report lists albums with one song, spelling clusters that look like one album (suggested only, never merged), and songs with an album but no number.
- Phase 0 starts with a read-only audit of the live library (how many distinct normalised albums, how many have two or more songs, how many spellings clash) so the numbers decide whether the thresholds in the UI make sense.

### Sync and the "data diverged" pitfall

- `albums.json` is an owned path (`audioplayer/users/<uid>/`, `GIT_SYNC_OWNED_PREFIXES`, ADR-0028): only the server writes it; an inbound change is validated by the sync's loader check (add `albums.json` to the list of per-user files with `drafts.json` and `genre_layout.json`: valid JSON, an object with `albums`).
- Nothing in this feature may be done by pushing files into the data repo by hand: a push to `audioplayer/users/<uid>/` while the server has unpushed commits is the case that makes the sync report "data diverged" and needs a manual rebase ([ADR-0027](../tech/decisions.md), the data-repo note in the project memory). Backfill and fixes go through the migration and the API only.
- Concurrency: link, unlink, refresh and merge run under `deps.tx` like every library write; the expected-list fetch (network) runs outside the lock and its result is written in one short transaction.

### API (planned only, API-241 to API-245)

- `GET /albums`: the derived list `[{id, title, albumArtists, releaseYear, type, cover, have, total, status, onPhoneHint, songIds}]` (cheap: computed from the library in memory, no external call).
- `GET /albums/{id}`: the album with `tracks[]` in order, each with `songId` or `null`, `audio_state` and `bonus`.
- `POST /albums/{id}/link` with `{url}` (a MusicBrainz or Discogs release, a YouTube playlist) or `{search: true}`: returns candidate releases to pick (never links silently); `POST /albums/{id}/link/confirm` stores the pick. `DELETE /albums/{id}/link` unlinks. `POST /albums/{id}/refresh` refetches the expected list.
- `GET /albums/{id}/download-plan`: the ordered song ids that need a server fetch and a phone copy, the quota check (hourly adds left, songs, bytes) and the byte estimate. The client then runs the existing per-song calls. A server-side `POST /albums/{id}/download-queue` is not recommended (a queue that outlives the app breaks the one-download-at-a-time and `hourly_limit` pause that ADR-0010 and ADR-0012 give clients).
- `POST /albums/{id}/missing` with `{track_nos}`: creates the metadata-only catalog entries (or drafts) for the chosen missing tracks.

## Open questions (JA to JL; recommendations, not decisions)

JA. What does "complete" mean?
1. All tracks of the official release (needs the expected list).
2. All tracks of that album that you added (no outside data, never "partial").
3. Official release when a list is linked, otherwise just "N songs" with no status. Recommended.

JB. Where does the expected track list come from?
1. MusicBrainz and Discogs candidates, you pick the release; a pasted MusicBrainz, Discogs or YouTube playlist link is also accepted; never linked silently. Recommended.
2. Discogs first (better for electronic releases, needs the token), MusicBrainz second.
3. Only a YouTube playlist or link you paste.

JC. Download on the web?
1. "Download" to the phone is iOS only; the web saves to the catalog and, with Auto-download on, asks the server for the audio per track. Recommended.
2. The web album page also gets a "Get audio on server" button always.
3. The web only streams audio already on the server.

JD. Compilations, various artists, multi-disc, bonus tracks?
1. One album type `compilation` with album artist "Various Artists", disc then track order, bonus tracks listed but not counted for "Complete". Recommended.
2. Every edition (deluxe, remaster, bonus) is its own album with its own list.
3. Ignore discs and bonus tracks.

JE. Storage and quota impact?
1. Album download obeys the existing limits (20 server fetches an hour, 500 songs, 5 GB), shows the cost first, pauses on the hourly limit and resumes. Recommended.
2. Raise the limits for album downloads.
3. Only the owner may download whole albums.

JF. Scope order?
1. Server and web first (phases 0, 1, 3), then iOS browse and download (2, 4), then add missing (5). Recommended.
2. iOS first (the download is the main use).
3. Web and iOS together per phase.

JG. Albums in the Genres map and Statistics?
1. Not now; Albums stay a Library view, an album facet in Statistics later. Recommended.
2. Add an "Albums" list to Statistics now (complete, partial counts).
3. Album filter on the Genres map.

JH. Which form does the Album entity take (ADR-0050)?
