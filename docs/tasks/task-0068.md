# Features screen: releases and planned features

> Alex: the Features screen (Help menu, `#/features`, now a "coming soon" placeholder, WEB-133) shows two tabs, "Releases" and "Planned".

## Decisions (owner, 2026-10-20)

- CH1: a release is a deploy. Its hash and date come from the deploy itself; its features are the finished work between the previous deploy and this one.
- CL1 (2026-10-21): one release per date. All deploys and features dated the same day are combined into one entry (one date heading, one merged feature list, newest first, de-duplicated); the entry id is the hash of the newest deploy of that day. This refines CH1 and CI1.
- CI1: Releases tab, newest on top. Each release is a block headed by the short hash (7 characters) and the date as `YYYY-MM-DD` (no time), with a bullet list of what was implemented: a short feature sentence, then a link to the task file when the feature belongs to a task.
- CJ1 (amended: three tabs Released, In progress, Planned): the In progress tab lists tasks whose status starts with `in progress`, the Planned tab those that start with `to do`, newest task id first; each row has title, task id, tags and a link to the task file.
- CK1: visible to everyone, guests and signed-out visitors included. The repo is public, so nothing new is exposed. If the repo is made private, the task links on GitHub break and the design must switch to in-app task pages (render the task markdown on a route of its own, served by the server); revisit this task then.

## Design (agent, to confirm)

- No build step for the web (ADR-0003, ADR-0017): the server builds the data itself (`server/app/features.py`) and serves it at `GET /features/data` (public, cached by HEAD); `scripts/gen-features.py` is a local CLI over the same module. The deploy user cannot write `/opt/audioplayer`, so nothing is generated at deploy time.
- Recorded deploys: at every service start the server appends `{HEAD, UTC date}` to `<data repo root>/_state/deploys.json` when HEAD changed (a restart on a new HEAD is a deploy).
- Backfill: there are no old deploy records. Days before the first recorded deploy are derived from git, one release per UTC calendar day, hash = last commit of the day, items = feat subjects (DA1) (docs, chore, test, style, merges skipped; all items listed, no "and N more"). From the first recorded deploy on, releases are the commit ranges between recorded deploys. Rule (owner, 2026-10-21): all features of one date are combined into one release, one date heading, one merged feature list (newest first, de-duplicated); several deploys on the same date give one entry whose hash is the last deploy of that day.
- DA1 (owner): only `feat` commits (with or without scope) become items; fix, perf, refactor and the rest never do; a release with no feat item is omitted (`KEEP_TYPES` in `server/app/features.py`).
- Data adjustments (genre removals, single-song genre fixes, scope `data`) are not published: excluded by scope, by regex patterns (`EXCLUDE` in `server/app/features.py`, overridable under `exclude` in `docs/releases-map.json`) and per `;` clause; a release with nothing left is omitted (owner).
- Curated text (owner, 2026-10-21): long or multi-feature subjects are rewritten by hand under `items` in `docs/releases-map.json`: a commit hash prefix (7+ hex characters) maps to `[{"text": ..., "task": "task-00NN"|null}]`, which replaces the item generated from that commit (empty list = hidden); the rest is unchanged.
- Task links: `task-00NN` in the commit message, else the hand-written `docs/releases-map.json` (commit prefix or subject keyword to task id), else a task file changed in the same commit (or in the same release) whose title shares words with the subject.
- The page shows the newest 30 releases and a "Show older" button; the route stays lazy (tier 2).
