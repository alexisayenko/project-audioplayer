# Test suite audit and parallel test runner

> Alex (2026-10-27): "do we need all those tests, are many useless or duplicates?"

Analysis and tooling only: nothing is deleted without Alex's approval.

## Why

- A full regression comparison (web plus server) takes very long: about 250 web test files, each launched separately through WSL, which crashes on `library.test.mjs`, plus about 4,300 server tests.
- Some tests hang on the network: `test_playlist_import`.
- SonarCloud flagged 396 composite assertions in `server/tests`, which suggests verbose tests.
- Several tests already fail at a clean HEAD (listed below), which makes before/after comparisons noisy.

## Goal

### 1. Audit (read-only first)

Deliver a table, one row per item, with a proposed action: keep, merge, delete, fix, or mark slow/network. Cover:

- slowest test files (web and server);
- near-duplicate and overlapping tests;
- tests without real assertions;
- tests of removed features;
- flaky or network-dependent tests;
- known failing tests at a clean HEAD: aubio bpm (2), 4 genre tests, `test_genre_sources` committed counts, `test_route_auth` drafts route, `test_web_preload` Studio modules, song-card Genre row, app-guest genres-map.

Rule: nothing is deleted without Alex's approval and without a coverage comparison before and after.

### 2. Parallel test runner

A script `scripts/test-all.sh` (or `.mjs`) that:

- runs the web test files concurrently with a worker limit and a per-file timeout;
- prints one result line per file, then a summary, and exits non-zero on failure;
- optionally compares against a baseline: a git worktree of HEAD, diffing the failing set by test name;
- runs the server suite through the venv with network tests skipped;
- has a flag for changed-files-only.

Document it in [docs/tech/ci-cd.md](../tech/ci-cd.md) (local checks) or the tests doc.

- The runner works from Git Bash and from WSL2.

## Open questions for Alex

A. What counts as a "useless" test?
1. No assertion on behaviour (only runs the code).
2. Duplicates another test's assertions.
3. Tests a removed or frozen feature.
4. All of the above.

B. Coverage threshold for approving a deletion?
1. No drop in line coverage.
2. Drop of at most 0.1 point.
3. Per-module: no uncovered new lines in touched modules.

C. Network tests?
1. Mark with a marker and skip by default; run only in a nightly or manual job.
2. Replace the network with a fake in each test.
3. Delete them.

D. Known failing tests at HEAD?
1. Fix first, then audit.
2. Audit first; fix in separate tasks.
3. Mark expected-fail until fixed.

E. Runner language?
1. Bash (`scripts/test-all.sh`), consistent with `check.sh`.
2. Node (`scripts/test-all.mjs`), easier concurrency and timeouts.
