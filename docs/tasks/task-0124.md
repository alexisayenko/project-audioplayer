## Facts verified in the code (2026-10-27)

- **Identity.** `uid` is the first 16 hex of `sha256(lowercased email)`, or `sha256(sub)` for an Apple token without email (`server/app/users.py`). `oauth.verify_identity` returns `{provider, email, sub}` (no `iat` yet). `deps.admit` creates `users/<uid>/profile.json` on first sign-in and would silently create it again for any valid credential.
- **Sessions are stateless.** The web cookie `__Host-session` is an HMAC-signed `{provider, email, uid, expiry}` for 30 days (`session.py`); the iOS bearer is the provider ID token. Nothing can be revoked server-side today, so after a deletion any old cookie or token would pass `admit` and re-create an empty profile.
- **Per-user stores** (everything keyed by `<uid>`):
  1. data repo `audioplayer/users/<uid>/`: `profile.json` (email, provider, created_at, Apple `sub`), `library.json`, `drafts.json`, `albums.json`, `playlists.json`, `genre_layout.json`, and the daily snapshot `play-history.csv` (`deps.py` path helpers, `plays.repo_copy`);
  2. LFS covers repo `audioplayer/users/<uid>/covers/` (`deps.covers_dir`);
  3. audio `<music_root>/users/<uid>/` including its `.peaks/` cache (`deps.audio_dir`, `peaks.cache_path`);
  4. live play history `<AUDIO_PLAYS_DIR or <music root>/.plays>/<uid>/` (`play-history.csv`, `batch-keys.json`), outside git (API-196, API-198);
  5. migration backups `<data repo root>/backups-credits|model2|model3|sources|reference-tags|genre-removals|genre-eras-seed/<uid>/library.json`, beside the git-added `audioplayer/` tree (not committed, so only on the server disk);
  6. process memory: `deps.JOBS` and the scheduler queue (`jobs.Scheduler`), `deps.SUBS`, `limits.RATE` stamps, the plays cache.
- **Already there:** `plays.delete_user(uid)` removes (4) and the snapshot in (1). Nothing else deletes a user; there is no `DELETE /me`. Existing routes are `GET /me` and `GET /me/usage` (`server/app/routes/me.py`).
- **Quota accounting is computed from disk** (`limits.dir_bytes` of the user's and the pool directory; the song count from `library.json`), so removing the directories frees quota with no counter to fix; the hourly add counter `limits.RATE` is in memory and re-learned from `added_at`.
- **Git history is permanent**: NFR-053 and ADR-0012 say deleting a user later does not erase the email from history. The data repos are private (`alexisayenko/data-storage`, `-lfs`), commits are `audioplayer: <uid8> <verb>`. Hand-made bundles in `/var/backups/audioplayer-<ts>/` (deploy.md) hold every user's data.
- **iOS sign-in** (`AuthService.swift`): native `ASAuthorizationAppleIDCredential` gives `identityToken` only; `authorizationCode` is ignored; the Google session keeps a refresh token in the Keychain. The app never calls `/me` today (it verifies with `GET /tags`), so it does not know whether the user is the owner.
- **Info.plist** comes from `ios/project.yml` (`info.properties`): `NSMicrophoneUsageDescription`, `UIFileSharingEnabled`, `ITSAppUsesNonExemptEncryption: false`, and `NSAppTransportSecurity: {NSAllowsArbitraryLoads: true}` with a comment calling it a known gap. Every endpoint in `Endpoints.swift` is built with `scheme = "https"` (electrophone.cc, the legacy play.isayenko.net, accounts.google.com, oauth2.googleapis.com, en.wikipedia.org); the only plain-http use is the `-serverURL` dev path to a mock server on localhost. No third-party SDK is linked.
- **The web UI is served by the same FastAPI app** (`web.mount`: `NoCacheStaticFiles(directory=web, html=True)`), anonymous for static files (API-090); `GET /legal` already returns a copyright note and an optional `LEGAL_CONTACT` (email or https URL). `studio.electrophone.cc` is a separate Cloudflare Pages site.
- `pyjwt[crypto]` is already in `server/requirements.txt`, so signing the ES256 client secret for Apple needs no new dependency. The server env file is `/etc/audioplayer/env` (secrets, root-owned).

## H2: account deletion (phases 2 to 4)

**Scope.** A signed-in non-owner user can delete their whole server-side account from iOS and the web; the server erases every store listed above, refuses the owner, invalidates old sessions, and (when configured) revokes the Sign in with Apple grant. Out of scope: data export (`GET /library` and `/files` exist; a bulk export is a separate task if wanted), the Mac app's UI, Apple server-to-server notifications, and H11 (credential state at launch). H11 relation: it is a dependency only for the review notes; the delete flow does not need the stored Apple user id, and the two can ship in either order. Do not widen into H11 here.

### Server design

`DELETE /me` (new `server/app/routes/me.py` handler, new module `server/app/account.py` for the purge so the route stays thin).

- **Auth.** `Depends(deps.require_token)`, then reject: guest or anonymous (401, as everywhere), the `X-API-Token` principal and the owner (`user["owner"]`, covers `OWNER_EMAIL` and the pinned Apple sub): 403 `owner_account`; the account of `PUBLIC_VIEW_EMAIL` (`guest.view_uid()`, the public-view account of [ADR-0018](../tech/decisions.md), superseded by ADR-0041 but still configurable): 409 `public_view_account`. A session-cookie call needs the CSRF header (already enforced for non-safe methods).
- **Request body** (JSON on DELETE; `APIClient.send` and `fetch` support a body; if a proxy ever drops it, the fallback is `POST /me/delete` with the same body): `{confirm: "<account email>" , id_token: "<fresh ID token>", apple_authorization_code?: str, apple_client?: "app"|"web"}`.
  - `confirm` must equal the account email (or the literal `DELETE` for an Apple account with no email, such as Hide My Email without a stored address): 422 `confirm_mismatch`.
  - `id_token` proves recent authentication: it must verify through `oauth.verify_identity`, map to the same uid, and have `iat` within 10 minutes (the claim is added to `verify_identity`'s result): else 401 `reauth_required`. iOS gets it by re-running the Apple sign-in sheet (which also yields the authorization code) or, for Google, `AuthService.refreshedToken()`; the web re-runs its sign-in button. This limits a stolen session cookie or an old token. (Decision AR5.)
- **Order of work**, all under `users.user_lock(uid)`; each step is idempotent so a failed call can be repeated:
  1. Write the tombstone (below) with state `deleting`; from now on `admit`, `tx` and download completion refuse this uid.
  2. Cancel work: drop queued scheduler items and mark running `deps.JOBS[(uid, *)]` cancelled; a download finishing later must not write (the writers check the tombstone, so no orphan file under `users/<uid>/`).
  3. Purge, outside git first: `plays.delete_user(uid)` (live history and cache); `rmtree` audio `<music_root>/users/<uid>/` (this includes `.peaks/`); `rmtree` `backups-*/<uid>` in the data repo root; pop `deps.SUBS`, `limits.RATE` and the plays cache entries for the uid.
  4. Purge from git in one `deps.tx(uid, "delete account")` transaction (commit message `audioplayer: <uid8> delete account`): remove `audioplayer/users/<uid>/` in the data repo and `audioplayer/users/<uid>/covers/` in the covers repo. `GitSync.commit` already commits changes under `audioplayer/` in every repo, so deletions are committed and pushed by the existing retry loop; with no `AUDIO_DATA_REPO` (dev and tests) the same `rmtree` applies to the plain tree.
  5. Apple revoke (below), best effort; its result never blocks the deletion.
  6. Tombstone becomes `deleted`; respond `200 {deleted: true, removed: {songs, audio_bytes}, apple_revoked: true|false|null}` (`null` = not an Apple account or revoke not configured). 200 with a summary rather than 204 so the clients can show what happened.
- **Session and token invalidation (tombstone).** A small JSON file `.deleted.json` in the plays root (outside git, next to `.last-sync`), `{uid: {state, at}}`, entries pruned after 30 days (`session.LIFETIME`, the longest a cookie can live). `deps.admit` consults it: a session cookie whose issue time (`expiry - LIFETIME`) or a bearer whose `iat` is not later than `at` gets 401 `account_deleted`; a fresh sign-in after deletion is a normal first sign-in and creates a new empty account (same uid, because the uid derives from the email). The tombstone holds a pseudonymous uid and a timestamp only, no email. State `deleting` lets the same user (fresh `id_token`) call `DELETE /me` again to finish.
- **What is deleted / what remains.** Deleted: everything in the five stores above plus memory. Remains: (a) git history of both data repos, which still contains the profile, library and cover blobs of earlier commits (NFR-053, ADR-0012: permanent); (b) hand-made bundles in `/var/backups/audioplayer-<ts>/`; (c) server logs (`journalctl`) with truncated hashes of the Apple `sub` and uid prefixes in commit messages; (d) Cloudflare tunnel logs. These are stated in the privacy policy; AR2 and AR3 choose how far to go.
- **Quota and accounting.** Disk usage and song counts are derived from the directories and `library.json` (see facts), so a deleted user's bytes return to the pool immediately and `POOL_MAX_BYTES` sees them. Because the uid is deterministic, a re-sign-up lands on the same uid with a fresh library and a fresh hourly add counter; that resets the 20 adds per hour counter (a minor abuse vector, bounded by the per-song and pool caps; AR8 offers a cooldown). The owner is exempt from the quotas and from deletion.
- **Apple token revoke.** Needs an Apple authorization code (single use, valid 5 minutes), because Apple only revokes through a refresh token that the server obtains from it:
  1. `POST https://appleid.apple.com/auth/token` with `grant_type=authorization_code`, `code`, `client_id`, `client_secret` (and `redirect_uri` for the web Services ID) returns a `refresh_token`.
  2. `POST https://appleid.apple.com/auth/revoke` with `client_id`, `client_secret`, `token` = that refresh token, `token_type_hint=refresh_token`.
  - `client_id` is the bundle id `com.alexisayenko.audioplayer` for the app and `APPLE_WEB_CLIENT_ID` for the web (`apple_client` says which). `client_secret` is an ES256 JWT (`iss` team id, `sub` client id, `aud` `https://appleid.apple.com`, `exp` a few minutes ahead, header `kid`) signed with a Sign in with Apple private key. New operator config in `/etc/audioplayer/env`: `APPLE_TEAM_ID` (`L8C7TUQLBM`, the project's `DEVELOPMENT_TEAM`), `APPLE_KEY_ID`, `APPLE_KEY_FILE` (path to the `.p8`, mode 600, never in a repo; credential rule in CLAUDE.md). Unset = no revoke, `apple_revoked: null`, and the confirmation text tells the user to remove the app in Settings > Apple Account > Sign in with Apple.
  - Network failure or a non-200 from Apple: log the status only (no token), `apple_revoked: false`, deletion stands. The authorization code and tokens are never stored or logged.
  - Google: no review requirement. Optional follow-up for the iOS app: call `https://oauth2.googleapis.com/revoke` with the stored refresh token before signing out (client-side, no server involvement). Not in this task unless Alex wants it.
- **API surface for the clients.** `GET /me` already returns `owner`; the iOS app starts reading it (`Endpoints.me`, a small `APIClient.me()`), to hide the row for the owner and read the email for the confirm text.

### iOS design

- Settings > Account card (signed in, not owner): a quiet text row "Delete account" below Sign out (the audit's H24 notes Sign out is drawn as a red danger button although nothing is lost; do not copy that: only the final confirm button is destructive-styled).
- Tap opens a sheet (not a popup alert; two steps): (1) what will be deleted, in plain words (your library, playlists, drafts, covers and downloads on the server, your listening history, your account), what stays (songs already downloaded on this iPhone stay playable, see AR4; Apple/Google keep their own account), that it cannot be undone, and the retention note; a field where the user types their email (or `DELETE`); (2) the re-authentication: Apple users get the system Sign in with Apple sheet (the same `SignInWithAppleButton`, scope none), which yields `identityToken` and `authorizationCode` for the request; Google users get `refreshedToken()`.
- On 200: `auth.signOut()`, `server.cancelBackgroundWork()`, clear the caches keyed by account (`CollectionStores` key), show "Account deleted" (and, if `apple_revoked` is false or null for an Apple account, the Apple ID settings hint), return to the signed-out local library (IOS-016a). On a failure the user stays signed in with the error text; 401 `reauth_required` restarts step 2; 403 `owner_account` is shown as "The owner account cannot be deleted here."
- Review notes for App Store Connect (only if ever submitted): the path "Settings > Account > Delete account".
- The iOS changes touch `ios/` and need Alex's go-ahead before coding (project rule for `ios/`).

### Web design

- Settings > Account card (signed in, not owner): "Delete account" button, a confirm dialog with the same texts and the typed email, re-auth through the existing Google or Apple sign-in buttons (the id token from the new sign-in goes in the body; for Apple the web flow also returns `code`, sent as `apple_authorization_code` with `apple_client: "web"`), then `DELETE /me` with the CSRF header, then the same cleanup as sign-out (`api.js` logout path: clear the in-memory library, stop playback) and the login screen. Hidden for the owner and for guests.

### Acceptance criteria

1. A non-owner user signed in on iOS deletes the account; afterwards `users/<uid>/` is gone from both repos' working trees, the audio, peaks, plays and `backups-*/<uid>` directories are gone, a local commit `audioplayer: <uid8> delete account` exists in each repo that had files, and other users' data is byte-identical.
2. The old session cookie and the old bearer token of the deleted user get 401 `account_deleted`; a new sign-in with the same email creates a fresh empty account (no songs, usage zero).
3. The owner (`X-API-Token`, owner email, pinned Apple sub) and the public-view account get 403/409 and lose nothing.
4. A download or job in flight at deletion time leaves no file behind.
5. With the Apple key configured, a deleted Apple user no longer lists the app under Settings > Apple Account > Sign in with Apple; without it the response says `apple_revoked: null` and the app shows the manual hint.
6. An interrupted deletion (killed after step 3) finishes when the user repeats the call with a fresh token.
7. Web and iOS show the confirm flow, the typed-email check and the re-auth step; the delete button never appears for the owner.
8. The privacy policy states exactly what criteria 1 to 3 do and what remains (history, backups, logs).

### Effort and risks

- Server purge, tombstone and route: M. Web: S. iOS flow and re-auth: M. Apple revoke plus operator setup: M (a key in the developer portal, env, one real device run). Total L, delivered in phases 2 (server and web), 3 (iOS), 4 (Apple revoke).
- Risks: (1) Irreversible deletion by mistake: typed confirm plus fresh re-auth plus no soft-delete window; a grace period is deliberately not designed (AR5). (2) Git history and backups keep the data: honest disclosure instead of a promise (AR2, AR3); a forced history rewrite on the live clones can diverge the server sync (memory note "Data repo pushes can diverge sync"). (3) A race with the git-sync push loop: the deletion goes through `deps.tx` like every write. (4) The deterministic uid lets a returning user land on the same uid; the tombstone keeps old sessions out. (5) `DELETE` with a body through Cloudflare or URLSession: verify on the real tunnel in phase 2, fallback route named above. (6) Apple's single-use 5-minute code: the iOS step 2 must send it immediately after the sheet. (7) Reviewer access (Guideline 2.1) and H3 still block a public release; this task does not change that.

## Phasing

1. **Phase 1, hygiene (S, about 1 day):** H8 manifest, H9 ATS, H10 policy page and links, app-store-metadata and legal-draft facts. Needs only AR6, AR7.
2. **Phase 2, deletion backend (M):** `DELETE /me`, purge, tombstone, `iat`, web Settings, specs, policy retention text (AR2, AR3, AR5, AR8).
3. **Phase 3, iOS deletion (M, needs Alex's go-ahead for `ios/`):** `GET /me` use, sheet, Apple/Google re-auth, tests, a TestFlight build.
4. **Phase 4, Apple revoke (M):** operator key and env, `apple_authorization_code` on both clients, device verification. Skip until a public release is real (AR1).
