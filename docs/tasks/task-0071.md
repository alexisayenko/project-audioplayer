# Start listening first, run startup work in the background

> Decision CV1 (2026-10-20, Alex): the server must start listening first and run the slow startup work in the background.

Before: FastAPI ran `_startup` (git recovery with up to 30 s timeouts per repo, six migrations, `record_startup`) before uvicorn accepted connections, so every deploy was a long 502 window through the Cloudflare tunnel, and the player stayed at 0:00 on a 502.

## Scope

- `server/app/readiness.py`: thread-safe `readiness` object (`idle`, `starting`, `ready`, `failed`, `overdue`), background worker running the steps in the old order, outermost ASGI gate answering `503 {"detail":"starting","step":...}` with `Retry-After: 3` for everything except the allow-list (`/health`, `/robots.txt`, `/legal`, the page and the static files), cap `AUDIO_STARTUP_MAX_S` (300), switch `AUDIO_STARTUP_SYNC=1` for the tests (API-188).
- `/health` gains `ready` and `startup` (additive); the sync probe is skipped while starting.
- Web: `fetchWhenReady` retries a starting server for about 20 s with an inline "Server is starting..." note; amber LED; media retry treats 503 like 502 (WEB-140).
- `scripts/deploy.sh` waits for `ready`; `scripts/check-domain.sh` tolerates the new fields.
- Docs: API-188, WEB-140, deploy.md (restart), architecture.md (startup sequence), CHANGELOG.

## Done when

- Built and tested (server `test_readiness.py`, web `api-starting.test.mjs`); deployed, and a restart shows `health: ready` in `scripts/deploy.sh` with no 502 from the tunnel; the web page survives a restart without an error toast.
