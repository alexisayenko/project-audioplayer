# Change playback tempo to a target BPM

Future and deferred: nothing is decided or scheduled. Details marked **(proposed)** are suggestions; see [Open questions](#open-questions-for-alex). Web first; the iOS app is a separate change.

## Problem and idea

Set a target BPM for the playing song; the player speeds it up or slows it down to match, keeping the pitch.

`rate = target_bpm / song_bpm`. Example: 125.1 -> 132.3 BPM gives x1.0576, +5.8%.

Playback only. The audio file and the stored `bpm` are never changed.

## Levels

| # | Level | Range and quality | Effort |
|---|---|---|---|
| 1 | Browser `HTMLMediaElement.playbackRate` with `preservesPitch = true` (Safari: `webkitPreservesPitch`), a target-BPM input and a speed readout | Clean up to about +-10-15%; beyond that, artefacts on transients and vocals | Small |
| 2 | WASM time-stretch (Rubber Band, SoundTouch or signalsmith-stretch) in an `AudioWorklet` | About +-30%, better transients | Medium: added latency, seeking, one audio graph shared with [task-0023](task-0023.md) (visualizer) and [task-0020](task-0020.md) (normalisation), WASM size and load |
| 3 | Beatmatch, sync and crossfade between songs | Needs a beat grid (beat positions and downbeats), not one BPM per song | Large; its own task |
| 4 | Native iOS: `AVPlayer.rate` plus `audioTimePitchAlgorithm` (`.spectral` for music, `.timeDomain` for speech-like or small changes) | Same idea as level 1 | Small to medium; separate change in `ios/Sources` |

**(proposed)** Do level 1 first and judge the sound; levels 2-4 only on request.

## BPM precision (decision OPEN)

Today `bpm` is an integer, 20..300; whole numbers only are stored and shown ([data-model.md](../specs/data-model.md) DATA-007, `server/app/bpm.py` returns `round(...)`). A target of 132.3 from 125.1 needs the fraction.

1. **One decimal kept internally** (new optional field such as `bpm_precise`, or store `bpm` as a float with 1 decimal), whole numbers still shown everywhere else. Exact targets; touches data model, API validation, normalise-on-load, the Edit dialog, the stats chart and sorting.
2. **Keep integer** and accept approximate results: 125 -> 132 gives x1.056 instead of x1.0576, an error of up to about +-0.4% at 125 BPM (up to 0.5/125).

Accuracy caveat: detected BPM is an aubio estimate rounded to an integer, with possible octave errors (70 vs 140; `fold()` halves or doubles into 70-180) and errors of about +-1-2%. A decimal target on a wrong base is false precision. The user corrects BPM in the Edit dialog; a decimal field only helps when the base value is itself right.

## UX proposal

Playback screen control (**proposed** placement; see question D):

- Target BPM number input, step 0.1, showing the song's BPM as placeholder or label.
- Speed readout, e.g. `x1.058, +5.8%`.
- Reset button (back to x1.000 and the song's own BPM).
- Slider, e.g. +-20% around the song's BPM; moving it updates the input and the readout.
- Beyond +-15% a small warning "Quality drops at this speed".
- Clamp the rate to 0.5x..2x.
- Mini-player badge `x1.06` when the rate is not 1; click opens the control.

Scope (**proposed**, see question B): per session, not persisted per song, reset to 1 on app reload. Options: remember per song; a global "Keep tempo across songs" mode where one target BPM applies to every song, so all songs play at the same BPM (songs without BPM stay at x1).

Effects:

- **Scrubber, duration, time labels:** the media timeline is in media seconds; displayed remaining time and duration scale by 1/rate (`duration / rate`); the scrubber stays proportional (PLY-120..122 keep working on media time).
- **Media Session:** `setPositionState` already passes `playbackRate: audio.playbackRate` (`web/js/player-media.js`); keep it in step on every rate change.
- **Visualizer (task-0023):** unaffected, it reads the analyser output of the already-stretched sound.
- **Loudness normalisation (task-0020):** unaffected, gain is per song and independent of speed.
- **Queue auto-advance:** unchanged; with the global mode the target BPM is reapplied to the next song, with the per-song or session mode it resets to that song's own BPM or x1 (see B).
- **Guest mode:** allowed; a local playback setting, no server write.
- **Keyboard shortcuts** (**proposed**, off in inputs and dialogs as PLY-090): `[` and `]` step -/+0.1 BPM, `\` resets.
- **Accessibility:** labelled input ("Target BPM"), slider with `aria-valuetext` such as "132.3 BPM, speed 1.058, plus 5.8 percent", readout in an `aria-live="polite"` region updated on commit (not on every drag tick), badge has an accessible name. `prefers-reduced-motion`: not applicable.

## Technical notes

- `playbackRate` limits differ by browser; Chrome and Firefox accept about 0.0625..16, Safari mutes or stalls outside about 0.5..2. Clamp to 0.5..2 (above).
- `preservesPitch` is true by default in current browsers; set it explicitly, including `webkitPreservesPitch` for older Safari, and `mozPreservesPitch` is not needed (Firefox follows the standard property).
- **Rate resets on `src` change:** the element returns to its default rate on a new load. Reapply the target on every new song (on `loadedmetadata`, and again on `play`).
- **Web Audio routing:** with `createMediaElementSource` (task-0023 and task-0020 graph) the element's `playbackRate` still applies before the graph; no extra node is needed for level 1.
- **Seek accuracy:** seeking uses media time and is not affected, but `currentTime` per wall-clock second moves by `rate`; time labels must divide by it.
- **Buffering:** a high rate on a slow link can outrun the buffer (stalls); streaming over the tunnel is the case to test; downloaded files are unaffected.
- **Battery:** the browser's own time-stretch is cheap; WASM level 2 costs CPU and must pass the task-0023 budget style (below 8% on a mid-range phone).
- **Safari quirks:** pitch preservation on iOS Safari can introduce a short glitch when the rate changes mid-play; test background and lock-screen playback; if it breaks, the feature stays off there (playback reliability beats features).
- **BPM source:** a song with `bpm` null has nothing to divide by: the control is disabled with a hint "Add a BPM in Edit to change tempo".

## Phases and acceptance

### Phase 1 (level 1, web)

- [ ] Rate maths: `rate = target / bpm`, clamped 0.5..2; null, 0, negative or NaN BPM or target leave the rate at 1.
- [ ] `preservesPitch` set; pitch audibly unchanged at +-10%.
- [ ] Rate is reapplied on every new song and survives pause, seek and queue advance.
- [ ] Target input (step 0.1), slider, readout, reset, mini-player badge work and are keyboard operable.
- [ ] Duration and time labels show scaled time; scrubber still seeks correctly.
- [ ] Media Session position state matches the rate; lock-screen scrubber stays right.
- [ ] Control disabled for songs without BPM; works in guest mode.
- [ ] Warning shown beyond +-15%; no crash or silence at the clamps.
- [ ] Playback unchanged when the control is untouched (rate 1, no extra nodes).
- [ ] `scripts/check.sh` and web `*.test.mjs` pass.

### Phase 2 (decimal BPM storage), only if question A says yes

- [ ] Data model, API validation, load normalisation, Edit dialog; whole numbers still shown elsewhere.

Not in scope now; each gets its own task when started.

## Tests

- Pure rate maths (`web/js/tempo.test.mjs`): `target/bpm`, clamping at 0.5 and 2, rounding of the readout (`x1.058`, `+5.8%`, negative `-5.8%`), null, 0, negative, NaN and string BPM or target, target equal to BPM gives x1.000 and "0.0%", 125.1 -> 132.3 gives 1.0576.
- Formatting: readout, `aria-valuetext`, scaled duration and remaining time (`duration / rate`).
- DOM-shim smoke with a fake audio element: rate set, `preservesPitch` set, reapplied after a `src` change and `loadedmetadata`, reset restores 1, disabled state for null BPM, badge appears and disappears.
- Persistence: per-session value not stored; if per-song or global mode is chosen, saved and restored through `storage.js` with a safe fallback on bad stored values.
- Media Session: `setPositionState` receives the current rate.

## Risks

- **Audio quality:** time-stretch artefacts beyond about +-15% (level 1); users blame the app, hence the warning.
- **Wrong base BPM:** an octave error (70 vs 140) or a +-2% detection error makes "match to 132.3" inaccurate; the control only reads the stored value.
- **False precision:** a decimal target on an integer-rounded or mis-detected BPM.
- **Safari and iOS quirks:** rate limits, glitches on rate change, behaviour on the lock screen.
- **Graph interplay:** levels 2 and later share one `AudioContext` graph with task-0023 and task-0020; design the singleton once ([task-0023](task-0023.md) `audio-graph.js`).
- **Playback beats features:** if any device shows playback regressions, the control is hidden there.
