# Development speed: parity policy, test tiers, release friction

> Alex (2026-10-27): what slows feature development, and what would speed it up?

Analysis and plan only; nothing is decided or built. Related: [task-0122](task-0122.md) (F3 shared fixtures, F7 and F10 legacy API), [task-0121](task-0121.md) (test runner).

## A. What slows development (observed 2026-10-26 and 27)

1. **Every feature is built two or three times.** Web, iOS and Mac are hand ports of each other (F3 of task-0122). The iOS app is about 25,200 lines of Swift (`find ios -name '*.swift'`, 2026-10-27) against 1,840 lines of Swift tests. iOS still lacks Add album, link/unlink and the release-type chips.
2. **Shipped iOS builds freeze the server API.** There is no minimum-version or force-upgrade mechanism (a grep of `server/app` and `ios/Sources` finds none). `server/app/credits.py` (API-149) keeps the flat legacy credit names because builds 20261034 and 20261035 still send them, so F7 and half of F10 of task-0122 wait for an iOS release that every phone must install.
3. **Releases are manual and local.** No `.github/` and no CI ([ci-cd.md](../tech/ci-cd.md), "This project"). `scripts/deploy.sh` runs over SSH to `claude@192.168.0.10`, which works only from the home network (blocked on 2026-10-27). TestFlight upload is a manual `xcodebuild archive`. There is no device automation, so iOS work ends "built, not run on a device".
4. **Slow, load-sensitive tests.** `scripts/check.sh` runs `node --test` once per file in a serial loop over 270 files (`web/js/*.test.mjs`), then the server suite (1,994 test functions in 131 files, no `pytest-xdist`, no markers, no pytest config). Measured 2026-10-27 on 8 cores at a load average above 300 (other sessions running): `node --test web/js/*.test.mjs` took 128 s for 3,054 tests and 2 failed, both on elapsed time: `genre-layout.test.mjs:75` (full run took 27.6 s against its bound) and `viz-bars-baseline.test.mjs:424` (34 ms per frame). Absolute-time assertions also sit in `server/tests/test_regex_backtracking.py` (`< 1` s) and `credits-regex.test.mjs:100` (`< 1500` ms). The server's "about 5 minutes" and the web's "about 85 s" are Alex's observations on a quieter machine; this task did not re-measure them there.
5. **Committed `web/dist` causes churn.** `web/dist` is 15 files, 1.0 MB, and `scripts/check.sh` fails when it is stale. Since 2026-10-13: 110 of 1,038 commits touch `web/dist`, 12 are dedicated "rebuild dist" commits. Any two branches that touch web code conflict in generated chunk files.
6. **Spec rule IDs collide.** Parallel agents each picked the next free `IOS-nnn` by reading the file and chose IOS-104 to IOS-106 together. `scripts/check.sh` already fails on duplicate IDs (lines 37-43) but only after the fact; nothing allocates.
7. **JSON in git races with the server's own sync commits.** Whole-file rewrites of `audioplayer/*.json` while the server timer commits and pushes the same repo. STO-035, STO-057 and STO-061 already fast-forward or rebase foreign commits outside the owned paths; a GitHub-side change to an owned path still stops sync with "diverged" and is fixed by hand (memory note "Data repo pushes can diverge sync").
8. **Smaller.** `web/js` is one flat folder: 308 non-test modules and 278 `.mjs` files (270 tests plus helpers); large closures in the web (task-0122 F8); one shared checkout used by several sessions (the CLAUDE.md rules for it cost attention).

## B. Proposed fixes (phased; effort S/M/L, risk low/med/high)

### Phase 1: policy and tiny scripts (S, low)

- **P1.1 Rule ID allocator.** `scripts/next-rule-id.mjs IOS` prints the next free ID (max over `docs/specs/*.md`, plus a reservation file `docs/specs/.reserved-ids` appended under a lock so two agents in one checkout never get the same number). Across worktrees the existing duplicate check stays the backstop. Agent briefs say "call the script, never count by eye".
- **P1.2 Parity policy.** New features are web-first. iOS gets only what the key principle needs (download, store, play offline, lock screen). Everything else goes on an explicit SKIP list in `docs/specs/ios.md` (rule IDs marked `SKIP-IOS` with a reason), so "iOS lacks X" stops being a backlog and becomes a decision. Add album, link/unlink and release-type chips are the first candidates for that list or for a clients-render-only design (P2.1).
- **P1.3 Parity gap table.** One table (feature, web, iOS, Mac, decision) in `docs/specs/ios.md`, so a missing port is visible in one place.

### Phase 2: less to port (M, low to med)

- **P2.1 Logic on the server where the phone is online anyway.** Matching, parsing, album candidates, stats and the genre layout move behind API endpoints that return render-ready data. Clients only render. Fits catalog features (the web is catalog-only, ADR-0010) and shrinks the Swift ports. Does not apply to anything the key principle needs offline.
- **P2.2 Shared pure-logic modules through JavaScriptCore.** `tokens.js`, `credits.js`, `url-clean.js` run in iOS and Mac via `JSContext`, replacing hand ports, only for logic needed offline. Trade-offs: a bridge layer to write and test (Swift types to JS values), a build step that bundles the JS into the app target, a bundle size increase, the JS must stay free of DOM and `import` of browser APIs, and debugging crosses a language boundary. Worth it only for modules with many shared cases; tokens, url-clean and credit titles qualify, the Genres map does not.
- **P2.3 Keep shared fixtures** (`server/tests/fixtures/*_cases.json`, F3 step 1, IOS-108). They are the cheap parity guarantee while P2.1 and P2.2 are partial.

### Phase 3: test speed (M, low)

- **P3.1 Tiers.** Fast tier on every change: only the test files whose module changed (a `scripts/check-fast.sh` mapping `web/js/x.js` to `x*.test.mjs`, and `pytest` on the changed server modules' tests), a few seconds. Full suite before deploy and nightly (local `launchd` or the server timer), not on every edit.
- **P3.2 Server.** `pytest-xdist` (`-n auto`) in `requirements-dev.txt`, a `slow` marker for the heavy files with `-m "not slow"` as the fast tier. First check test isolation (shared temp dirs, git-sync tests, ports) before enabling `-n`.
- **P3.3 Web.** Replace the serial per-file loop in `scripts/check.sh` with one `node --test` invocation over all files (the runner already isolates per file and runs them in parallel, `--test-concurrency`), keeping the "no tests in file" and failure-listing behaviour. `--test-isolation=none` (one shared process) was tried once on 2026-10-27 and was still running after more than 4 minutes under load because of an 86 s fake-time test; do not adopt without fixing shared state first.
- **P3.4 Timing tests.** Assert ratios or counts instead of absolute time: compare the slow input to a baseline input of the same test (backtracking is quadratic or not regardless of machine load), or count operations. Tests that only guard performance move to the slow tier.
- **Not recommended: turning tests off for a period.** The 2026-10-20 "no tests" rule exists and tests were run on 2026-10-26 by permission; whether to suspend them is Alex's policy decision, and this task advises against it: the tiers above get most of the speed without losing the safety net.

### Phase 4: release friction (M to L, med)

- **P4.1 Minimum supported iOS version.** The app sends its build number (`X-App-Build` header or the existing sign-in call). The server holds `MIN_IOS_BUILD`; below it, endpoints answer `426` with a stable body and the app shows "Update required" (TestFlight link). Offline playback keeps working (the key principle). Once builds 20261034 and 20261035 are below the minimum, F7 and F10 of task-0122 can finish. Needs one TestFlight build to carry the sender, so ship it first.
- **P4.2 A reachable deploy path.** Options: (a) a Cloudflare Access SSH tunnel or a pull-based deploy (the server polls `origin/main` for a signed tag and runs `audioplayer-deploy`), (b) a self-hosted runner on `perkunas`, (c) GitHub Actions `workflow_dispatch` calling the tunnel. Choose by who must be able to deploy (only Alex's Mac, or any session anywhere). The current Actions budget policy (manual workflows only, [ci-cd.md](../tech/ci-cd.md)) argues for (a) or (b).
- **P4.3 Device verification.** A small XCUITest smoke run on the simulator in the release checklist (launch, sign in as a test user, play a bundled file); a real device stays a manual step for background audio and lock screen.
- **P4.4 `web/dist` churn.** Options: (a) stop committing `dist` and build it in `audioplayer-deploy` (removes conflicts; the server then needs Node and esbuild, or the deploy builds on the Mac and syncs the artifact, not through git); (b) keep committing but mark `web/dist/**` as `-diff merge=ours` in `.gitattributes` and rebuild once per merge by a script; (c) only rebuild in the deploy commit. (a) is the cleanest; (b) is a one-line change to try first.
- **P4.5 Data repo.** Writes to `audioplayer/*.json` from outside the server go through the API or a pull-then-write script that refuses on a dirty or diverged tree; nothing hand-pushes owned paths.

## C. Recommendation

Order by speed gained per effort:

1. **P1.1 allocator** and **P3.3 single `node --test`** plus **P3.4 ratio assertions**: a day, no risk, removes two recurring annoyances (ID collisions, load-flaky failures).
2. **P3.1 and P3.2 tiers and xdist**: the biggest day-to-day gain (seconds instead of minutes per change).
3. **P4.1 minimum version**: ship one iOS build with the sender; it unlocks the legacy removal that has been waiting for a minimum build.
4. **P1.2 and P1.3 parity policy**: a decision more than work; it prevents building a feature three times by default.
5. **P4.2 deploy path** next time SSH is blocked again, and **P4.4(b)** for `dist`.
6. **P2.1** per feature as it comes up; **P2.2 JavaScriptCore** only after fixtures show which modules keep drifting.

### What not to do

- Do not suspend tests for a period; tier them.
- Do not adopt `--test-isolation=none` or `pytest -n` before checking shared state (temp dirs, global stubs, git-sync tests).
- Do not rewrite the web in a cross-platform framework or ship a full JS engine for the whole app to get parity; the audit (task-0122) found no case for a broad refactor.
- Do not share the Genres map or visualizer code with iOS through JavaScriptCore; they are large, UI-bound and not needed offline.
- Do not remove committed `web/dist` before the deploy can build it.
- Do not add CI that runs on every push; the $0 Actions budget policy stands.
