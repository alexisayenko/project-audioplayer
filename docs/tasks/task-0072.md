# Studio: a page to work on a track: waveform, A-B loop and saved loops

> Alex (2026-10-20, DD1, DE2): a new main-menu item named **Studio** where tracks are worked on ("dissected"). First version: a waveform of the song that is playing, a marked region A-B, a loop on/off, and named loops saved on the song. Example use: the Free Bird solo, A at the start of the solo, B 15 s later.

## Scope (first version)

- Nav: `Studio` between Song stats and Help (`#/studio`, lazy tier-2 route, new `studio` icon: five vertical bars of different heights). Page head "Studio", tagline "Work on a track: loop a section, mark it, keep it." Empty state "Play a song to open it in the Studio." with a Library button.
- Waveform of the current song (canvas, retina aware, light and dark tokens) with a playhead; click to seek.
- Region A-B: drag handles (keyboard: arrows 0.1 s, Shift 1 s), "Set A here" and "Set B here" (take the play position), mm:ss.s fields with -1 s, -0.1 s, +0.1 s, +1 s nudges.
- Loop on/off: while on, playback jumps back to A when it reaches B. The state lives in the player (`player.loop`), so it survives page changes; the dock shows an inline "Loop A-B" chip with an off button (WEB-115) while active; a song change clears it.
- Saved loops: per-song list `loops: [{name, start, end}]` (seconds; start < end <= duration, max 20 per song, name up to 40 characters, default "Loop 1", "Loop 2", ...). Chips under the waveform: click selects the region and starts looping; rename inline; delete. Stored with the song in the user's library (optional field, no migration, git-synced by the normal save path). Guests and signed-out visitors can use the waveform and the A-B loop on public audio but cannot save: no save buttons and the inline note "Sign in to save loops".
- Waveform data: the server computes a compact peaks array with ffmpeg (already used by `bpm.py`) on the first request, caches it beside the audio outside every git-synced tree, and serves it at `GET /songs/{id}/peaks` with an ETag (API-195). Without a usable server peaks route the client decodes the file with `decodeAudioData` only when it is small (under 12 MB). While it prepares: "Preparing waveform..."; when nothing works: "Waveform unavailable" and a plain timeline slider so A-B still works. Playback is never blocked.

## Wide screens

The Studio page drops the 1100px main cap (`body[data-route="studio"] main`) and fills the page area; the waveform height is `clamp(140px, 22vh, 260px)` and `wavePaint` reads the real element height and width, observed by a `ResizeObserver` (WEB-156). Not run, not seen.

## Decisions

- Loop accuracy (superseded 2026-10-21 by [task-0077](task-0077.md): a buffer-based gapless loop now plays when the file can be decoded; the timer engine below is the fallback and keeps the element in step): no sample-accurate engine. A timer scheduled just before B (lookahead 25 ms, re-armed on play, seek, rate change and `timeupdate`) seeks to A on the `<audio>` element. The gap is the decoder's seek time; limits and measurements are in PLY-160 and WEB-152. In a hidden tab or with the screen locked the browser throttles timers (about 1 s), so the loop can overshoot B by up to that much there; the Studio is a foreground tool.
- Peaks: 1200 min/max pairs, 8-bit signed, from mono 8 kHz PCM; cached as `<audio dir>/.peaks/<id>.<size>-<mtime>.json` (the audio pool is outside the git-synced data and covers repos). Route auth is the same as `/files` (guests only for public audio) and it is on the guest allow-list. No ffmpeg: 503 `peaks_unavailable` and the client falls back.
- Loops are replaced as a whole list by `PATCH /songs/{id}` (`loops`), validated on the server; `end` may exceed the stored `duration` by at most 1 s because durations are stored rounded.
- Phone tab bar: with Studio there are eight entries. Below 400 px they no longer fit at 44 px with the 4 px gaps, so the bar drops its gaps and side padding there (8 x 44 = 352 px fits 360 px); the targets stay 44 px.
