# Countries back on songs, Artist table removed (data model v3)

> Alex: countries stay associated with songs; no table per fact. A song may have several countries.

Decision: [ADR-0031](../tech/decisions.md). Rules: DATA-147, DATA-148, DATA-157 to DATA-160 and DATA-164 to DATA-166 in [data-model.md](../specs/data-model.md), TAG-098, API-147. Builds on [task-0043](task-0043.md) (data model v2, deployed), which it partly reverses. Deploy: [deploy.md](../tech/deploy.md#data-model-v3-migration-countries-back-on-songs).

## Done

1. `country:<iso2>` tags are stored on the song again, any number of them; the tags view returns the stored countries plus the computed `decade:`.
2. `artist_table.py`, `routes/artists.py`, the `artists` key of `library.json` and of `GET /library`, `GET /artists`, `PATCH /artists/{name}` and the 422 rule for countries on a song with several main artists are removed; PATCH and POST treat country tags like any other tag.
3. `app.migrate_model3` (startup after `migrate_model2`; CLI dry run by default): restores each song's countries from the table or from `backups-model2/<uid>/library.json`, drops the table, sets `credits_schema: 3`.
4. Web: the Countries chip field takes several countries.
5. Tests: `test_migrate_model3.py`, the rewritten `test_artist_table.py`, the iOS contract test.

## Open

- Deploy and verify on the live library (order in deploy.md).
- A MusicBrainz or Wikipedia lookup keeps suggesting one country; a "suggest all" is not planned.
