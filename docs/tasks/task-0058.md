## Data model

A playlist is an object:

- `id` (server generated, opaque: `pl_` plus 8 random characters), `name` (1 to 120 characters, trimmed, unique per user case-insensitively; 409 `playlist_name_taken`, the UI suggests "Name (2)"), optional `description` (at most 1000 characters), `created`, `updated`.
- `songs`: an **ordered list of song ids** (the song's own library id: a YouTube id, `soundcloud-<n>`, or a `spotify-`, `applemusic-`, `shazam-` id). There is no `entryId` and no `addedAt`. A playlist **references** songs by id and never copies song data, so title, artist and cover edits show up in every playlist.
- A song id appears at most once in a playlist; a second add is ignored and reported as skipped (the web shows the toast "Already in the playlist").
- The cover is derived by the client from the first song and is not stored.

**No hierarchy:** no folders, no nested playlists, no `parent` field. The playlists of a user form one flat list, ordered by name, A to Z (no manual order).

## Proposed behaviour

### Playlists page

- The sidebar item "Playlists" (a placeholder today) opens a page listing the user's playlists: name, song count, cover, last change.
- Create, rename and delete a playlist. Delete asks for confirmation and offers an undo toast.
- Opening a playlist shows its ordered songs as Library-like rows (cover, title, artist, duration, audio state); the web joins the song ids with its library store.
- Reorder songs by drag and drop and by keyboard (focus a row, move with Alt+Up / Alt+Down); the final order is sent once.
- Remove a song from the playlist (the song stays in the library).
- Actions on a playlist: Play all, Add all to the queue, Shuffle, Export as text.

### Add to playlist

- An "Add to playlist" action on the song card and on Library rows opens a menu listing the playlists plus "New playlist...". A playlist that already holds the song is marked.

### Naming clash with the queue

The existing toggle on the song card and on rows, labelled "Add to playlist" / "In playlist", actually controls the **play queue** (LIB-012). This task resolves the clash: rename the queue toggle to "Add to queue" / "In queue", and use the word "playlist" only for saved playlists (decision D).

### Songs removed from the library

A song deleted from the library is removed from every playlist of that user in the same transaction (decision B). Ids that are not in the library are also dropped on read.

### Text export

`GET /playlists/{id}/export` returns a text file: one line per song in the playlist's order, `Artists - Title (Version) - m:ss`. `Artists` are the main artists joined with `, `; ` (Version)` appears only when the song has a version (as stored, e.g. `Liquid Soul rmx`); the length is `m:ss` (`h:mm:ss` from one hour) and the whole ` - length` part is left out when the duration is unknown. Lines end with a newline; no header; songs no longer in the library are skipped. The file is `<playlist name>.txt` (PLS-118, PLS-119, API-237).

### Visibility

Playlists are private to their user. The public read-only view (ADR-0018) never shows them, and guests and anonymous callers cannot read or create them (401).

## Storage and API

- Server side, per user, in its own file `users/<uid>/playlists.json` (DATA-199), written through the same atomic, git-synced mechanism as `drafts.json` and `genre_layout.json`. One commit per change; reorders are one write (the client sends the final order once, not one request per drag step).
- Caps (for non-owners; the owner is exempt as elsewhere): 200 playlists per user, 2000 songs per playlist (decision E), 422 with the project's error shape. Playlists do not count toward library quotas (DATA-112).
- API (API-229 to API-238):
  - `GET /playlists` (`{playlists: [{id, name, description, count, first_song_id, updated}]}`, by name), `POST /playlists` (`{name, description?, song_ids?}`, 201)
  - `GET /playlists/{id}` (`{id, name, description, created, updated, songs: [song_id]}`), `PATCH /playlists/{id}` (name, description), `DELETE /playlists/{id}`
  - `POST /playlists/{id}/songs` (`{song_ids}`; appends in order; answers `{added, skipped}`)
  - `DELETE /playlists/{id}/songs/{song_id}`
  - `PUT /playlists/{id}/order` (`{song_ids}`, exactly a permutation of the current songs, else 422 `bad_order`)
  - `GET /playlists/{id}/export` (text)
- Audio availability is not a playlist concern: a playlist row follows the song's own state (none / server / phone).

## Decisions (all recommendations confirmed by Alex, 2026-10-24)

- A. Duplicates inside one playlist: not allowed, a second add is ignored with a toast "Already in the playlist".
- B. A song removed from the library: it is removed from every playlist at the same time.
- C. Order of the playlists themselves: by name, A to Z, no manual order for now.
- D. Naming of the queue toggle: "Add to queue" / "In queue"; "playlist" is reserved for saved playlists.
- E. Maximum sizes: 200 playlists per user and 2000 songs per playlist; the owner is exempt.
- F. "Save queue as playlist": a button in the queue that creates a playlist from the current queue, in phase 3.
