This task is the **flat first slice** of it and the one to build: no folders, no nesting, no import. It narrows phase 1 of task-0034 (the `playlists.json` store, the API, the page, the row picker, the "Add to queue" rename, "Save queue as playlist", Play / Shuffle / Add to queue). Folders, import, export, smart playlists and sharing stay in task-0034 and return after this one ships. When phase 1 below starts, the spec and ADR-0022 are amended to the flat model (their folder tree, PLS folder items and the 200-node cap are dropped for now).

## Data model

A playlist is an object:

- `id` (stable, server generated), `name`, optional `description`, `createdAt`, `updatedAt`.
- `songs`: an ordered list of entries `{entryId, songId, addedAt}`. An entry **references** a song by its id; it never copies the song's data, so title, artist and cover edits show up in every playlist.
- Optional cover: the cover of the first song (derived, not stored).
- The same song may appear once or several times; recommended once (open question A). The `entryId` identifies a position-independent entry so remove and reorder stay unambiguous even if duplicates are allowed later.

**No hierarchy:** no folders, no nested playlists, no `parent` field. The playlists of a user form one flat list. Their own order is by name or manual (open question C).

## Proposed behaviour

### Playlists page

- The sidebar item "Playlists" (a placeholder today) opens a page listing the user's playlists: name, song count, cover, last change.
- Create, rename and delete a playlist. Delete asks for confirmation and offers an undo toast.
- Opening a playlist shows its ordered songs as Library-like rows (cover, title, artist, duration, audio state).
- Reorder songs by drag and drop and by keyboard (focus a row, move with Alt+Up / Alt+Down).
- Remove a song from the playlist (the song stays in the library).
- Actions on a playlist: Play all, Shuffle, Add all to the queue.

### Add to playlist

- An "Add to playlist" action on the song card and on Library rows opens a menu listing the playlists plus "New playlist...". A playlist that already holds the song is marked.

### Naming clash with the queue

The existing toggle on the song card and on rows, labelled "Add to playlist" / "In playlist", actually controls the **play queue** (LIB-012). This task resolves the clash: rename the queue toggle to "Add to queue" / "In queue", and use the word "playlist" only for saved playlists (open question D).

### Songs removed from the library

A song deleted from the library disappears from playlists, or is shown as unavailable (open question B).

### Visibility

Playlists are private to their user. The public read-only view (ADR-0018) never shows them, and guests cannot create them.

## Storage and API

- Server side, per user, in its own file `users/<uid>/playlists.json`, written through the same atomic, git-synced mechanism as `drafts.json`. One commit per change; reorders are batched (the client sends the final order once, not one request per drag step).
- Caps (for non-owners; the owner is exempt as elsewhere): 200 playlists per user, 2000 songs per playlist (open question E).
- API sketch:
  - `GET /playlists`, `POST /playlists`
  - `GET /playlists/{id}`, `PATCH /playlists/{id}` (name, description), `DELETE /playlists/{id}`
  - `POST /playlists/{id}/songs` (add one or several song ids)
  - `DELETE /playlists/{id}/songs/{entryId}`
  - `PUT /playlists/{id}/order` (the full ordered list of entry ids)
- Audio availability is not a playlist concern: a playlist row follows the song's own state (none / server / phone).

## iOS and Mac

Later (phase 4). The app reads playlists through the same API; offline availability of a playlist's songs follows each song's state (a playlist does not download anything by itself). Editing `ios/` needs Alex's permission.

## Out of scope

## Open questions

- A. Duplicates inside one playlist: not allowed, a second add is ignored with a toast "Already in the playlist". **Recommended.**
- B. A song removed from the library: it is removed from every playlist at the same time. **Recommended.** (Alternative: keep the entry and show it greyed out as unavailable.)
- C. Order of the playlists themselves: by name, A to Z, no manual order for now. **Recommended.** (Alternative: manual drag order.)
- D. Naming of the queue toggle: "Add to queue" / "In queue"; "playlist" is reserved for saved playlists. **Recommended.**
- E. Maximum sizes: 200 playlists per user and 2000 songs per playlist; the owner is exempt. **Recommended.**
- F. "Save queue as playlist": a button in the queue that creates a playlist from the current queue. **Recommended**, in phase 3.
