# Studio Tools on iOS

> Alex (2026-10-24): "don't do them on iOS app yet"; later the same day, lifting the hold: "add bpm meter to iOS; create another menu, call it Tools".

Started 2026-10-24. Follow-up of [task-0106](task-0106.md). Live BPM and the Tools screen are built (source only, not run on a device, not uploaded to TestFlight); the other tools are not.

## What is built

- Drawer entry "Tools" (SF Symbol `wrench.and.screwdriver`) between Statistics and Settings, opening `ToolsView.swift` (a root screen like Statistics; open question A is settled: a drawer entry, Settings stays untouched). The screen is a list of cards; the first is "Live BPM (microphone)", with room for the next ones.
- Live BPM card: Start/Stop, a large BPM badge ("- - -" when idle or silent; one decimal up to and including 200 BPM, integer above), a level meter, a state line (listening, silent, denied, stopped reasons) and the hint "Hears the phone speaker through the microphone. Not headphones."
- `LiveBPM.swift`: Swift port of the web engine (`web/js/live-bpm.js`, `mic-bpm.js`, `bpm-label.js`): same constants and steps (400 Hz onset envelope, 6 s window plus 3 s short window, octave-aware agreement, publish every 0.5 s, median of 3, silence at RMS < 0.002 for 1.5 s, range 30-1200 BPM). Foundation only, so it is testable on its own and portable.
- `MicBPMModel.swift`: `AVAudioEngine` input tap (mono), filters and estimate on a private queue. Session `.playAndRecord` / `.measurement` / `[.mixWithOthers, .defaultToSpeaker]`. Stop restores the player's session (`PlatformAudio.restorePlayback`): kept active while a song plays, otherwise deactivated with `notifyOthersOnDeactivation`. It stops on Stop, when the Tools screen is left, when the app goes to the background, on an interruption, on a route change (after a 1.5 s grace) and after 10 minutes.
- Microphone permission through `AVAudioApplication`; denied shows a message and an "Open Settings" button. `NSMicrophoneUsageDescription` is in `ios/project.yml`.
- The Mac target does not include any of this (it shows the web GUI); both schemes build.

## Not verified

No device run: the real microphone, a real speaker with music, the permission prompt, the session restore against background playback, and interruptions are untested. The Swift engine has no unit tests (owner rule: no tests run) and has not been compared with the web engine on the same input.

## Facts to keep

- Limit: the microphone hears the phone speaker only, not headphones or Bluetooth. iOS cannot capture another app's internal audio without a screen-recording broadcast extension.
- Editing `ios/` for this work is permitted by the owner (2026-10-24); the existing Settings screen and its Library-card tools stay unchanged.

## Mac app

The Mac app shows the web GUI, so the web Analyze tab needs the microphone there: the entitlement `com.apple.security.device.audio-input`, `NSMicrophoneUsageDescription`, and a `WKUIDelegate` media-capture permission handler in the web view. Without the handler the Analyze tab cannot open the microphone in the Mac app. Not done.
