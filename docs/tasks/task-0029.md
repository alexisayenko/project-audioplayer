# Demucs stems for Terrain parts

Planned. Due Thu 2026-10-15: decide the next step (test on a real song, then go or no-go on the pipeline).

## Goal

Per-part timelines from real stem separation, so Terrain shows vocals, piano, drums and bass each in its own height and colour, with the beats as the canvas. Concept: [terrain-concept.md](../specs/terrain-concept.md).

## What exists

- Demucs 4.1.0 with torch 2.14.1 (CPU) installed in `/home/claude/demucs-env` on the server LXC `tools`.
- Benchmark: [demucs-benchmark.md](../tech/demucs-benchmark.md). About 5x real time on 2 cores with `htdemucs`; the 6-stem variant measured about 2x, unexplained; about 1.3 GB RAM while running; 1.1 GB env plus 133 MB of models on disk.

## Open decisions

- Test stems on a real library song first and look at the result in Terrain before building anything.
- Pipeline: background job, one at a time, `nice -n 19`, hard timeout, cache per song id and model.
- Per-part timeline format, similar to the lookahead timeline Terrain already uses.
- API to fetch the per-part timeline.
- Quotas: who may trigger separation (owner only, or users within quota), and how much cache per user.

## Risks

- CPU time per song on a 2-core LXC shared with the server; a long queue delays everything else.
- Quality is uneven: vocals are strong, piano is so-so.
- The frame governor is JS-only, so extra per-part data must not cost frame time on the web side.
