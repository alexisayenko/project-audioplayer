# Speed up saving songs (git store)

Everything marked **(proposed)** is a suggestion; Alex has not decided it. See [Open questions](#open-questions-for-alex). Related: [ADR-0005](../tech/decisions.md#adr-0005-library-metadata-lives-in-the-data-storage-git-repos), [storage-and-sync](../specs/storage-and-sync.md), [deploy.md](../tech/deploy.md).

## Problem

Every save (add, edit, delete, tag change) runs, synchronously and inside the git lock (`server/app/gitstore.py`: `transaction()` -> `pull()`, then `commit()` -> `_push_all()`): `git pull --rebase`, write, commit and `git push` for BOTH data repos (library and covers). Over SSH to GitHub this takes up to ~10 s; the request waits and every other writer waits on the lock. Playback is unaffected, but the UI feels stuck on Save.

## Options

| # | Option | Gain | Trade-off |
|---|--------|------|-----------|
| 1 | Background push: save commits locally and returns; a worker pushes, debounced ~3 s, coalesced | Removes the push (the bulk) from the request | Unpushed window; needs a "sync pending" status (the retry loop and `status()` already exist) |
| 2 | Skip the pull on every save; pull at startup, periodically, and when a push is rejected (single writer) | Removes a network round trip per save | Breaks if anything else writes the repos (manual edit, second host); a rejected push then needs a rebase |
| 3 | Touch the covers repo only when a cover changed | Halves the git work for ordinary edits | Small code change in `commit()`: per-repo dirty check |
| 4 | SSH `ControlMaster`/`ControlPersist` connection reuse | Saves the ~1-2 s SSH handshake per git call | Ops config only; a stale socket needs cleanup |
| 5 | Coalesce commits for rapid edits (one commit per burst) | Fewer commits and pushes during bulk edits | Coarser history |
| 6 | Push both repos in parallel | Cuts push time to the slower repo | Moot if 1 or 3 is done |
| 7 | Live file on disk + periodic git snapshot (design change) | Instant saves, git only as backup | Loses per-save history; changes ADR-0005 semantics |
| 8 | GitHub contents API instead of a git clone | No local clone | Rewrite of the store, API limits, no LFS parity; worst fit |

## Recommended bundle (proposed): 1 + 2 + 3 + 4

Target: a save returns in under 1 s; no behaviour change except a visible "sync pending" window. Options 5 and 6 come for free or are moot (1 coalesces; 3 removes most second pushes); 7 and 8 are rejected unless the DB direction below is taken.

## Design details (proposed)

- **Lock rules**: one lock guards the working tree. `transaction()` takes it, writes, commits locally, releases it. The pull/rebase takes the same lock (never concurrent with a save). The push runs OUTSIDE the lock: it only reads committed history, and a save landing meanwhile is just another commit for the next round.
- **Push worker**: a single thread; a save sets a "dirty" event; the worker waits ~3 s after the last event (debounce), then pushes each repo that has unpushed commits. Failure keeps the existing backoff (`_retry_loop`).
- **Pull**: at startup (existing `resync()`), then every N minutes (e.g. 10) under the lock, and on a rejected push (pull --rebase under the lock, then push again). No pull inside `transaction()`.
- **Covers**: `commit()` stages and pushes a repo only if it has changes.
- **Shutdown flush**: `stop()` pushes pending commits (bounded timeout) before exit; on a crash the commits stay local and `resync()` pushes them at the next start.
- **Status**: `status()` already returns ok/pending/error; surface `pending` in `/health` and the existing sync banner in the UI (pending = unpushed commits exist, error = retries keep failing).
- **Risk window**: edits not yet pushed exist only on the LXC disk (the same disk that holds the audio). The window is ~3 s plus retry time; nothing is lost on a normal restart.
- **SSH**: in the service user's `~/.ssh/config` for `github.com`: `ControlMaster auto`, `ControlPath ~/.ssh/cm-%C`, `ControlPersist 10m`.

## Acceptance criteria

- [ ] Save latency under 1 s with a slow remote (measured, not assumed).
- [ ] Bursts of saves produce one push per repo per debounce window.
- [ ] A failed push is retried with backoff, `/health` shows `pending` then `error`, and recovers to `ok`.
- [ ] Shutdown flushes pending commits; a crash loses nothing after the next start.
- [ ] A rejected push (remote moved) rebases under the lock and succeeds; a rebase conflict is reported and does not corrupt the working tree.
- [ ] Editing a song without a cover change touches only the library repo.
- [ ] The UI banner shows "sync pending" while unpushed commits exist.
- [ ] Concurrent saves from two users never interleave inside the working tree.
- [ ] `cd server && python -m pytest -q` and `scripts/check.sh` pass.

## Tests

Fake slow remote with local bare repos (a wrapper adding a delay to push and pull):

- Save latency is independent of the remote delay.
- Coalescing: N rapid saves give one push per repo.
- Push failure (remote unreachable): pending, then error, then recovery on reconnect.
- Shutdown flush with pending commits; restart with leftover commits.
- Concurrent saves from two users (threads): two commits, consistent files.
- Rebase-conflict path: the remote changed the same file; the result is reported and the tree stays clean.
- Covers only when changed: an edit without a cover leaves the covers repo untouched.

## Risks

- Unpushed edits live on one disk for a few seconds.
- Dropping the per-save pull assumes a single writer; a manual edit of the data repos must be followed by a restart or the periodic pull.
- Rebase conflicts surface later than before (at push time), so the conflict path needs a clear error, not silence.
- Worker-thread bugs (lost wakeups, double push) are hard to see; the tests above cover them.

## Later direction: database

Alex's question (AZ, 2026-10-14): would a database replace the git store?

- **SQLite (WAL)** with a daily JSON export committed to data-storage.
- **Postgres** via the self-hosted Supabase in LXC 103.
- **Stay on git** (this task's speed-ups).

Benefits of a DB: instant saves, real deletion of strangers' personal data (git history keeps it), queries instead of loading `library.json`. Costs: rewrite of `server/app/library.py` and `gitstore.py`, a migration, adapting about 1500 tests, loss of per-save git history. Recommendation: SQLite plus a daily export; it would supersede ADR-0005 (and amend the storage layout of ADR-0012). Decision deferred by Alex ("bigger change, later"). If the DB switch is more than a few weeks away, do the speed-ups above first; if it is close, skip them.
