# Suggest genre, style and year from Discogs in POST /metadata

Add Discogs as a second optional source next to MusicBrainz, per [ADR-0013](../tech/decisions.md#adr-0013-music-database-lookups-musicbrainz-now-discogs-later) (Discogs: Proposed). Discogs returns genres plus finer styles (progressive house, vocal trance), which fits the electronic catalog and fills what community-voted MusicBrainz tags miss.

Depends on: ADR-0013 and the existing MusicBrainz merge (`server/app/genre_lookup.py`, merged in `server/app/metadata.py` `gather`/`merge`). No separate MusicBrainz task: that source is already live (descriptive `User-Agent` from `AUDIO_MB_USER_AGENT`, one request per 1.1 s, per-query cache, silent failure), so nothing is missing there.

Related, separate and already in progress by another agent: the MusicBrainz and Discogs link icons in the song link row (web and iOS). They only link out, with no API call and no token.

## Scope

1. New `server/app/discogs_lookup.py`: search by artist + title (`/database/search`, type `release`), take the best match, read genres, styles and year. Returns suggestions only; nothing is applied server-side.
2. Token: Discogs free personal access token read from a `chmod 600` env file on the server, outside the repo (`~/.config/discogs/token.env`, per the secrets rule), sourced by the service. Never in git, logs, responses or tests. With no token the source is silently off.
3. Request limits: about 60 requests/minute with a token; a per-source limiter below that, a descriptive `User-Agent`, a hard timeout, a per-query cache (same shape as `genre_lookup._cache`).
4. Merge: add Discogs as a source in `metadata.gather`/`merge` with a fixed precedence (decide and document: genres and styles become `genre:` tags through `genre_filter`; year only fills when MusicBrainz and Wikipedia gave none). Runs under the existing 15 s cap and the `AUDIO_TAG_LOOKUP` switch.
5. Terms: use only for genre, style and year suggestions. No image or cover caching, no stored dumps, no bulk reuse of Discogs data. Do not persist Discogs responses beyond the in-memory per-query cache.
6. Failure (no token, 401/429, timeout, no match) is skipped silently and the response equals today's.

## Acceptance criteria

- With a token and a match, `POST /metadata` suggests Discogs genres/styles as `genre:` tags and a year where the others gave none; the user still confirms in the shared song form.
- Without a token, or on any Discogs failure, the response is identical to today's and no error reaches the client.
- Repeated identical queries make one Discogs call; calls never exceed the limiter rate.
- The token never appears in git, logs or API output; the token file is `chmod 600` on the server and the deploy steps say so.
- Playback and offline use do not depend on this source.

## Tests (`server/tests/test_discogs_lookup.py`, extend `test_metadata.py`)

- HTTP is mocked (patch the opener the way `test_genre_lookup.py` does); no network in tests, no real token.
- Cases: match with genres+styles+year; no match; no token; 401; 429; timeout; malformed JSON; cache hit makes one call; limiter spacing; merge precedence; Discogs failure leaves the MusicBrainz/Wikipedia result unchanged.
- `cd server && python -m pytest -q` on Python 3.11+ passes; `scripts/check.sh` passes.
