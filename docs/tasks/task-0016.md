# iOS client for open signup and per-user storage

The server is open to any verified Google or Apple account and keeps one library per user (ADR-0012). The iOS code was inspected, not changed (no Xcode in the cloud sandbox). The app already works for the owner and for any user on the happy path; these are the changes it needs. Paths below are in `ios/Sources/`.

## What already works

- Auth: `APIClient.request` sends `Authorization: Bearer <ID token>`; the server derives the user from the token, so no path, query or header changes. `/files/{id}`, `/covers/{id}`, `/catalog`, `/library`, `/songs*` URLs are unchanged.
- The phone's own `library.json` and `Documents/audio` are local and unrelated to the server layout.
- `APIClient.check` turns a JSON error `{error, detail}` into `APIError.refused(code, detail)`, so the new refusals already show the server's readable `detail`.

## To do

1. Sign-in refusal: a closed signup returns 403 `{"error":"signup_closed"}` on the first call (`APIClient.verify` is `/tags`). `ServerLink.check` only sets `reachable = false`; show "Sign-up is closed on this server." in Settings (`SettingsView`, `AuthService` error slot).
2. Add errors: `AddSheet.save` and `APIClient.addSong` surface `.refused` text; map the new codes in `linkErrorCopy`-style copy so the sheet keeps its form: `hourly_limit` (429, body has `retry_after_minutes`), `library_full_songs`, `library_full_bytes` (403), `server_full` (503). Same texts as the web (`web/js/limits.js` `friendly`).
3. Job status `queued`: `ServerLink.ingest` and `listWhenSaved` poll `GET /songs/{id}/status` until `done` or `error`; `queued` is a new value (progress 0). Keep polling and show "Waiting..." instead of a percentage; raise the 120 x 2 s cap in `listWhenSaved` or fall back to the next catalog sync, because a queued job can wait minutes. A refused job ends as `error` with `code` (`SongStatus` has no `code`; add `var code: String?`).
4. Legacy `POST /download` (`APIClient.download`, `SearchView`) is quota-checked like `POST /songs`: 429/403/503 bodies as in 2.
5. Optional: Settings meter from `GET /me/usage` (`{songs, max_songs, bytes, max_bytes, adds_last_hour, max_adds}`; `max_*` are `null` for the owner) and the email from `GET /me`.
6. Apple tokens without an `email` claim map to the user through the `sub` the server stored at the first sign-in with email; sign in once with an email-bearing token (the first Apple authorization always has it) before relying on it. `AuthService.claims` already reads `email` optionally; nothing to change unless Apple sign-in is used as the very first login after a token without email.
7. Cosmetic: the comment "Owner-only OAuth sign-in" in `AuthService.swift`, and any Settings copy that says "owner".
8. Verify on a device: covers of server songs (`CoverURL.resolve` appends `?token=` only for the API token, which a non-owner does not have) must be fetched with the Bearer header, not with a token in the URL.
