# Song and genre distance: similar songs and a tag-outlier check

> Alex: "Is there a scientific way to formally describe distance between certain music tracks? Genres?" and "based on song distance we could define genres?". Describe it as its own task.

## Why

We have judged genres by hand, row by row, against Wikipedia (90+ removals so far). A formal distance would give a second, independent opinion: which songs look mistagged, which songs are similar, and how far apart two genres really are. It would also let the genre tree be checked against the data instead of only against sources.

## Background (music information retrieval, ISMIR)

- **Audio distance:** MFCC (timbre), chroma (harmony), tempo and rhythm patterns with cosine or Euclidean distance; Gaussian models of MFCCs compared with KL divergence or the Earth Mover's distance; learned embeddings (MusiCNN, OpenL3, CLAP, MERT, Essentia models) with cosine distance.
- **Metadata distance:** Jaccard or cosine over genre and tag sets; tag co-occurrence on artists and tracks; collaborative filtering and item2vec on listening data.
- **Genre distance:** shortest path in the taxonomy graph; Wu-Palmer and Resnik (depth and information content of the shared ancestor); the distance between the centroids of the track embeddings of two genres.
- **Validation:** triplet judgements by people ("which of B or C is closer to A?").

## Proposed phases

### Phase 1: tag-based, no audio analysis (cheap, offline, in the library only)

- **Genre distance:** shortest path in our parent graph (all parents equal, ADR-0037). A modifier (dark, progressive, ...) adds a small cost; a shared family counts as closer than a shared medium group. The distance table is generated, not hand-written, and covered by tests.
- **Song distance:** weighted Jaccard over the song's genres (a genre counts as partly present through its ancestors, so house and deep house are close), plus small terms for BPM and release year; weights are constants.
- **Similar songs:** a "Similar songs" list on the song card (top N by distance) and a Library sort "most similar to this song".
- **Tag-outlier check:** a report of songs whose genres disagree with their nearest neighbours (for example a song tagged `dub` whose ten nearest songs are all folk punk). It is a review list for the owner, like the genre cleanup review; it never changes data by itself.

### Phase 2: audio embeddings (later; offline job, never in the player path)

- Compute an embedding per downloaded song once, store it next to the song (a small vector file), recompute only when the audio changes.
- Distance by cosine; nearest neighbours as an independent opinion beside Wikipedia and Discogs; feed the genre suggestion rule (ADR-0035) as another source group.
- Runs as a background job on the server (CPU only, low priority); playback and offline reliability stay untouched.

### Phase 3: data-driven genres (research)

- Cluster songs by audio distance (hierarchical clustering or density methods such as HDBSCAN) and compare the clusters with our tree: which genres are sound-coherent, which are not.
- Clusters need human names and cut across our axes (form, medium, purpose, tradition, mood), so they inform the tree and never replace it.

## Open questions

- A. Which weights for the song distance, and should genre depth count (a shared level-3 genre closer than a shared family)?
- B. A library of about 420 songs is too small for stable clusters; embeddings of the nearest neighbours need an outside reference set, or only compare within the library?
- C. Embedding model choice (size, licence, CPU speed on the server LXC).
- D. Where the "tag-outlier" review lives: a report file in `docs/tech/`, or an owner-only page.

## Acceptance (to refine when built)

- Phase 1: spec ids in docs/specs/genres.md (distance) and library.md (similar songs); server tests for the genre distance (symmetric, zero on the same genre, shortest path, modifier cost) and the song distance; a test that the outlier report flags a seeded mistag.
- No effect on playback; no audio analysis in the request path; owner data is never changed by the report.

## Not in scope

- Recommendations from other users' data (the app has no social features).
- Public aggregates or sharing of embeddings.
