# Plan a native Android app

> Alex (2026-11-09): "Electrophone Android app, plan first".

Status 2026-11-09: proposal. Planning docs only: [spec](../specs/android.md) (AND-001 onwards, all planned), decision record [ADR-0051](../tech/decisions.md) (proposal), this task, concern C3. No code, no `android/` folder, no tooling installed, nothing accepted. Phases that create `android/` or touch `scripts/sync-design-system.py`, `scripts/check.sh` or `.github/workflows/` start only after the owner accepts ADR-0051 and answers NA and NB.

## Goal

The iOS app's job on an Android phone: pick songs on the server, get the audio onto the phone through the existing client-paced flow, play it offline with the screen locked, with the Electrophone look and the same account.

Key principle check ([CLAUDE.md](../../CLAUDE.md)): everything in v1 downloads, stores or plays songs; nothing else is in scope until v1 is verified on a device.

## What exists today (read 2026-11-09)

- Nothing for Android: no folder, no Kotlin, no Gradle, no Play or APK mention anywhere in the repo (`docs/ui-ux/style-guide.md` and `performance-guide.md` list Material 3 and the Android Studio Profiler as general references only).
- What the Android app reuses as it is: the server and its API (`GET /catalog` with ETag, `POST /songs`, `POST /songs/{id}/audio`, `GET /songs/{id}/status`, `GET /files/{id}` with Range capped at 768 KiB per request (API-318), `POST /plays`, `GET /me/usage`; API-007 Bearer tokens; ADR-0012 quotas); the data shapes on the phone (`library.json`, `phone-index.json`, `library.json.good`; song state `onServer` plus local file); `docs/brand/tokens.json` and `scripts/sync-design-system.py` (iOS and web outputs, the `platform` rule, `--check`); the web icon set `web/js/icons.js` (68 icons); the shared test fixtures in `server/tests/fixtures`; the iOS screens and rules as the reference ([ios.md](../specs/ios.md)).
- What the server needs: nothing in v1 (the web Google client id is the token audience); later one redirect endpoint for Apple sign-in on Android (AND-075).
- What Google Cloud needs: an Android OAuth client (package `com.alexisayenko.audioplayer.android`, the debug and release SHA-1) in the existing project.

## Phases

Each phase ends with the app still playing downloaded songs with the screen locked (from phase 2 on). Nothing starts before acceptance.

0. [ ] Toolchain and skeleton: Android Studio on the MacBook; `android/` with Gradle Kotlin DSL, a version catalog, one `app` module, Compose, `minSdk` 28; the `android` output and the `platform: android` rule in `scripts/sync-design-system.py` (AND-010, AND-011), `--check` extended; the icon pipeline chosen (ND); the GitHub Actions job and the `check.sh` step (AND-083, AND-084; question NH). Acceptance: an empty themed shell builds on the emulator and in CI; `--check` passes.
1. [ ] Sign-in, catalog sync, Library: Credential Manager Google sign-in with the web client id (AND-070 to AND-074), the Android OAuth client created, `ApiClient` and `Endpoints` (AND-021), `LibraryIndex` and the tolerant loaders (AND-057), catalog sync (AND-058), the Library screen with search, chips, sort and the song details sheet (AND-032 to AND-035), the drawer shell (AND-016 to AND-018), the Kotlin ports with fixture tests (AND-020). Acceptance: the owner's library lists on a device; the ports pass every fixture case; token renewal observed across an hour (or the AppAuth fallback chosen).
2. [ ] Playback: `MediaSessionService` with ExoPlayer, notification and lock screen, headset and Bluetooth, audio focus, the resume rule, weighted shuffle and repeat, the play log (AND-060 to AND-067); the Now playing screen and the mini-player bar (AND-036, AND-017). Acceptance: 30 minutes of locked-screen playback of files placed by hand; a call interrupts and resumes; kill and relaunch restores the position by the rule; fixture tests for the shuffle and the recorder pass.
3. [ ] Downloads and storage: `DownloadWorker`, the planner, the hourly pause, Range resume, the foreground notification, `audio/` and `phone-index.json` writes, Remove from phone (AND-050 to AND-059); the row download state (AND-033). Acceptance: a download survives swipe-away and reboot; a forced `hourly_limit` pauses and resumes on time; a cancelled copy leaves no half file; fake-clock tests for the planner.
4. [ ] Add, Edit and Settings: the shared `SongForm` with pill fields and drag (AND-037), paste and the share-sheet target (AND-038), the Settings cards (AND-040, AND-041), the auto-download and mobile data switches wired to the worker constraints. Acceptance: a link shared from the YouTube app lands in Add, saves and downloads; the payload matches `ios_contract.json`; Edit round-trips an unchanged song.
5. [ ] Release: the keystore and passwords in `~/.config/android/`, `scripts/build-android-release.sh`, the date-based `versionCode`, the first signed APK on a GitHub Release, the device checklist (AND-101) recorded here, docs (this task, the spec statuses, CLAUDE.md and AGENTS.md, the README structure, `docs/README.md`, CHANGELOG). Acceptance: a sideloaded install on the first user's phone passes the checklist.

- NE. YouTube text search in Add on Android (not only link paste and share)? 1. Not in v1 (link paste and the share sheet only; IOS-023 keeps it secondary). 2. In v1, as the iOS "Search YouTube by title" link. 3. Later phase.
- NF. Order of the later phases? 1. Playlists, Albums and album download, Apple sign-in, Statistics, Tools, the rest. 2. Albums first (bulk download is closest to the key principle). 3. Apple sign-in first (another Apple-account user needs it).
