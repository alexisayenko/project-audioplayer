# Normalise the volume level per song

Alex decided the open questions on 2026-10-19 ("take the recommendations"); see [Decisions](#open-questions-for-alex). Not started.

## Problem

Songs from YouTube and SoundCloud differ a lot in loudness (quiet remasters next to hot club mixes). The listener keeps reaching for the volume control between tracks. Reliable playback is the key principle, so the fix must never alter or risk the audio files and must work offline once a song is on the phone.

## Approach

Measure once, store a number, apply a gain at playback. Audio files are never touched.

1. **Measure** integrated loudness (EBU R128, LUFS) and true peak once per song with ffmpeg, after the download, in the existing background slot next to BPM detection (`server/app/main.py` `_run_download`, `server/app/bpm.py` pattern: never raises, returns `None` on failure). First pass only, no re-encode:
   `ffmpeg -nostdin -hide_banner -i <file> -af loudnorm=I=-14:TP=-1.5:LRA=11:print_format=json -f null -` (parse the trailing JSON: `input_i`, `input_tp`), or the `ebur128=peak=true` filter. Run under `nice`, with a timeout, and through the download scheduler so it waits behind running downloads (same as identification, API-071).
2. **Store** per song in `library.json`: `loudness_lufs` (float, 1 decimal) and `true_peak_db` (float, 1 decimal), plus `gain_trim_db` (manual override, default 0).
3. **Compute** the playback gain on the client from the stored numbers:
   `gain_db = clamp(target - loudness_lufs, -12, +12) + gain_trim_db`, then limited by headroom so the true peak never exceeds -1 dBTP: `gain_db = min(gain_db, -1.0 - true_peak_db)`. Songs that cannot reach the target without clipping stay quieter (no limiter; see risks).
4. **Apply** non-destructively in the player:
   - Web: Web Audio API, `createMediaElementSource(audio)` -> `GainNode` -> destination. `audio.volume` cannot exceed 1, a `GainNode` can (boost). Gain change on song change, with a short `setTargetAtTime` ramp; the user's volume slider stays on `audio.volume`.
   - iOS: AVPlayer with an `AVAudioMix` (`AVMutableAudioMixInputParameters.setVolume`) for attenuation. Boost above 1.0 is not possible there; if boosting is wanted, use `AVAudioEngine` (`AVAudioPlayerNode` plus a gain node) or clamp the iOS gain to <= 0 dB (attenuate-only). Decided: attenuate-only (gain clamped to <= 0 dB) unless the phase 3 device test says otherwise.
5. **Settings** (web `Settings`, iOS `SettingsView`):
   - "Normalise volume" toggle, default **on**.
   - Target level: **-14 LUFS (default, like streaming services)**, -16, -18.
   - Track mode only; no album/playlist mode, because songs are played in mixed queues.
6. **Per-song override**: a trim (-6..+6 dB, step 0.5) in the Edit dialog; a "Re-analyse" button next to it.
7. **Backfill** for existing songs: a low-priority batch job (below), started explicitly by the user from Settings (a button), never automatically at server startup.

## Catalog states

A song without audio on the server has no measurement (ADR-0010: none/server/phone states). The loudness is measured on the first download or audio fetch and then stays with the catalog entry, so a phone that later receives the song already knows its gain. Songs with no measurement play at unity gain (0 dB), never blocked.

## Where results live

Per user in `library.json` (ADR-0012): three small numbers per song, size impact negligible. Writes during backfill go in batches (one `library.json` write and one git commit per batch of 25 songs, never one per song) to avoid hundreds of commits and pushes.

## API changes

- `GET /library` and `GET /catalog`: songs carry `loudness_lufs`, `true_peak_db` (both `null` when unmeasured), `gain_trim_db`.
- `PATCH /songs/{id}`: accepts `gain_trim_db` (float, -6..+6, rounded to 0.5), validated like the other song fields; `loudness_lufs` and `true_peak_db` are server-owned and rejected from clients (or ignored).
- `POST /songs/{id}/loudness`: re-analyses one song whose audio is on the server; returns `{loudness_lufs, true_peak_db}`; 404 `unknown song` / `not downloaded`; 200 with nulls when ffmpeg fails.
- `POST /library/loudness-backfill` (owner only, or per user): starts or resumes the backfill (the only trigger; there is no automatic start at server startup); `GET` returns `{done, total, running}`.
- Limits: none of these count toward the add quota or the hourly limit (NFR-070), the same as `identify`.

## Backfill job

- Selects songs of the user with audio on the server and `loudness_lufs` missing; processes oldest first, one at a time.
- Low priority: `nice -n 19`, `ffmpeg -threads 1`, runs through the download scheduler and never while a download job is running (perkunas gives this service 1-2 cores).
- Resumable: progress is the data itself (a measured song is skipped), so a restart or crash just continues; an interrupted song is re-measured.
- One `library.json` write per batch; a failed song is recorded with `loudness_lufs: null` and a `loudness_failed` marker so it is not retried in a loop (cleared by the manual re-analyse).
- Cost: a few seconds of ffmpeg per song; a few hundred songs run in the background in minutes to tens of minutes.

## Web caveats

- `createMediaElementSource` outputs silence for cross-origin media without CORS. Audio is served same-origin from `/files/{id}` with the session cookie; keep it same-origin, or add `crossorigin="use-credentials"` and matching `Access-Control-Allow-Origin`/`Allow-Credentials` if the host ever differs. Verify with a real signed-in session, not just the owner token.
- The `AudioContext` starts suspended: create it and call `resume()` inside the first user gesture (the Play click); Safari and iOS Safari require this and may re-suspend after the page is backgrounded or the screen locks, so resume on `play`.
- Once a media element is connected to a context, its sound goes only through the graph; do not recreate the source per song (it throws if called twice for one element), connect once and only change the gain.
- Background and lock-screen playback on iOS Safari may behave differently with Web Audio than with a plain element; test it, and fall back to plain `audio.volume` attenuation (gain <= 0 dB) if it breaks. The web UI is secondary to the iOS app.

## Acceptance criteria

- [ ] A downloaded song gets `loudness_lufs` and `true_peak_db` within a few seconds, without delaying the song becoming playable; failure leaves them `null` and the song still plays.
- [ ] Measurement is within 0.5 LU of a reference (ffmpeg fixture tones of known LUFS).
- [ ] Playback gain follows `clamp(target - loudness, -12, +12) + trim`, and never pushes the true peak above -1 dBTP.
- [ ] Toggle off restores unity gain immediately; target change applies to the next song and to the current one without a gap.
- [ ] Trim and re-analyse work from the Edit dialog and persist.
- [ ] Web: no silence, no clipping, works with the signed-in cookie session, resumes after a locked screen or backgrounding.
- [ ] iOS: gain applies in background and lock-screen playback and offline.
- [ ] Backfill is resumable, low priority, writes once per batch and never blocks a download.
- [ ] A user sees and changes only their own songs' values (isolation); none of this counts toward quotas.
- [ ] Audio files are byte-identical before and after.
- [ ] `cd server && python -m pytest -q` and `scripts/check.sh` pass; web `*.test.mjs` pass.

## Tests

- Gain maths unit tests (server helper and a `web/js/loudness.test.mjs`): clamp at +/-12, trim, target change, the clipping guard with a hot track (peak -0.2 dBTP cannot be boosted), unmeasured -> 0 dB.
- Backfill: resumes after an interrupted run, skips measured songs, batches writes, skips failed songs, does not run during a download.
- API: PATCH validation (range, rounding, client cannot set measured fields), `POST /songs/{id}/loudness` 404s, quota not charged, per-user isolation (user A cannot read or re-analyse user B's song).

## Risks

- YouTube normalises loudness in its own player, but the downloaded file is the original, so the spread is real; a measured number is needed.
- A loud track with little true-peak headroom cannot be boosted without a limiter; it simply stays where the guard puts it, so quiet and loud may not fully meet at the target.
- Seeks and song changes: change the gain only on song change, with a short ramp, to avoid clicks; a gain jump mid-song on a target change should also ramp.
- ffmpeg time is a few seconds per song; backfill competes for 1-2 cores on perkunas, hence nice, one at a time and not during downloads.
- `AudioContext` needs a user gesture and can be suspended by the browser (see web caveats).
- Per-song gain does not fix loudness within a song (dynamic range); that is out of scope.

## Alternatives

- **ReplayGain tags (`REPLAYGAIN_TRACK_GAIN`/`PEAK`) written into the m4a**: lets third-party players apply the gain. Adds a file rewrite (remux, `-c copy`) and risk to a file Alex wants safe; optional phase 5, off by default (decided: not written).
- **Server-side re-encode to a normalised file**: rejected. It is lossy (a second generation of AAC), costs CPU and disk, doubles storage, and the choice of target becomes irreversible.
- **Fixed-gain compressor/limiter in the player**: rejected for now; changes the sound and is harder to get right than a per-song number.
