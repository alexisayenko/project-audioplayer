# Cut a time range when importing a track from YouTube or SoundCloud

> Alex: "when importing track from youtube/soundcloud - allow to cut a certain time", example https://youtu.be/HdR7uf2l7Ac (a long video of which only a part is wanted).

## Why

A link often points to a long video (a stream, a conversation, a mix, a live set) of which only one part is the song. Today the whole thing is a library entry with the full duration and the full audio.

## Proposed behaviour

Decided by Alex (FE1, 2026-10-21), [ADR-0040](../tech/decisions.md): **download trimmed**. Not a non-destructive clip. The stored audio file is only the cut part; the trim stays in the metadata next to the source as a reproducible recipe (where it was downloaded and how it was cut).

- Each source entry gets `trim_start` and `trim_end` (seconds, null = none), plus the source's original duration if known. The trim belongs to the source (a song may have several sources, each with its own trim). Works with either source shape under discussion (`{type, ref, trim_start, trim_end}` with a derived URL, or the current `{platform/source, id, url}`).
- API: `POST /download` and `POST /songs` accept an optional trim per source; old clients send none and get the whole track. The server cuts with ffmpeg during download (yt-dlp `--download-sections` or a post-process `-ss/-to`; pick in the analysis). Trimmed songs are re-encoded for accuracy (stream copy snaps to frames); untrimmed songs are unchanged.
- Add dialog (web): after pasting a link, **Start** and **End** fields (`mm:ss` or `h:mm:ss`; empty = from the beginning / to the end). A link that carries a start time (`?t=85`, `&t=1m25s`, SoundCloud `#t=1:25`) pre-fills Start. A preview play button plays only the range from the YouTube embedded player (no download, no waveform) and the resulting length is shown.
- The Add flow saves the song with metadata as usual. The web UI downloads no audio itself (audio reaches the server through the iOS download), so the trim is stored on the source and applied when the download runs.
- Edit dialog shows the trim and a "Re-download with a new trim" action; for songs whose audio already exists a change needs the re-download.
- No clip logic in players: the file is the song, so duration, progress bar, lock screen, listening statistics and the 90% rule are right automatically.
- The same mechanism serves manual trims of beginnings and endings of ordinary songs and the automatic silence trim of [task-0052](task-0052.md).

## Data shape (FG1, 2026-10-21)

Decided by Alex, [ADR-0040 "Sources shape"](../tech/decisions.md), [DATA-193](../specs/data-model.md): `sources` becomes `[{type, ref, trim_start, trim_end}]` plus optional `duration`. `type` = youtube | soundcloud | spotify | url (catch-all, `ref` = the full address) | more later; `ref` = the identifying part only (YouTube video id, Spotify track id, SoundCloud `artist/track`). The URL is derived from `type` + `ref` by one template table in the server (mirrored in the web); `t=`, `list=`, `utm_*` are never stored; dedupe by (`type`, `ref`); several sources of one type allowed, first is primary. API still returns the derived `url` and legacy `source`/`id` for the primary source; writes still accept `url` (parsed into `type` + `ref`, `t` becomes a `trim_start` suggestion for the Add dialog).

## Open questions (decided)

- A. How is the cut applied? Decided: option 2, destructive, reframed. Trim on download with ffmpeg, only the cut is stored, source plus trim kept as the recipe (the audio file is derived, like peaks and covers).
- B. Web playback of audio already on the server: needs no clip handling, the file is already the cut.
- C. Editing the trim after the audio was downloaded: allowed; it means downloading again from the source with the new trim (cheap because the recipe is stored).
- D. Where iOS and the server meet: the optional trim in the download request (`POST /download`, `POST /songs`); old clients send none and get the whole track. iOS needs no clip handling.
