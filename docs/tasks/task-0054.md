# Change a song's cover from the song card

Status (2026-10-21): server and web built and deployed (PUT/DELETE cover, URL/upload/default, Wikipedia suggestions via the summary API, Discogs page URLs). Open: live verification (the Wikipedia cover for "Birdy - Wings", `DISCOGS_TOKEN` set on the server, the Discogs flow never tried live), and a possible follow-up for artist and version images from the cover fallback chain of ADR-0039 decision D (not part of this task).

> Alex: allow changing the song cover in the infobox: specify a URL (download and store), upload from the local device, get the suggested album cover from Wikipedia.

## Proposed behaviour

- The song card (infobox) gets a "Change cover" action on the cover (visible on hover, round icon button, owner and signed-in users with edit rights; guests never).
- A small dialog with four options:
  1. **URL**: paste an image link; the server downloads it, validates it as an image, re-encodes it to the app's cover size and format, and stores it as the song's cover.
  2. **Upload**: pick a file from the device (drag and drop on the web); same validation and re-encoding.
  3. **Wikipedia suggestion**: show the album cover(s) found through the song's `wikipedia_song` / `wikipedia_album` links (the infobox image of the page), the user picks one.
  4. **Set default image**: use the app's default cover (the neutral placeholder the cards and rows show when a song has no cover) instead of an automatic or custom one. It is a deliberate choice, so it is stored as `cover_source: default` and a later automatic cover refresh does not replace it. (Alex, 2026-10-20: "add to it option set default image".)
- Preview before saving; "Remove custom cover" returns to the automatic cover (YouTube thumbnail or the existing fetch); "Set default image" is different: it pins the neutral placeholder, and choosing any other option or "Remove custom cover" ends it.
- The new cover replaces `cover` and bumps `cover_v` so clients refetch; the change goes through the normal save path (one commit, git sync).

## Open questions

- A. Where is the custom cover kept so a later automatic cover refresh does not overwrite it (a `cover_source: custom` flag)?
- A2. What exactly is the default image: the existing placeholder asset of the design system (no new file), shown in the same cover frame? Recommended: yes, no new asset; confirm whether Alex means the placeholder or the automatic cover.
- B. Limits: file size (for example 5 MB), accepted types (JPEG, PNG, WebP), SSRF protection for the URL download (no private addresses, redirect and size limits).
- C. Wikipedia and copyright: store only the user-chosen image for personal use; show the source link.
- D. iOS: the app shows `cover`, so no contract change; the editing UI is web only first (iOS needs Alex's permission to edit `ios/`).

## Decisions (2026-10-21, Alex: "let's implement this")

- A. Resolved: `cover_source` on the song: `custom` (upload, address, Wikipedia pick), `default` (pinned placeholder, no file, clients draw the placeholder; A2: the existing placeholder asset, no new file), absent = automatic. The audio download skips the cover fetch for `custom` and `default` songs. DATA-192.
- B. Resolved: 5 MB, JPEG/PNG/WebP decoded with Pillow (magic bytes, not the content type), re-encoded as JPEG up to 1024 px, 40 megapixel guard; URL downloads only from public addresses (every hop checked, at most 3 redirects, timeouts, streamed size cap, no cookies); 30 downloads and 60 suggestion lookups per hour per non-owner. API-201.
- C. Resolved: only the chosen image is stored; the source address is not kept (no place in the data model); the "source" link shown in the dialog comes from the suggestion's `page` (web).
- D. Resolved: web only, iOS contract unchanged (`cover`, `cover_v`).
- Server built, not deployed (2026-10-21): API-201 (`PUT` raw / multipart / JSON `{url}` / `{default: true}`), API-202 (`GET /songs/{id}/cover/suggestions`), API-203 (`DELETE` resets custom/default to automatic); `server/app/routes/covers.py`, `wiki_lookup.cover_candidates`, `downloads.fetch_cover_bytes`; tests in `server/tests/test_covers.py` pass (run on their own, the full suite not run).

- Fix (2026-10-21, built, not deployed): the Wikipedia option found nothing for single and album pages (Birdy - Wings, `Wings_(Birdy_song)`) because MediaWiki `pageimages` does not return non-free infobox images (files on en.wikipedia.org itself). `wiki_lookup._page_image` now tries the REST summary (`thumbnail`, `originalimage`), then `pageimages`, then `prop=images` plus `imageinfo` filtered for cover-like names; Wikimedia calls and downloads (`coverimg.http_get`) use the User-Agent `Electrophone/1.0 (https://electrophone.cc)`, `utm_*` is dropped from fetched URLs; the dialog hides the preview frame while nothing is selected. API-202 updated; tests written, not run, not tried against live Wikipedia.
- Discogs pages (2026-10-21, built, not deployed): "From address" also takes a Discogs master or release page (for example `https://www.discogs.com/master/5659-Hallucinogen-Twisted?redirected=true`); the server resolves it through the Discogs API (`server/app/discogs_cover.py`, API-201) and stores the image as a custom cover. A song with a stored `discogs_url` also gets a Discogs entry in the suggestions, so the dialog option is now called "Suggestions". Needs `DISCOGS_TOKEN` on the server; never tried against live Discogs (tests use faked API answers).
