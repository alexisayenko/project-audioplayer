# Refactor the music metadata model: structured artist credits, contributors, versions

Type: analysis first. NO code changes until Alex approves the analysis below.

## Context

Songs store flat strings: `title` (may hold featured artists, remix or version text), `artist` (several artists joined by `&`, `,` or `feat.`), `remixer` (an artist name, a full remix title, or a mixing credit), `year` (ambiguous: original release, remix year or source publication; `remix_year` also exists). Real library examples:

- 'Martin Garrix & Tiesto': two main artists.
- 'Vortex Involute feat. Yana Kay', 'Kato Feat. Jon': main plus featured.
- 'Nadia Ali, Starkillers & Alex Kenji': three credited artists.
- 'Alesso Remix': remixer plus version.
- 'Gabriel & Dresden Chill Mix': remixer plus a specific mix name.
- 'Mixed By DJ Gvozd': a mixing credit, not a remix.

These need distinct structured representations.

## Proposed model (to be analysed, not decided)

- `artists[]` of `{name, role: main|featured, position}` plus preserved join phrases and ordering, so the public credit can be rebuilt.
- `contributors[]` of `{name, role}` from a small controlled vocabulary (remixer, producer, composer, lyricist, vocalist, mixing_engineer; extend only on a real requirement).
- `version` `{type: original|remix|edit|extended|live|acoustic|instrumental|remaster|other, subtitle: exact credited text}`.
- Canonical data separated from presentation: base title, version, main artists, featured, contributors, display artist credit, display title.
- `&` is not equal contribution and `feat.` is not a vocalist (presentation conventions); never infer roles from punctuation alone.

Concepts to distinguish (no tables): work, recording, version, release, artist, contributor, source. A remix is potentially a distinct recording: never attach the original's MusicBrainz recording MBID to a remix because title and main artist match. A library item keeps a stable internal id independent of YouTube, SoundCloud and MusicBrainz ids.

## Scope

- Inventory every current use of title, artist, remixer, year, remix_year: server, web, iOS, API, import/export, enrichment.
- Backward compatible: preserve data and user edits; add fields incrementally; keep original source strings (immutable source vs user-edited values); no silent rewriting of ambiguous credits; automatic parsing is a SUGGESTION needing verification when uncertain; legacy fields only as derived projections (one editable source of truth); web and iOS share semantics; existing songs stay playable.
- Enrichment review (MusicBrainz, Discogs, Wikipedia, YouTube, SoundCloud): prefer verified structured credits over parsing display strings; keep imported and user-corrected values distinguishable; never overwrite curated values without permission; no recording-level metadata onto a different remix or version; incomplete metadata allowed, nothing invented.
- UI: minimal changes to the shared Add/Edit form (and playback displays): several main artists, featured artists, remixer or other contributors, pick or type a version, preview of display title and credit. Reuse the Electrophone design system and token-pill conventions; no unrelated redesign.

## Deliverables (analysis, no code)

1. Inventory of metadata fields and where each is used.
2. Current vs proposed comparison.
3. Recommended JSON schema with realistic examples: A two main artists; B main plus featured; C three main artists plus remixer plus remix version.
4. Mapping to DDEX and MusicBrainz semantics, formal terminology kept apart from Electrophone abstractions.
5. Backward-compatible migration strategy.
6. Required backend, API, web and iOS changes.
7. Compatibility risks, ambiguities, test cases.
8. Ordered implementation plan.

Then WAIT for Alex's approval before changing code.

## Constraints

- Smallest coherent model that solves the demonstrated problems; no unnecessary normalisation, relational tables or abstraction layers.
- Do NOT implement the DDEX ERN standard.
- Do not assume complete metadata; document uncertainty wherever a role is inferred from a string.

## Coordinator's recommendation (2026-10-16)

Adopt a SLIM first phase. The demonstrated problems are only: (a) main vs featured artists with preserved join phrases; (b) remix vs mixing credit vs other versions; (c) ambiguous `year` / `remix_year`.

Phase 1:

- `artists[]` with role main|featured and joins.
- `version` `{type, subtitle}` with an optional remixer name.
- Raw source strings kept immutable.
- Legacy `title` / `artist` / `remixer` derived as projections.
- Parsing only as suggestions.

DEFER:

- producer, composer, lyricist, vocalist, mixing_engineer contributors (nothing in the UI uses them).
- Separate work and release entities.
- Provenance machinery beyond raw strings.
- MBID-per-version logic; keep only the rule "never reuse the original MBID for a remix".
- DDEX mapping beyond a short glossary.

Build on the existing pills: the shared song form already tokenises Title, Artist and Remix into pills (separators in [add-song.md](../specs/add-song.md), ADD-071, and `web/js/tokens.js`). The structured model should build on those pills, not replace them. The library is a few hundred songs, so no migration framework: a one-off, idempotent, backed-up startup migration like the genre one ([task-0035](task-0035.md)).
