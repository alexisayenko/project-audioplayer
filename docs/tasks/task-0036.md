## Context

Songs store flat strings: `title` (may hold featured artists, remix or version text), `artist` (several artists joined by `&`, `,` or `feat.`), `remixer` (an artist name, a full remix title, or a mixing credit), `year` (ambiguous: original release, remix year or source publication; `remix_year` also exists). Real library examples:

- 'Martin Garrix & Tiesto': two main artists.
- 'Vortex Involute feat. Yana Kay', 'Kato Feat. Jon': main plus featured.
- 'Nadia Ali, Starkillers & Alex Kenji': three credited artists.
- 'Alesso Remix': remixer plus version.
- 'Gabriel & Dresden Chill Mix': remixer plus a specific mix name.
- 'Mixed By DJ Gvozd': a mixing credit, not a remix.

These need distinct structured representations.

## Decided structure (Alex, 2026-10-16)

UI label -> JSON key:

| Label | Key | Meaning |
| --- | --- | --- |
| Title | `title` | base title, no version text |
| Artists | `artists` | main artists, ordered |
| Featuring | `featured` | featured artists |
| First released | `released` | year of the original recording |
| Version | `version.kind` | remix, live, acoustic, extended, instrumental, remaster, edit, other |
| Version name | `version.name` | credited text exactly as written ('Alesso Remix', 'Live, Royal Albert Hall') |
| Remix year | `version.year` | year of the version |
| Remix by | `version.by` | people credited on the version, incl. mixing credits |

Rules:

- A remix is one kind of version. "Remixer year" and "version year" are the same field: there is no separate `remix_year` in the new model. The old `remix_year`, `remixer`, `artist` and `year` stay as derived compatibility values.
- A song with no version has no `version` object.
- The credited version name wins for display; `version.by` is for search and filters, and the form warns when the two disagree.
- Parsing `&` and `feat.` from raw strings is only a suggestion. The raw source title and artist stay stored untouched.
- A live version is a different recording: never reuse the studio recording's MusicBrainz id.
- `released` is the first-release year of the original recording. For versions, the platform publish year is a visibly marked suggestion unless a better source exists (ADD-111).
- Deferred as before: producer, composer, lyricist and vocalist contributors, work and release entities, DDEX mapping.

Examples:

```json
// A: two main artists, no version
{"title": "The Only Way Is Up", "artists": ["Martin Garrix", "Tiesto"], "featured": [], "released": null}

// B: released 1993; the YouTube upload year (2014) must not become `released`
{"title": "What Is Love", "artists": ["Haddaway"], "featured": [], "released": 1993}

// C: live version; released is the year of that recording, unknown here, so null
{"title": "Cold Heart", "artists": ["Dua Lipa", "Elton John"], "featured": [], "released": null,
 "version": {"kind": "live", "name": "Live, Royal Albert Hall", "year": null}}

// D: three artists, remix
{"title": "Pressure", "artists": ["Nadia Ali", "Starkillers", "Alex Kenji"], "featured": [], "released": null,
 "version": {"kind": "remix", "name": "Alesso Remix", "by": ["Alesso"], "year": null}}
```

(Example A's `released` is left null: not verified.)

Concepts to distinguish (no tables): work, recording, version, release, artist, contributor, source. A remix is potentially a distinct recording: never attach the original's MusicBrainz recording MBID to a remix because title and main artist match. A library item keeps a stable internal id independent of YouTube, SoundCloud and MusicBrainz ids.

## Scope

- Inventory every current use of title, artist, remixer, year, remix_year: server, web, iOS, API, import/export, enrichment.
- Backward compatible: preserve data and user edits; add fields incrementally; keep original source strings (immutable source vs user-edited values); no silent rewriting of ambiguous credits; automatic parsing is a SUGGESTION needing verification when uncertain; legacy fields only as derived projections (one editable source of truth); web and iOS share semantics; existing songs stay playable.
- Enrichment review (MusicBrainz, Discogs, Wikipedia, YouTube, SoundCloud): prefer verified structured credits over parsing display strings; keep imported and user-corrected values distinguishable; never overwrite curated values without permission; no recording-level metadata onto a different remix or version; incomplete metadata allowed, nothing invented.
- UI: minimal changes to the shared Add/Edit form (and playback displays): several main artists, featured artists, remixer or other contributors, pick or type a version, preview of display title and credit. Reuse the Electrophone design system and token-pill conventions; no unrelated redesign.

## Constraints

- Smallest coherent model that solves the demonstrated problems; no unnecessary normalisation, relational tables or abstraction layers.
- Do NOT implement the DDEX ERN standard.
- Do not assume complete metadata; document uncertainty wherever a role is inferred from a string.

## Coordinator's recommendation (2026-10-16)

Adopt a SLIM first phase. The demonstrated problems are only: (a) main vs featured artists with preserved join phrases; (b) remix vs mixing credit vs other versions; (c) ambiguous `year` / `remix_year`.

Phase 1:

- `artists[]` with role main|featured and joins.
- `version` `{type, subtitle}` with an optional remixer name.
- Raw source strings kept immutable.
- Legacy `title` / `artist` / `remixer` derived as projections.
- Parsing only as suggestions.

DEFER:

- producer, composer, lyricist, vocalist, mixing_engineer contributors (nothing in the UI uses them).
- Separate work and release entities.
- Provenance machinery beyond raw strings.
- MBID-per-version logic; keep only the rule "never reuse the original MBID for a remix".
- DDEX mapping beyond a short glossary.

Build on the existing pills: the shared song form already tokenises Title, Artist and Remix into pills (separators in [add-song.md](../specs/add-song.md), ADD-071, and `web/js/tokens.js`). The structured model should build on those pills, not replace them. The library is a few hundred songs, so no migration framework: a one-off, idempotent, backed-up startup migration like the genre one ([task-0035](task-0035.md)).

## References

DDEX is the industry standards body for exchanging music metadata along the digital value chain. ERN (Electronic Release Notification) is how labels and distributors deliver releases to streaming services and stores; MEAD (Media Enrichment and Description) delivers extra descriptive data to services. Electrophone follows its conventions only where they help (a version as a subtitle, contributors with roles, ordered display artists with join phrases, featured vs main) and deliberately does not implement the ERN schema. Checked 2026-10-16; only pages that were opened are linked.

| Source | What it says | How we use it | Link |
| --- | --- | --- | --- |
| DDEX ERN | Describes releases and their resources plus the terms for offering them; sender is usually a record company or distributor, receiver usually a DSP; an Implementation Licence is needed to implement it | Reason to borrow vocabulary only, no schema | [ddex.net](https://ddex.net/standards/electronic-release-notification-message-suite/) |
| DDEX MEAD | Gives DSPs richer information about releases than ERN usually carries | Out of scope | [mead.ddex.net](https://mead.ddex.net/media-enrichment-and-description/1-introduction/) |
| DDEX knowledge base (ERN) | Lists guides on differentiating versions with SubTitle, communicating remixes and remixers, DisplayArtists and display artist roles; the page is navigation only, and the featured/main role terms are unverified there | `version.name` as the subtitle, `version.by` as remixers, `artists` ordered | [kb.ddex.net](https://kb.ddex.net/implementing-each-standard/electronic-release-notification-message-suite-(ern)/) |
| MusicBrainz artist credits | A credit lists the credited artists, each with an optional credited name and a join phrase; the full credit is built from them | `artists` ordered, join phrases kept | [Artist Credits](https://musicbrainz.org/doc/Artist_Credits) |
| MusicBrainz recording | A remix or a live version is a different recording from the studio original | Never reuse the original's recording id for a version | [Recording](https://musicbrainz.org/doc/Recording) |
| MusicBrainz relationship types | The "remix" relationship links a remixed recording to its source recording | Version as a link to the original, not a copy | [Recording-Recording](https://musicbrainz.org/relationships/recording-recording) |
| MusicBrainz remix style | A remix keeps the original title including the remixer text, is typically credited to the original artist, and the remixer is linked with a remixer relationship | `title` plus `version.name`; remixer in `version.by` | [Remixes and mashups](https://musicbrainz.org/doc/Style/Specific_types_of_releases/Remixes_and_mashups) |
| Discogs | Unverified: guidelines pages returned 403 to our fetch; a search excerpt says a remix named in a track title is also entered as a remix credit for that artist | Same idea as `version.by` | not linked |
| Beatport | Unverified: no official help page defining "Mix name" was found; catalog pages show a separate mix label (Original Mix, Extended Mix, remix names) | Same idea as `version.name` | not linked |

Exact DDEX terms for each concept (AVS values, DisplayArtistRole, SubTitle, VersionType, RelatedResource) and a proposed rename table: [ddex-terminology](../tech/ddex-terminology.md).

## Server build (2026-10-16)

- BJ1. Resolved 2026-10-16 (Alex): mashups. A mashup is a version of kind `mashup`; the main artists are whoever MADE the mashup and the source artists or works go in `version.of`, which becomes a list of names (a cover has one, a mashup several; a single string is accepted and normalised). A title that does not say who made it (for example an upload by a repost channel) is only suggested, with the question "Who made this mashup?".
