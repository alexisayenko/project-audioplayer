Two phases. **Phase 1** (a YouTube video with time codes imports like a playlist; the former task-0060, merged here 2026-10-21) may be built when Alex says go. **Phase 2** (silence detection, cutting audio, timeline editor, iOS) is analysis first: NO code changes until Alex approves the analysis in phase 2.

## Context

A long source (a DJ mix, a live set, a full album uploaded as one YouTube video or SoundCloud set) is one library item today. Alex wants to offer splitting it into separate songs by time, with suggestions from time codes in the description and/or from periods of silence.

Read first: [catalog vs audio concept](../product/concept-catalog-and-audio.md) (states none/server/phone), [data-model.md](../specs/data-model.md), [add-song.md](../specs/add-song.md), [api.md](../specs/api.md), [library.md](../specs/library.md), [playback.md](../specs/playback.md), [task-0036](task-0036.md) (metadata model).

Inventory (to verify):

- `server/app/extractor.py` keeps only title, artist, duration, thumbnail, dates and genre from yt-dlp. `description` and `chapters` are returned by yt-dlp but dropped today.
- Audio reaches the server only through the iOS download; the web saves metadata and plays audio already on the server.
- iOS plays with AVPlayer and lock-screen controls; the song record has `id`, `file`, `duration`, `sources[]`, `tags`, `year`, `remix_year` and no notion of a time range.

# Phase 1: YouTube video with time codes imports like a playlist

> Alex: create task md: when importing a YouTube video with time codes - act the same as when importing a playlist

Build when Alex says go. Needs no audio: web and server only, catalog entries.

## Today

Pasting a YouTube video link into the Add dialog opens the single-song form. A DJ mix, a full album upload or a compilation is one long video, so it becomes one song of an hour or more. The track list that its author wrote down as time codes (`00:00 Artist - Title`) is ignored.

## Proposed behaviour

- When the video has a **track list** (at least two time codes, see below), the Add dialog treats it like a YouTube playlist (ADD-150 to ADD-159): the time codes become entries in the same import table, and "Add N songs" saves the songs and a playlist.
- **Where the time codes come from** (the one parser spec), first source that yields at least two entries wins, no merging:
  1. yt-dlp `chapters` metadata (title and start/end already structured; the extractor must keep `description` and `chapters`).
  2. The description: one entry per line that starts with, ends with, or is wrapped in a time code. Accepted shapes: `00:00 Artist - Title`, `1:02:30 Artist - Title`, `[00:00] Artist - Title`, `(00:00) Artist - Title`, `00:00 - Title`, `1. 00:00 Artist - Title`, `Artist - Title 00:00`. Minutes may be one or two digits, hours optional, `:` the only separator.
  3. The top pinned comment of the video, parsed with the same line rules (many mixes keep the list there).
- **Trigger:** at least two time codes, in ascending order. One time code, or a description that mentions a time only inside a sentence, does not trigger.
- **Entries** (`start`, `end`, `title`, `artist`):
  - `start` is the time code in seconds; `end` is the next entry's start, the last entry ends at the video duration.
  - Artist and title go through the same parsers as the playlist import ([ADD-154](../specs/add-song.md)): `titles.split_title`, the version and bracket handling (ADD-159), the clean-up (ADD-077, ADD-179) and the credit split (`feat.`, `vs`, `x`, ADD-165). The video's channel is the fallback artist when a line has no "Artist - Title" (open question C).
  - Lines that are not a time code (intro text, links, "Tracklist:") are ignored; a time-coded line that cannot be read into a title is kept as a flagged row (ADD-158 style, "Could not read this line") so the owner can fix or untick it. Always a suggestion, never applied silently.
- **Import table:** the same table as the playlist import (ADD-151 to ADD-153): one row per entry, with a time range column ("12:34 to 15:50") next to the duration, ticks by default for rows that are not duplicates and not longer than 5 minutes (ADD-152; the rule uses the entry length, not the video length), "In library" for duplicates, flags for unparsed lines. Select all, Select none, the counter and "Add N songs" behave as in ADD-151.
- **Playlist:** adding creates or extends a saved playlist exactly as in [task-0059](task-0059.md): named after the video title, songs in time order, `source: {type: "youtube", id: <video id>, url}`. Re-importing the same video appends only the missing entries; the "Save as playlist" option and the editable name stay.
- **How an entry plays** (phase 1): the catalog entry of each song points to the same video with a start offset, `https://www.youtube.com/watch?v=<id>&t=<SECONDS>`. The song stores `source: {type: "youtube", id, start, end}`; no audio is cut. Where the web plays audio that is already on the server, an entry without its own audio plays from the original link at that offset and stops at `end` (open question A).
- **Keep the single-video Add intact:** a video link with a track list shows a choice above the form, "This video has a track list: import N tracks" (primary) and "Add the whole video as one song". The second one opens the existing single-song form with no change. A video without a track list opens the form at once, as today, with no extra step and no delay beyond the details lookup the form already does.
- **Duplicates** are decided by video id plus start offset (the same video imported twice gives "In library" rows), then by the normalised title + artists + version match of ADD-153. A whole-video song and a track of the same video do not count as duplicates of each other.
- **Limits:** 200 entries per import (ADD-156), the playlist and quota caps of task-0058/0059. Guests and the public read-only view are unaffected (no import, ADR-0018). iOS later (phase 2).

## Phase 1 open questions

- A. How an entry plays: a catalog entry pointing to the same video with `&t=SECONDS` and an end time, no audio cutting in phase 1. **Recommended.** Alternative: cut audio on the server with ffmpeg at import time (needs the whole audio first and the iOS download flow; large for a 2-hour mix).
- B. Source order chapters, description, top pinned comment, no merging. **Recommended.** Alternative: also scan all comments (noisy, rate-limited, rejected).
- C. A line without "Artist - Title" (`00:00 Sunset`): title only, artist is the video's channel, row flagged "Artist is the channel". **Recommended.** Alternative: leave the artist empty.
- D. Minimum time codes to trigger: two. **Recommended.** Alternative: three, to avoid a false trigger on a start and an end time.
- E. The whole-video option is always offered as the second button. **Recommended.** Alternative: remember the choice per video id.
- F. Duplicates by video id + start offset, not by video id alone. **Recommended.**
- G. Time codes that overlap or go backwards: keep the ascending prefix, flag the first out-of-order line, drop the rest. **Recommended.**

## Phase 1 steps

1. **Parser and preview** (after task-0058 phase 1): a pure server module for the time-code lines (chapters, description, pinned comment) with a fixture file like `credit_title_cases.json`, entries with `start`/`end`, and `POST /preview` (or a sibling endpoint) returning `trackList: {source, entries}` next to the usual preview. Spec ids next to ADD-150 and in the API spec.
2. **Import table reuse and playlist creation** (after task-0059 phase 2): the choice "import N tracks / add the whole video as one song", the playlist-import view fed by the entries (time range column, flagged lines), songs saved as catalog entries with `source {type: "youtube", id, start, end}` and the `&t=` link, duplicates by id + offset, the playlist step of task-0059, playback from the original link at the offset in the web.

## Phase 1 acceptance (to refine when built)

- Spec ids in add-song.md (next to ADD-159) and api.md; server tests for the line shapes (`00:00 A - B`, `1:02:30 ...`, `[00:00] ...`, `00:00 - Title`, trailing time), the minimum of two, source priority, `end` of the last entry, ascending order and out-of-order lines, lines without an artist, and the single-video Add unchanged when there is no track list; web tests for the choice, the time range column and the duplicate rule by id + offset.

# Phase 2: analysis and features beyond time codes

Type: analysis first. NO code changes until Alex approves the analysis below. Starts after phase 1 is built; builds on the `source {start, end}` model of phase 1.

Covers: silence detection on downloaded audio, cutting audio into files (the iOS download of a track fetches only its time range with yt-dlp `--download-sections` or ffmpeg `-ss/-to`, so the phone holds a real file per song and plays offline; the web stays catalog-only, ADD-053), the timeline editor, and the iOS and Mac import view (needs Alex's permission to edit `ios/`).

## Suggestion sources beyond phase 1

1. Time codes (chapters, description, pinned comment): phase 1, parser specified there once.
2. Silence detection on downloaded audio (ffmpeg `silencedetect`: noise floor, minimum silence length, minimum segment length). Works only when the audio exists on the server or phone, so a "Suggest from audio" action, like Identify from audio.
3. Beat or energy change detection: deferred.

## Behaviour

- A timeline shows suggested split points with proposed names (split with the existing Artist - Title splitter, Title, Artist and Remix token pills).
- Alex accepts, edits, adds or removes points, previews by playing around a point, then creates N library items.
- No auto-split without approval.

## Design choice to analyse

Virtual segments (each item references the same audio file with start and end offsets; no re-encoding, fast, no extra storage) versus physical cut files (ffmpeg stream copy or re-encode; more storage, simpler players). Lean: virtual segments with `start` and `end` offsets, plus an optional "export as file" later. The analysis must give reasons and list consequences for:

- playback and gapless seeking on iOS and web (AVPlayer time ranges, boundary accuracy of m4a);
- progress and queue logic; lock-screen metadata and artwork;
- offline download (download once, play segments);
- library listing and counts; stats;
- deleting one segment vs the source;
- duplicates and share links;
- search and tags (segments inherit source tags; per-segment tags editable);
- the metadata model of [task-0036](task-0036.md): keep the models compatible;
- year and remix semantics: source publish date vs per-track release.

## Constraints

- Smallest coherent model.
- Never lose the original source link or item.
- Splitting is reversible (merge back, or delete segments).
- Signed-in owner only; guests stay read-only.
- Web and iOS have equivalent semantics.
- Do not auto-split without approval; show uncertainty for suggestions.
