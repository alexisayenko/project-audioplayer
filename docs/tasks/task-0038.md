# Phase 1: YouTube video with time codes imports like a playlist

> Alex: create task md: when importing a YouTube video with time codes - act the same as when importing a playlist

## Today

Pasting a YouTube video link into the Add dialog opens the single-song form. A DJ mix, a full album upload or a compilation is one long video, so it becomes one song of an hour or more. The track list that its author wrote down as time codes (`00:00 Artist - Title`) is ignored.

## Proposed behaviour

- When the video has a **track list** (at least two time codes, see below), the Add dialog treats it like a YouTube playlist (ADD-150 to ADD-159): the time codes become entries in the same import table, and "Add N songs" saves the songs and a playlist.
- **Where the time codes come from** (the one parser spec), first source that yields at least two entries wins, no merging:
  1. yt-dlp `chapters` metadata (title and start/end already structured; the extractor must keep `description` and `chapters`).
  2. The description: one entry per line that starts with, ends with, or is wrapped in a time code. Accepted shapes: `00:00 Artist - Title`, `1:02:30 Artist - Title`, `[00:00] Artist - Title`, `(00:00) Artist - Title`, `00:00 - Title`, `1. 00:00 Artist - Title`, `Artist - Title 00:00`. Minutes may be one or two digits, hours optional, `:` the only separator.
  3. The top pinned comment of the video, parsed with the same line rules (many mixes keep the list there).
- **Trigger:** at least two time codes, in ascending order. One time code, or a description that mentions a time only inside a sentence, does not trigger.
- **Entries** (`start`, `end`, `title`, `artist`):
  - `start` is the time code in seconds; `end` is the next entry's start, the last entry ends at the video duration.
  - Artist and title go through the same parsers as the playlist import ([ADD-154](../specs/add-song.md)): `titles.split_title`, the version and bracket handling (ADD-159), the clean-up (ADD-077, ADD-179) and the credit split (`feat.`, `vs`, `x`, ADD-165). The video's channel is the fallback artist when a line has no "Artist - Title" (open question C).
  - Lines that are not a time code (intro text, links, "Tracklist:") are ignored; a time-coded line that cannot be read into a title is kept as a flagged row (ADD-158 style, "Could not read this line") so the owner can fix or untick it. Always a suggestion, never applied silently.
- **Import table:** the same table as the playlist import (ADD-151 to ADD-153): one row per entry, with a time range column ("12:34 to 15:50") next to the duration, ticks by default for rows that are not duplicates and not longer than 5 minutes (ADD-152; the rule uses the entry length, not the video length), "In library" for duplicates, flags for unparsed lines. Select all, Select none, the counter and "Add N songs" behave as in ADD-151.
- **Playlist:** adding creates or extends a saved playlist exactly as in [task-0059](task-0059.md): named after the video title, songs in time order, `source: {type: "youtube", id: <video id>, url}`. Re-importing the same video appends only the missing entries; the "Save as playlist" option and the editable name stay.
- **How an entry plays** (phase 1): the catalog entry of each song points to the same video with a start offset, `https://www.youtube.com/watch?v=<id>&t=<SECONDS>`. The song stores `source: {type: "youtube", id, start, end}`; no audio is cut. Where the web plays audio that is already on the server, an entry without its own audio plays from the original link at that offset and stops at `end` (open question A).
- **Keep the single-video Add intact:** a video link with a track list shows a choice above the form, "This video has a track list: import N tracks" (primary) and "Add the whole video as one song". The second one opens the existing single-song form with no change. A video without a track list opens the form at once, as today, with no extra step and no delay beyond the details lookup the form already does.
- **Duplicates** are decided by video id plus start offset (the same video imported twice gives "In library" rows), then by the normalised title + artists + version match of ADD-153. A whole-video song and a track of the same video do not count as duplicates of each other.
- **Limits:** 200 entries per import (ADD-156), the playlist and quota caps of task-0058/0059. Guests and the public read-only view are unaffected (no import, ADR-0018). iOS later (phase 2).

## Phase 1 open questions

- A. How an entry plays: a catalog entry pointing to the same video with `&t=SECONDS` and an end time, no audio cutting in phase 1. **Recommended.** Alternative: cut audio on the server with ffmpeg at import time (needs the whole audio first and the iOS download flow; large for a 2-hour mix).
- B. Source order chapters, description, top pinned comment, no merging. **Recommended.** Alternative: also scan all comments (noisy, rate-limited, rejected).
- C. A line without "Artist - Title" (`00:00 Sunset`): title only, artist is the video's channel, row flagged "Artist is the channel". **Recommended.** Alternative: leave the artist empty.
- D. Minimum time codes to trigger: two. **Recommended.** Alternative: three, to avoid a false trigger on a start and an end time.
- E. The whole-video option is always offered as the second button. **Recommended.** Alternative: remember the choice per video id.
- F. Duplicates by video id + start offset, not by video id alone. **Recommended.**
- G. Time codes that overlap or go backwards: keep the ascending prefix, flag the first out-of-order line, drop the rest. **Recommended.**

## How it works end to end

1. The user opens "Add album" (web `albums.js` dialog, later iOS) and pastes a YouTube video link (`youtu.be/<id>?si=...`, `watch?v=<id>&...`; `si`, `t`, `list` are ignored by the existing URL cleaning). The dialog now recognises three sources: Discogs, a YouTube playlist, a YouTube video. For a video it calls the preview (below). The server reads the video with yt-dlp (no download): title, uploader, duration, thumbnail, `description` and `chapters`. Sources of the track list, first with at least two entries wins, no merging: (a) yt-dlp `chapters` (structured), (b) the description, (c) the top pinned comment (as phase 1, optional and last), (d) text pasted by the user.
2. The TRACKLIST PARSER (a pure function, `server/app/tracklist.py`, with a fixture file like `credit_title_cases.json`, a JS twin only if the client must re-parse a pasted text locally) turns lines into entries `{start, end, trackNo, raw, artists[], featuredArtists[], title, version?, flags[]}`.
3. The PREVIEW step shows an editable table (below). Nothing is created before the last step (the CAT-058 rule).
4. The CREATE step (commit) creates the Album (task-0120) with one metadata-only song per included track, each song carrying `sources[0] = {type: "youtube", ref: <video id>, trim_start, trim_end, duration}` (the task-0045 recipe, so a track is always reproducible from the video), and links track to song. The album `source` is `{type: "youtube", id: <video id>, url, kind: "video"}` (the duplicate check of `albums.find_source` must tell a video from a playlist: the same video added twice answers "already in your albums").
5. The audio comes from the SPLIT JOB (below): one download, N ffmpeg cuts, each file attached to its song. On the web it runs when "Auto-download songs" is on (PLY-110) or when the user presses "Get audio" on the album page; on iOS the app calls it and then downloads the per-track files to the phone like any song (`getAudio`, `download`, "Download album" of task-0120 phase 5).
6. When the video has no track list (or the link is a SoundCloud mix, which has none), the preview returns an empty list and the dialog shows "No track list found. Paste one:" with a text box; the same parser reads it and its `start` times drive the same split. A pasted list with no time codes is refused (it is a playlist of names: use Drafts).

## Parser requirements

- Time code at the line start (`00:00`, `0:00`, `1:02:30`, `01:02:30`), wrapped (`[00:00]`, `(00:00)`), followed by a separator (`00:00 - Title`, `00:00 | Title`, `00:00: Title`) or at the line end (`Artist - Title 00:00`, `Artist - Title (00:00)`). Minutes and seconds one or two digits, hours optional, `:` the only separator, `.` not accepted as a separator (`1.02` is a number). `MM:SS` with minutes of 60 or more is read as minutes (`75:30`), up to 999.
- Optional numbering before or after the time code: `01.`, `1)`, `1 -`, `#1`, `12 .Shanti` (stray space before the dot), `Track 3:`; it becomes `trackNo` and is not part of the title. No numbering: `trackNo` is the order of appearance.
- Separators between artist and title: ` - `, en dash `–`, em dash `—`, ` | `, a colon in `Artist: Title` only when there is no other separator; a hyphen without spaces never separates. No separator at all: title only, the artist is the album artist or the channel, flag "Artist is the channel" (phase 1 open question C).
- Artists: `A & B`, `A, B`, `A x B`, `A feat. B`, `A ft. B`, `A vs B` through the credit split (ADD-165, CRD-010 to CRD-016); a lone `and` does not split (flagged). Version and remix suffixes in brackets (`(Original Mix)`, `[Remix]`, `(Artist Remix)`) through the version split of ADR-0024 and ADD-159; promo noise cleaned as ADD-077.
- Ignored: blank lines, header lines without a time code (`Tracklist:`, `Track list`, `Setlist`), links, and a trailing `Total time 1:35:20` or `Total: 95:20` line (never a track; a total is kept as a check against the duration). A time-coded line that cannot be read into a title is kept as a flagged row ("Could not read this line"), never dropped silently.
- Order: ascending. A non-increasing or equal time code is flagged ("Time is not after the previous track") and kept in the table for the user to fix; the track is excluded from the split until it is fixed (phase 1 question G dropped the tail; here the user fixes it, because the table is editable).
- A time code beyond the video duration is flagged "After the end of the video" and excluded; `end` of the last track is the duration (the real duration of the file is checked again by the job with ffprobe).
- A first time code above zero ("00:42 first track"): the first track starts at that time; the part before is not a track (the table offers "Add intro track" only as a manual row).
- Fewer than two entries: not a track list (a lone "Watch at 12:30" in a sentence does not trigger).
- Lengths: at most 200 entries (ADD-156) and each track at least 5 s (a shorter span is flagged as a probable mis-parse).

## Split job (server)

- `POST /albums/{id}/split-audio` starts ONE job per album through `downloads.run_scheduled` (so the per-user concurrency and global caps apply), tracked with `downloads.new_job` and `jobs.Tracker`/`jobs.public` like a download: states queued, downloading (percent), splitting (k of N), done, failed with an `error_code`.
- Steps: charge one add (the whole video is one fetch, ADR-0012; the N metadata-only songs were free); check the song and byte limits again; download the full audio once into a staging folder (`extractor.download_audio` without a trim); `trim.probe_seconds` for the real length and clamp the last `end`; for each included track cut with ffmpeg `-ss start -to end`, re-encoded to AAC m4a (`trim.encode_command`; stream copy would snap to frames), with an optional fade (question JN); attach the file to the song the way a download does (`downloads._attach_audio`: duration, BPM, peaks, cover from the video thumbnail); delete the staging file. A failed track does not stop the others; the job reports "11 of 13 tracks have audio, 2 failed" and "Retry the failed tracks" reuses the staging file when it is under one hour old, otherwise it is a new fetch and a new add.
- Built 2026-10-26 (`server/app/video_split.py`, API-290 to API-295, tests `server/tests/test_video_split.py` with faked yt-dlp and ffmpeg; not run against the real tools yet): `submit` registers the job and queues it on the scheduler, `run_split` is the worker, `public` the status body, `precheck` and `check_request` the refusals. Differences from the plan above: the cut is a stream copy of the AAC audio (accurate to one AAC frame, no generation loss) and a re-encode only when a fade is applied; the staging folder is `.split-<videoId>` in the user's audio folder, kept for an hour only after a partial failure; the route, the album record and the song records belong to `album_video.py`.
- Private, age-restricted, geo-blocked, deleted videos fail at the preview with the existing messages (`MSG_PRIVATE` style, 404 `not_found`, 422 `age_restricted`); a video that goes away between preview and split fails the job with the same codes.
- Time and size: a 2-hour video is about 110 MB of audio at 128 kbit/s and takes minutes; the job runs in the existing scheduler thread and never blocks requests. Copyright and ToS: downloading from YouTube carries the same risk as every other download in the app (CLAUDE.md: "not for distribution"); nothing new is published and the album stays inside the user's own library.
- Quality limit to state in the UI: a continuous DJ mix has no true track boundaries (transitions overlap), so a cut at the timestamp is approximate; per-track fades and the boundary nudge (question JN) soften it.

## Design choice to analyse

Virtual segments (each item references the same audio file with start and end offsets; no re-encoding, fast, no extra storage) versus physical cut files (ffmpeg stream copy or re-encode; more storage, simpler players). Lean: virtual segments with `start` and `end` offsets, plus an optional "export as file" later. Update 2026-10-26: for tracks of an album made from a time-coded video Alex decided physical files (Phase 1B, one download and ffmpeg cuts), so the lean towards virtual segments now applies only to later splits by silence. The analysis must give reasons and list consequences for:

- playback and gapless seeking on iOS and web (AVPlayer time ranges, boundary accuracy of m4a);
- progress and queue logic; lock-screen metadata and artwork;
- offline download (download once, play segments);
- library listing and counts; stats;
- deleting one segment vs the source;
- duplicates and share links;
- search and tags (segments inherit source tags; per-segment tags editable);
- the metadata model of [task-0036](task-0036.md): keep the models compatible;
- year and remix semantics: source publish date vs per-track release.

## Constraints

- Smallest coherent model.
- Never lose the original source link or item.
- Splitting is reversible (merge back, or delete segments).
- Signed-in owner only; guests stay read-only.
- Web and iOS have equivalent semantics.
- Do not auto-split without approval; show uncertainty for suggestions.
