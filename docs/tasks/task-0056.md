# Count listening statistics: listened, or started but changed

> Alex: create an md task: count statistics for listened songs: time started, if listened more than 90% then mark as listened, otherwise "started, but changed"

## Proposed behaviour

- Every playback produces a **play record**: song id, started-at timestamp, device/platform (web, iOS, Mac), duration actually listened, song duration.
- Outcome of a play:
  - `listened` when at least 90% of the song was listened (constant `LISTENED_THRESHOLD = 0.9`);
  - `started, but changed` otherwise (the user switched to another song, skipped, or stopped).
- Plays shorter than a minimum (5 s) are ignored as accidental.
- "Listened" is measured by **accumulated actual play time**, not by the final position, so seeking to the end does not count as listened. Forward seeks add nothing; backward seeks and replays of the same part do add time, capped at the song duration.
- A repeat of the same song is a separate play.
- Per-song aggregates: times listened, times started-but-changed, first listened at, last listened at.

### Where it shows

- Song card: "Listened 3 times · last 12 Oct" (and "Started, not finished 2 times" when relevant).
- Library: a filter and sort "Never listened".
- Song stats page: a "Listening" section with most listened, most started-but-changed, and listened per day and per week.

### Storage and API

- Server side, per user, in its own file (`users/<uid>/plays.json`, like `drafts.json`), through the same atomic write and git-synced mechanism; or a compact append-only log (one line per play) if a single JSON file grows too large.
- Writes are **batched** (the client collects records and sends them every N seconds or on pause, song change and page hide): one commit per batch, never one per play, because git sync is single-writer.
- The guest/public view has no plays and cannot write.
- API sketch:
  - `POST /plays` with a batch of records `[{song_id, started_at, platform, listened_s, duration_s}]`; the server computes the outcome, and an idempotency key per record avoids duplicates on retry.
  - `GET /stats/listening` returns the aggregates per song plus the day/week series for the stats page.
- Privacy: plays are visible only to their owner; no sharing, no public aggregates; deleting an account deletes its plays.

### Hooks

- Web: the existing player events in `web/js/player.js` (`play`, `pause`, `timeupdate`, `ended`, next/prev, song change). A play is opened on `play` of a new song and closed on `ended`, song change or page hide; `timeupdate` ticks accumulate actual played seconds.
- iOS (later): AVPlayer observers (periodic time observer, item end, item change), records kept in an offline queue and flushed when online.

## Open questions

- A. Threshold and measure: 90% of the duration by accumulated play time. **Recommended.**
- B. Minimum play length: 5 s, shorter plays ignored. **Recommended.**
- C. A song paused and then resumed: one play, as long as it stays the current song. **Recommended.**
- D. Autoplay of the queue: counts the same as a manual play. **Recommended.**
- E. iOS records plays made offline and flushes them later. **Recommended.**
- F. Retention: keep all plays for now; aggregate after 12 months only if the file becomes large. **Recommended.**
