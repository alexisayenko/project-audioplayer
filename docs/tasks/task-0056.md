# Count listening statistics: listened, or skipped

> Alex: create an md task: count statistics for listened songs: time started, if listened more than 90% then mark as listened, otherwise "started, but changed"

Decided 2026-10-20 (chat): the stored record is minimal (timestamp, song id, listened seconds); the outcome is computed when reading. "Started, but changed" is called `skipped` below.

## Proposed behaviour

- Every playback produces one **play record**: `timestamp` (when listening started), `song_id`, `listened_s` (accumulated actual play time in seconds). Nothing else is stored: no platform, no song duration, no outcome.
- The outcome is computed on read, never stored:
  - `listened` when `listened_s >= 0.9 x` the song's **effective window** (constant `LISTENED_THRESHOLD = 0.9`);
  - `skipped` otherwise (this includes started-but-changed: the user switched to another song, skipped, or stopped).
- The effective window is the song duration after the auto-jump start ([task-0051](task-0051.md)), the clip ([task-0045](task-0045.md)) and the silence trim ([task-0052](task-0052.md)) once they exist; today it is the full duration. Because the outcome is computed on read, changing the threshold or the window rules needs no migration.
- Plays shorter than 5 seconds are ignored as accidental.
- "Listened" is measured by **accumulated actual play time**, not by the final position, so seeking to the end does not count as listened. Forward seeks add nothing; replays of the same part do add time, capped at the window.
- A song paused and then resumed while it stays the current song is one play.
- Autoplay of the queue counts like a manual play.
- A repeat of the same song is a separate play.

### Where it shows

- Song card (info box): a small table with the rows Listened and Skipped and the columns Today, Last 7 days, Last 30 days, All time. Below it: "Total listened" (sum of `listened_s`, shown as h and min) and "Last listened" as a date (no time). No first-listened date, no platform.
- Library: a "Never listened" filter and a sort by last listened.
- Song stats page: a "Listening" section with most listened, most skipped, and listened per day and per week (see the open question on scope).

### Storage and API

- One append-only CSV per user, header line `timestamp,song_id,listened_s`, three columns only, one line per play. Timestamps are ISO 8601 UTC; `listened_s` is in seconds. **Storage decision, 2026-10-21 (Alex):** the live file is kept OUTSIDE the repo, like the audio pool and `.peaks/`: `<AUDIO_PLAYS_DIR, default <music root>/.plays>/<uid>/play-history.csv` (on perkunas `/srv/music/.plays/<uid>/`). A background task copies it ONCE A DAY into `users/<uid>/play-history.csv` of the git-synced data tree (one commit `sync listening history`, only when the content changed) as a snapshot; the outside file stays the source of truth, so a play never makes a commit.
- Appends are **batched**: the client collects records and sends them every few minutes and on pause, song change and page hide, so there is one git-synced commit per batch, never one per play (git sync is single-writer).
- Each batch carries a unique key, so a retry is not appended twice; the server keeps the last N keys.
- The guest/public view has no history and cannot write.
- API:
  - `POST /plays`: a batch of `{timestamp, song_id, listened_s}` plus the batch key.
  - `GET /stats/listening`: per-song counts of listened and skipped for the four windows (today, 7 days, 30 days, all time), total listened and last listened, aggregated server-side from the CSV; optionally cached and invalidated on append. Owner and signed-in user only.
- Privacy: the CSV and the API are per user and visible only to the owner; no sharing, no public aggregates; account deletion removes both the outside file and the in-repo copy (`plays.delete_user`).

### Hooks

- Web: the existing player events in `web/js/player.js` (`play`, `pause`, `timeupdate`, `ended`, next/prev, song change). A play is opened on `play` of a new song and closed on `ended`, song change or page hide; `timeupdate` ticks accumulate actual played seconds.
- iOS: AVPlayer observers (periodic time observer, item end, item change), records kept in an offline queue and flushed when online (needs Alex's permission to edit `ios/`).
- Recording is fire-and-forget: a failed POST never touches playback; failed batches wait in a local queue and are retried with the same batch key.

## Bug 2026-10-21: one listen recorded as three skips (fixed, deployed 2026-10-21)

Cause: `web/js/play-recorder.js` closed the open play on every `visibilitychange` to hidden (and on `pagehide`), so each tab switch or screen lock while audio kept playing ended the play and the next tick began a new one; a 4:53 song heard once became three plays of about 80 s, all under the 0.9 threshold. Pause, flush, re-render (`sync`), seek and loop paths do not close the play (checked).

Fix: hidden only persists the open play and flushes already closed plays; the play keeps running. `pagehide` closes the accumulated seconds (if at least 5 s) as a record and starts a continuation flagged `cont: true`; a page load of the same song within 10 minutes of a `pagehide` (`ap2.plays.last`) also starts a `cont` play. New optional boolean on a play record, `cont: true`: "continues the previous play of the same song"; the server merges it into the previous record of that song on read (summing listened seconds, keeping the earlier timestamp). Tests PLY-178, PLY-179 written in `play-recorder.test.mjs`, not run.

## Continuation of one listen (server), built, deployed 2026-10-21

A live listen of a 293 s song was recorded as three plays of about 80 s, counted as 3 skipped. Server side: `POST /plays` takes an optional `cont: true` per play; when the user's last stored record is the same song and the play starts within 15 minutes of that record's end, its seconds are added onto that record in place (last CSV line rewritten atomically under the user lock; the CSV keeps three columns); a `cont` piece under 5 s is kept only this way, pieces inside one batch merge too, a `cont` play with no match is appended as usual (dropped when under 5 s). On read, `plays.merge_fragments` joins consecutive records of one song when the previous is under 0.9 x duration, the gap from its end to the next start is at most 120 s and timestamps are in order (sum capped at 1.1 x duration), so already stored fragments are repaired without rewriting the file. Alex's three 80 s records now count as one 240 s play, still "skipped" by the 0.9 rule (240 < 263.7); the threshold is unchanged. Tests written, not run.

Second trigger, during continuous playback (Culture Beat - Mr. Vain): the recorder asked `player.current?.id`, which is `null` whenever the song is briefly missing from the store (library or catalog refresh, e.g. after `plays-flushed` or a 3-minute reload); `sync()` saw `open.song_id !== null` and closed the play, then reopened it on the next tick. Fix: the recorder is given `player.currentId` (the queue item id, independent of the store) and `sync()` never closes on an empty id. A flush never closes the open play (it only sends queued, closed records). Test PLY-172 added, not run.

Third trigger (short first piece, back-to-back pieces, no `cont`): a transient other song id from the queue (queue index flicker on a queue rebuild or refresh) made `sync()` close the play of song A and open and drop (under 5 s) a play of the other song, then reopen A: contiguous A pieces with no rows for the other song. Fix: with the audio `src` unchanged since the play began, an id mismatch is ignored; only a changed `src` (a real song change), `ended` or `pagehide` close a play. `waiting`, `stalled`, seeks and renders never close it. Tests added, not run; the queue flicker source itself was not traced.

Diagnostics (deployed 2026-10-21): `play-recorder.js` keeps the last 40 opens, closes and ignored id flickers in `localStorage['ap2.plays.log']`; `window.apPlaysLog()` returns it. Test PLY-180 written, not run. Remove once the splitting cause is confirmed.

Playing-now card (LIB-206): the song card of the currently playing song shows "·" instead of Skipped numbers and a note until the song ends; `song-ended` event added in `player.js`, stats refresh 2.5 s after it. Tests written, not run.

Shuffle prefers less-played songs (PLY-178): in shuffle mode the next song is drawn from a weighted order where weight = 1 / (1 + n)^2 and n = listened.d30 + skipped.d30 (songs absent from `GET /stats/listening` count 0). The order is built once per round by Efraimidis-Spirakis sampling (key = rng^(1/weight), sorted descending), not per Next; it is rebuilt when the queue ids change, when a round restarts under Repeat whole list (the last song is kept off the first slot), and when the counts first arrive. Uses the cached `getListening()` synchronously, refreshing in the background; without data (guest, failure, not loaded) it is a uniform shuffle. Code: `web/js/shuffle-pick.js`, `queue-logic.js` (`shuffleRank`), `player.js`. Tests `web/js/shuffle-pick.test.mjs` written, not run.

Library table view (LIB-209): a List | Table switch in the Library shows the current result as a sortable table (Song, Length, Times listened, Times skipped, Total listened); code `web/js/library-table.js`, test `web/js/library-table.test.mjs` written, not run.
