# Count listening statistics: listened, or skipped

> Alex: create an md task: count statistics for listened songs: time started, if listened more than 90% then mark as listened, otherwise "started, but changed"

Decided 2026-10-20 (chat): the stored record is minimal (timestamp, song id, listened seconds); the outcome is computed when reading. "Started, but changed" is called `skipped` below.

## Proposed behaviour

- Every playback produces one **play record**: `timestamp` (when listening started), `song_id`, `listened_s` (accumulated actual play time in seconds). Nothing else is stored: no platform, no song duration, no outcome.
- The outcome is computed on read, never stored:
  - `listened` when `listened_s >= 0.9 x` the song's **effective window** (constant `LISTENED_THRESHOLD = 0.9`);
  - `skipped` otherwise (this includes started-but-changed: the user switched to another song, skipped, or stopped).
- The effective window is the song duration after the auto-jump start ([task-0051](task-0051.md)), the clip ([task-0045](task-0045.md)) and the silence trim ([task-0052](task-0052.md)) once they exist; today it is the full duration. Because the outcome is computed on read, changing the threshold or the window rules needs no migration.
- Plays shorter than 5 seconds are ignored as accidental.
- "Listened" is measured by **accumulated actual play time**, not by the final position, so seeking to the end does not count as listened. Forward seeks add nothing; replays of the same part do add time, capped at the window.
- A song paused and then resumed while it stays the current song is one play.
- Autoplay of the queue counts like a manual play.
- A repeat of the same song is a separate play.

### Where it shows

- Song card (info box): a small table with the rows Listened and Skipped and the columns Today, Last 7 days, Last 30 days, All time. Below it: "Total listened" (sum of `listened_s`, shown as h and min) and "Last listened" as a date (no time). No first-listened date, no platform.
- Library: a "Never listened" filter and a sort by last listened.
- Song stats page: a "Listening" section with most listened, most skipped, and listened per day and per week (see the open question on scope).

### Storage and API

- One append-only CSV per user: `users/<uid>/play-history.csv`, header line `timestamp,song_id,listened_s`, three columns only, one line per play. Timestamps are ISO 8601 UTC; `listened_s` is in seconds. Written through the same git-synced mechanism as the other per-user files.
- Appends are **batched**: the client collects records and sends them every few minutes and on pause, song change and page hide, so there is one git-synced commit per batch, never one per play (git sync is single-writer).
- Each batch carries a unique key, so a retry is not appended twice; the server keeps the last N keys.
- The guest/public view has no history and cannot write.
- API:
  - `POST /plays`: a batch of `{timestamp, song_id, listened_s}` plus the batch key.
  - `GET /stats/listening`: per-song counts of listened and skipped for the four windows (today, 7 days, 30 days, all time), total listened and last listened, aggregated server-side from the CSV; optionally cached and invalidated on append. Owner and signed-in user only.
- Privacy: the CSV and the API are per user and visible only to the owner; no sharing, no public aggregates; account deletion removes the file.

### Hooks

- Web: the existing player events in `web/js/player.js` (`play`, `pause`, `timeupdate`, `ended`, next/prev, song change). A play is opened on `play` of a new song and closed on `ended`, song change or page hide; `timeupdate` ticks accumulate actual played seconds.
- iOS: AVPlayer observers (periodic time observer, item end, item change), records kept in an offline queue and flushed when online (needs Alex's permission to edit `ios/`).
- Recording is fire-and-forget: a failed POST never touches playback; failed batches wait in a local queue and are retried with the same batch key.
